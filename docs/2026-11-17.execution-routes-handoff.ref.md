# Ordered execution routes: implementation handoff

Date: 2026-11-17

## Outcome and scope

The [execution-chain spec](specs/execution-chains.spec.md) owns the general
configuration contract. Every difficulty has the same ordered list of complete
alternatives: an explicit harness/executor pair or a single-layer harness/model.
Fallback advances that entire alternative. It never independently ranks two
model arrays or makes `trivial` a special topology.

This work implements only the safe, pure foundation:

- `packages/core/src/argus_core/execution_chains.py`: closed discriminated policy,
  exact account selectors, static role/provider/model-source compatibility,
  pair restrictions, per-difficulty inheritance and stable revisions.
- `packages/core/tests/test_execution_chains.py`: executable policy and
  inheritance coverage. Single mode cannot carry an executor, even null.
- No API, settings registry, database migration or worker imports the new module.
  The policy cannot yet be saved or run. This is not a repaired Setup or fleet.

The remaining feature crosses claim admission, leases, durable task lifecycle,
worker/runtime handoff, model selection and Setup. A partially wired control
would promise ordering and isolation that runtime does not enforce. Keep the
feature unavailable until the dependent implementation and gates below exist.

## Inspection findings in the previous prototype

These findings refer to the preserved uncommitted prototype, not to main or to
runtime-tested defects. They are reasons not to publish it as a completed fix.

1. `tasks/execution_routes.py:report` releases all caller engine/executor leases
   by role. A selection carries exact lease IDs, but release does not use those
   IDs. The production path must fence task, attempt, agent, selection generation
   and exact selected tuple before releasing anything.
2. `reset` deletes traversal state including generation. The protocol needs a
   monotonic generation or fresh selection nonce across reset/invalidation;
   deleting the cursor must not accidentally recycle selection identity. Attempt
   fencing remains mandatory even with a monotonic generation.
3. `reserve` checks one `execution-chains-v1` capability and harness providers;
   it does not validate per-adapter/per-role conformance. `argus.ts` adds that
   capability when account model/recycle callbacks merely exist. Those callbacks
   do not prove every proposed runtime/adapter combination works.
4. `wake` indiscriminately calls unblock for every route-wait task and is not
   wired to all quota/account/runtime lifecycle paths in the inspected changes.
   Availability, waiting and waking need the same non-mutating eligibility logic
   as tuple admission, without touching human or policy decisions.
5. The channel handles explicit-route quota specially, but maps other classified
   failures back to ordinary `worker_fail`. The API accepts a broader advance
   reason set. Failure classification, stop acknowledgement, account exhaustion
   and retry accounting need a single reviewed allowlist and matching tests.
6. The prototype hashes the entire merged policy into a revision. Editing one
   difficulty resets another difficulty's traversal. The new pure resolver
   instead hashes each effective difficulty, including source and ordered list.
7. Its static pair validator applies local-only restrictions to custom harnesses.
   Main's `argus-delegate.mjs` has separate `withoutCustomHarness` stripping;
   local task-pin restrictions are not a general custom pair prohibition. The
   core foundation keeps the conservative existing local pair matrix and does
   not extend that limitation to custom harnesses.
8. No dashboard editor or generated client changes exist in that prototype.
   Existing Setup cannot add/reorder/remove complete alternatives or show the
   required effective project/global route. A settings backend alone is not UI
   delivery. None of the prototype's executable behavior is certified here.

## Contract and dependency-ordered remaining split

The owning spec fixes the wire setting as `execution.chains`, version 1; the
word "chain" means an ordered list of complete routes. Do not introduce a second
competing setting named routes. All four difficulty keys accept identical lists.
The pure core resolver returns `legacy` with no alternatives when neither scope
has a list; the stored scoped policy remains separate from its effective result.

### 1. Shared settings and diagnostics contract

Use the new core policy. Finish `ExecutionCapability` and typed setting/effective
response models in core; do not use a static target matrix as runtime readiness.
Wire `settings/{registry,service}.py`, `engines/routes.py`, `tasks/route.py` and
REST/MCP wrappers to one shared service. Validate exact account ID, provider,
role configuration, supported model source and legacy env locks on save. Disabled
or exhausted accounts can be saved with warnings; unsupported roles cannot.

Acceptance: typed API/MCP roundtrip; unknown field/version rejection; save/reopen;
all difficulty levels; project whole-list replacement and per-level reset;
account deletion/provider mismatch; no credential disclosure or network writes.
Keep the setting execution-disabled until the runtime slices are complete.

### 2. Atomic tuple admission and exact claim snapshot

Integrate account service, task engine gate and claim around one resolver.
Evaluate explicit alternatives in order. Reserve both roles in one write/savepoint
or neither. Single mode reserves only the engine. Do not call global provider
ranking to fill a missing layer. Preserve native safe reuse and PR #407's custom
executor lease/settings/gateway separation, even on one custom account.

Acceptance: full second account rollback; competing claims; account priorities
cannot change the configured pair; missing executor does not create an attempt;
no executor lease for single; local harness + explicit OpenCode/custom route;
custom same-account capacity refusal; legacy/pin behavior unchanged.

### 3. Durable traversal, lifecycle and scoped worker protocol

Add the next additive migration after rechecking main's migration number. Persist
cursor, route-affecting fingerprint, selected snapshot, monotonic generation and
skip evidence. All task/attempt transitions use `Database.write()` and `tx.now`.
Add worker selection/stop acknowledgement contracts and retry/unblock reset to
both transports. Reaper, account/quota wake and diagnostics share resolution.

Quota or provider unavailability may advance only after old runtime stop. Release
only the exact tuple. Unknown/ordinary implementation failures retain the route;
existing escalation chooses the next difficulty. Security/guard/budget denial,
owner decisions and stop failure never fall through. Exhaustion blocks without
wrapping or synthesizing cloud fallback. A policy change affects future claims,
not the frozen running attempt. Pins choose the complete legacy pin path; never
merge one pin with half an explicit route.

Acceptance: restart/reopen; duplicate/stale reports; reset without generation
reuse; transient preflight skips reconsidered on wake; exact quota transition;
retry limits and escalation; denied stop/guard/human-decision negative controls.

### 4. Worker adapters and exact model application

Update `argus.ts`, account application, model-policy snapshot and delegate to
consume the exact claim snapshot. Explicit models cannot walk an independent
policy chain or failure-index model fallback. Check selected IDs/provider/model
and installed adapter capabilities before execution. Do not repurpose the Claude
single-layer experiment. Executor-only CLIs remain unsupported as harnesses.

Acceptance: native/local/custom direct adapters with fake providers; no executor
probe/lease/call in single mode; paired-to-single and single-to-paired transitions;
old worker refusal; stop handoff; fixed model after ordinary retry; separately
scoped custom executor gateway lease and unchanged legacy PR #407 regressions.
Only verified adapters may be advertised as runnable. No paid calls are required.

### 5. Setup editor and operator evidence

Regenerate OpenAPI/client types. Add a capability-driven complete-route editor
at both `#setup` and `#setup/settings`, with all four difficulties and scope picker.
Add/remove/reorder whole alternatives, add/remove the optional executor layer,
and show stored versus inherited effective lists, source/revision and account
model facts. Clearing one scoped difficulty restores inheritance, not an empty
executable list. Unsupported controls explain the reason. Saving a preview must
not materialize inherited values or mutate accounts.

Acceptance: exact mixed-route payloads, ordering/topology changes, project reset,
stale account model warnings, pins/env locks and legacy labels; isolated fixture
API/browser evidence, no preview credentials or server reload.

### 6. Joint compatibility gate

Run the full Python/Node/NanoClaw suites, `make check`, `make build`, OpenAPI
freshness and MCP tool-token delta after protocol edits. Add per-difficulty
mixed-topology route tests through claim, quota transition and model application.
Only then update implementation statuses and allow execution configuration.
Publication and live activation remain separate owner-authorized operations.
