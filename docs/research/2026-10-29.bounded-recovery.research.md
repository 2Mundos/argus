## 1. Restart concurrency and where a start throttle would live

**Verified (Argus side):**

- The claim loop in `argus.ts` (`claimLoop`, ~L2980–3080) is sequential. It `await`s `runTask(task)` and
  only then claims again. One worker channel therefore runs one task at a time, so Argus itself never
  starts several sessions at once from one loop.
- On startup the loop waits for `startupReady` (`startupAdoptionDone`) before it claims. The gate
  (`patch-startup-adoption-gate.py`) only orders adoption before claiming. It does not limit starts.
- Concurrency after a restart comes from the number of worker instances that claim at once. The
  reconciler (`worker-lifecycle.spec.md` §3.5) starts instances up to `desired_replicas` (bounded by
  `max_replicas`), reserving a DB slot per start. The spec names no start rate limit.
- `argus.ts` has no start deadline and no start-concurrency setting (grep for deadline, concurrency,
  capacity, cpus, parallel: none in the channel).

**Unverified (NanoClaw upstream):**

- Whether NanoClaw's host sweep wakes or spawns several containers at once on restart for pending
  inbound rows. The patches show that `reconcile-session.ts` and `host-sweep.ts` exist and that
  adoption stops listed containers that have no database row. Nothing shows a start path or a limit.

**Where a throttle would live:**

- The start gate belongs to the process that starts containers, i.e. `container-runner.ts` (or the
  NanoClaw sweep that calls it). The channel adapter cannot count NanoClaw's container spawns; it only
  sees its own claims. A channel-side throttle would limit claims, which is a different and weaker lever.
- The reconciler (Argus API, `worker-lifecycle` §3.5) is the other option. It can cap how many instances
  it starts per tick, with a longer start deadline. That needs no NanoClaw patch, and it covers the case
  the draft is about (instances starting after a node restart). It does not cover NanoClaw waking
  several existing containers at once.
- **Recommendation:** put the start gate in the reconciler first (Argus-owned, testable, no upstream
  patch). Check the upstream start path before deciding whether a container-runner patch is needed; that
  needs the NanoClaw source at the pin (`8fbacc91`).

**Concurrency cap:** the throttle only gates starts. Running sessions are never capped (the draft says
the same). `worker-efficiency` P5 and the no-ceiling patch already say that a long-lived session is valid.
No running-session cap is needed by the evidence here.

## 2. Exactly-one automatic resume (`session` class)

**Current behaviour (verified):** `failure-classes.spec.md` §3.2 says a `session` fail requeues at once and
spends an attempt. The `session` class is `session_lost`, `stalled`, `timeout`, `lease_expired`,
`agent_ended`. `worker-efficiency` P6 says "retry once and resume (P4)", and P4 is *partial*.
`failure-classes` §2 keeps today's retry until P4 lands. So a crashing session can use up `max_attempts`
at once.

**Proposed rule (refines the `session` row; no contradiction with the current spec):**

- After an unexpected exit (`session_lost` or `agent_ended`), requeue once, and only after the old
  container is confirmed gone (the `session_lost` path already checks the container within 90 s).
- A second automatic requeue needs *new progress* since the last automatic resume: a milestone or a
  completed turn, recorded as a progress event. Otherwise the attempt fails with its cause (the exit code
  and stderr tail, per P6), and no further attempts are spent on the same crash.
- Operator action (retry, unblock) resets the rule.
- `stalled` and `timeout` are not "unexpected exits" and keep their current rule. The draft should say so.

**Open:** "new progress" must be a signal the server can see. Milestones and checkpoints exist
([progress milestones](../specs/progress-milestones.spec.md)). The exact event that counts still needs a choice.

## 3. Unknown outcome for dispatched-but-unconfirmed work

**Audit of dispatch-then-confirm writes:**

| Write | Confirm | Dies in between | Current behaviour | Needs `unknown`? |
| --- | --- | --- | --- | --- |
| Steer (task-steering §3.4, §3.6) | heartbeat `steer_acks` after `onInbound` resolves | injected, ack lost | stays `pending`; re-injected on the next heartbeat in the same attempt; expires at attempt end, without notice | **Yes.** Currently at-least-once within an attempt; the draft says "not delivered again". Contradicts the current spec, see below. |
| Steer across attempts | attempt end | — | expired; never carried over (§3.3) | No; already the draft's rule. But the next attempt is not told that a steer may have happened. |
| PR create (task-delivery, `argus-github-api create`) | API response | response lost | create is idempotent per head/base | No (idempotent by design). |
| Comment create (`comment-create --idempotency-key`) | API response | response lost | keyed; a retry returns the existing comment | No, if callers pass the key. Verify that every caller does. |
| Checkpoint write (task-checkpoint) | manifest hashes | crash mid-write | atomic rename, hash-verified restore | No; restore already refuses partial state. |
| Lease / claim / complete / fail | DB write (`Database.write()`) | fenced by attempt and assignee | `409` on stale attempts | No: the write either commits or does not. |
| Account lease / apply (`argus.ts` `ensureAccount`) | lease result | apply half-done | `account_unavailable` (no attempt) | Partly: a repeated apply is not known to be harmless. Note it, do not add a state yet. |

**Contradiction to resolve (the only one found):** `task-steering.spec.md` §3.4 says a steer stays in
`steers` until acknowledged, so a crashed injection is retried. The draft's item 3 says a steer dispatched
just before a crash becomes `unknown` and is not sent again. Both can hold only if `unknown` is a new
steer state set when the session dies after `onInbound` but before ack, with no re-delivery. The ack-after-
injection rule itself is sound. Its weak point is the window between `onInbound` resolving and the agent
acting on the text.

**Other gap:** the next attempt is never told that an unknown steer may have happened. That fits the
draft's "the next attempt is told it may have happened". It needs a continuation field, which
`task-continuation` already has in shape (`gaps`).

## 4. Spec-update plan

Fold into [worker efficiency](../drafts/2026-10-24.worker-efficiency.draft.md) P4 if P4 lands first;
otherwise update the living specs directly:

1. `failure-classes.spec.md` §3.2: the `session` row becomes "requeue once after confirmed exit; a
   further automatic requeue needs progress since the last automatic resume, else fail with the cause".
   Add the progress definition and its event. Keep `stalled` and `timeout` on today's rule.
2. `task-steering.spec.md` §3.3–3.4: add state `unknown` (set when a session dies with a steer
   `pending`-after-injection, or on attempt end if the channel had injected it). Document that
   re-delivery within an attempt stops at `unknown`. Name the attempt-level flag the next attempt reads.
3. `worker-lifecycle.spec.md` §3.5: add a start-rate cap in the reconciler (e.g. at most
   `max(1, floor(logical_cpus / 2))` starts in flight) and a longer start deadline. Running instances
   are not capped.
4. `task-operations.draft.md` §2: link the audit table above as its evidence for the retry-key scope.
5. Verify the start path in upstream NanoClaw (container-runner / host-sweep) before any patch.

**Non-contradiction check:** the items above refine `failure-classes` §3.2 and `task-steering` §3.3–3.4 only;
they do not change the admission, environment, or task class rules. The one real conflict is steer
re-delivery (§3 above), which must be resolved in the steering spec.

## Verified / left open

**Verified:** the sequential claim loop; the startup gate's scope; the reconciler's lack of a start cap;
the `session` class's current action; steering's ack and expiry rules; the audit table above.

**Settled 2026-11-01 (review of attempt 2):**

- Start cap: shipped in the reconciler (`default_start_cap()` = `max(1, cpu_count // 2)`, #76).
  `apps/api/tests/test_fleet_start_cap.py::test_cap_limits_new_starts_per_pass` queues 5 instances
  against a cap of 2 and asserts all 5 reach `running`; the file passes (15 tests).
- NanoClaw concurrent start on restart: **external dependency, not answerable here.** `container-runner.ts`
  and the host sweep are not in this repo; the only checkout (pin `8fbacc91`) is built by `provision.sh`
  and was not audited. The reconciler cap covers Argus-started instances only. Open until someone reads
  that source.
- `comment-create` callers: no code in this repo calls it. The only callers are agents following the
  prompt text in `argus.ts` and `gitea-helper.spec.md`, which document `--idempotency-key K` but do not
  require it (`gitea-api.mjs` accepts the command without one). So the key is **not enforced**; a lost
  response with no key can duplicate a comment. Closing this needs a decision: require the key, or accept it.
- `argus-steer-unknown.e2e.test.ts`: run via `scripts/steer-unknown-e2e.sh` on 2026-11-01; 1 test passed
  (90 s). Steer went `pending` -> `unknown`, `steer_unknown` 1 on attempt 1, and attempt 2's prompt
  warned by count without the text.

**Left open:**

- Which event counts as "progress" for the resume rule.
- The exact start cap formula and deadline value (the draft's numbers are Cloudroom's, not measured here).
- Whether `comment-create` callers always pass an idempotency key.

## 5. Resolution (2026-11-01)

Implemented since this read; the draft is closed except for the upstream question.

- **Start rate and deadline:** [worker lifecycle](../specs/worker-lifecycle.spec.md) 3.5,
  in the reconciler as recommended in §1 (`max_starts_in_flight`, `START_TIMEOUT_S = 120`
  against `PROVIDER_OP_TIMEOUT_S = 30`). The values are still Cloudroom's, not measured.
- **One resume:** [failure classes](../specs/failure-classes.spec.md) 3.2. "Progress" is a
  `task.progress` event of the claimed attempt after the latest `task.auto_resumed`.
- **Steer `unknown`:** [task steering](../specs/task-steering.spec.md) 3.3, 3.4, 3.6; the
  contradiction in §3 is resolved there (re-delivery stops at `unknown`).
- **Audit outcome:** no other write gets an `unknown` state. PR create, keyed comment
  create, checkpoint write and the lease/claim/complete/fail writes are idempotent,
  atomic or fenced. Account apply is the only partial case and stays noted, not changed.
- **Still open:** NanoClaw upstream start path (source not in this repo); whether every
  `comment-create` caller passes `--idempotency-key` (the channel prompt offers it, it
  does not require it).
