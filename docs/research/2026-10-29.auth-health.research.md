# Auth health: investigation report

Status: report · 2026-10-29 · answers the open questions in
[auth health draft](../drafts/2026-10-29.auth-health.draft.md). No implementation.

Pinned Claude Code: **2.1.296** (`engines/smoke.sh:30` expects
`2.1.296 (Claude Code)`; the local binary at
`/pnpm/global/5/.pnpm/@anthropic-ai+claude-code@2.1.296/…/bin/claude.exe`
reports the same version).

## 1. Can the two timestamps be derived on read?

**`last_accepted_at`: yes, derivable. No migration.**

- `account_usage` (`db/migrations/0053_attempt_usage.sql:6-25`) has `account_id`,
  `at`, `measurement` (`measured | not_reported`), `output_tokens`, `role`,
  `engine`, `model`. Index `account_usage_account (account_id, at)` exists
  (`0053:41`).
- Spec: rows are kept forever and aggregated on read
  (`account-usage.spec.md` §3.1); a `measured` report needs at least one token or
  cost field, so a cost-only row can have `output_tokens` null (§3.2).
- Proposed rule: `MAX(at) WHERE account_id = ? AND measurement = 'measured' AND
  output_tokens > 0`. A `NULL` output never matches, and `not_reported` rows
  (placeholders, §3.10) never match.
- Caveats: `at` is the report time, not the request time (reports are posted at
  run end, §3.2, and drained up to 10 s after the task, §3.9), so it is accurate to
  about a run. A late report rewrites `at` in place (§3.10), so the value can move
  forward, never back.

**`last_rejected_at`: derivable from the existing `events` table. No migration.**

- Exhaustion writes an `account.exhausted` event whose data carries
  `reason_code` (`accounts/service.py`: `_reset_detail` ~L749-760, merged in
  `_mark_exhausted` ~L642-665).
- `reason_code` is `quota_exhausted | auth_expired` (`packages/core/src/argus_core/accounts.py:451`).
  Filtering on `auth_expired` keeps rate limits and quota out by construction.
- Rate-limit probe outcomes (`provider_rate_limited`, `probe_rate_limited`) live
  in `account_quota_probe`, not in events, so they never reach this query.
- Query shape: `MAX(at) FROM events WHERE subject_type='account' AND subject_id=?
  AND kind='account.exhausted' AND json_extract(data,'$.reason_code')='auth_expired'`.
  `events_subject (subject_type, subject_id, id)` (`0001_events.sql:13`) narrows
  it; the JSON filter is a scan within one account's events.
- Caveat: no pruning of `events` was found in `apps/api/src` (grep for DELETE and
  retention returned nothing), so the history is probably kept. Not verified against
  a real database.
- Caveat: `account.exhausted` also changes `state`. A rejection therefore exhausts
  the account until a cooldown. If the decision is that a rejection should not
  exhaust, it needs its own event kind (see §3, recommendation).

**Migration decision.** None is needed for either timestamp. A migration is needed
only for **credential expiry** (see §4), and only if read-time expiry must avoid
decrypting the secret.

## 2. Claude Code's authentication-failure signal in stream JSON

**Verified present in the pinned 2.1.296 binary; not in the shipped typings;
not observed live.**

- The SDK output message of type `assistant` has an optional `error` field. Its
  enum, read from the 2.1.296 binary's message schema (`claude.exe`, the schema
  `rr = …type:"assistant", …, error: Zn().optional()`), is:
  `authentication_failed, oauth_org_not_allowed, account_on_hold,
  verification_required, billing_error, rate_limit, overloaded, invalid_request,
  model_not_found, server_error, unknown, max_output_tokens, cloud_credential_error`.
- `result` messages carry `api_error_status` (an integer HTTP status) and the
  transcript form carries `isApiErrorMessage`. Both were found in the binary.
- `sdk-tools.d.ts` (2.1.296, shipped with the package) does **not** define
  `SDKAssistantMessage` or this enum. So the field is in the binary's schema but
  not in the public typings. Its stability as a contract is therefore not
  documented.
- **Precedent in production code:** `integrations/nanoclaw/patch-claude-rate-limit.py:144-147`
  already reads `(message as { error?: string }).error === 'rate_limit'` on the
  assistant message. The same field is consumed today for quota, so
  `authentication_failed` sits on a path Argus already relies on.
- **Not verified:** that an expired or revoked login actually emits
  `authentication_failed` in `-p` stream mode. The binary contains user-facing
  strings for this (`Login expired`, `OAuth token revoked`, `Failed to
  authenticate`) and an `invalid_credential_header` branch that yields
  `authentication_failed`, but no live run was done. A live check needs a forced
  failure on a disposable credential. That is a credentialed run, outside this
  task.
- The existing channel handles only `rate_limit` for Claude
  (`argus-accounts.ts` `classifyProviderFailure`, the `claude` branch). Nothing maps
  `authentication_failed` today.

**Answer:** the stable candidate is `assistant.error === "authentication_failed"`.
It is confirmed in the pinned binary's schema and reuses an existing hook point.
Live emission is open.

## 3. Mapping `last_rejected_at` to Codex and Claude

**Codex: confirmed.** The `auth_expired` path runs end to end:

1. NanoClaw failure notice with `content.providerFailure = {provider:"codex", kind:"auth_expired"}`
   (`integrations/nanoclaw/argus-accounts.ts:1046-1052`) → exhausted with the fixed
   reason `OpenAI/Codex authentication expired`, `code: auth_expired`.
2. Text fallback: `AUTH_EXPIRED_PATTERN` (`argus-accounts.ts:879-884`, providers
   `openai` and `custom`), mirrored in `packages/core/src/argus_core/quota.py:52-57`.
3. Stored as `account.exhausted` with `reason_code: auth_expired`
   (`apps/api/tests/test_codex_failover.py:126`, `:138`).
4. **Ran:** `uv run --frozen --all-groups python -m pytest apps/api/tests/test_codex_failover.py`
   → 14 passed, including the expired-login case (`401 … token_expired` →
   `reason_code == "auth_expired"`).

**Claude equivalent:** `assistant.error === "authentication_failed"` (§2). Only
that value counts. `oauth_org_not_allowed` and `account_on_hold` are
account-level, not credential-level, and are kept out of `last_rejected_at`.
`billing_error` and `rate_limit` are excluded.

Rate limits and quota notices stay out of both fields: Codex by the
`reason_code` filter, Claude because `rate_limit` is not in the rejection set.

**Recommendation.** Record rejections as their own event kind,
`account.auth_rejected`, written by both paths. Do not reuse
`account.exhausted`. Reuse would make a rejection exhaust the account, which the
draft does not want (automatic disabling is out of scope), and it would keep
Claude and Codex on different event shapes. Codex would emit the new event in
addition to its exhaustion for now, so existing behaviour does not change. The
Claude side needs: a runner hook analogous to the `rate_limit` one
(`patch-claude-rate-limit.py`), and a `classifyProviderFailure` branch for
`{provider:"claude", kind:"auth_expired"}` against an `anthropic` account.
`ProviderFailureKind` already includes `auth_expired` in the patch's type.

## 4. Credential state (present / missing / expired)

- **Missing:** stored. A registry account whose secret is absent is `disabled`
  with `disabled_reason = "secret not found: …"` and `auto_disabled = 1`
  (`accounts/service.py:102-118`), reconciled against the secret store. Reading
  this needs no new data.
- **Expired:** **not stored.** Claude's `expiresAt` lives inside the secret
  document (`packages/core/src/argus_core/claude_auth.py:103-109`). The
  quota probe reads it only when it runs (`quota_probe.py:343-348`, skipped as
  `credential_expired`). Codex's expiry is a JWT claim, read the same way
  (`codex_auth.py:27`). No `accounts` column holds it (`0010_accounts.sql`).
- So "expired from stored data" needs either:
  - (a) a new column, e.g. `accounts.credential_expires_at`, written at create,
    renew and credential update, from `access_expires_at` (already computed there).
    This is a migration. The value goes stale when the holder refreshes the token
    on a worker, so it must be labelled "as stored at <time>".
  - (b) reading the secret on the read path. Rejected: it adds a store read to a
    read model and widens credential exposure.
- `setup-token` credentials (kind `subscription`, `oauth_token`) carry no
  `expiresAt`. Their state is "present, expiry unknown", never "healthy".

**Design (for the spec update):**

| Fact | Source | Shown as |
|---|---|---|
| present / missing | registry `state`/`disabled_reason` | present, or missing |
| expired | `credential_expires_at` (if the migration is taken) | expired, with the stored time |
| unknown expiry | `oauth_token` kind | "present, expiry unknown" |
| last accepted | `MAX(account_usage.at)`, measured, output > 0 | timestamp, or "never" |
| last rejected | `MAX(events.at)` for `account.auth_rejected` (see §3) | timestamp, or "none" |

Credential state is never rendered as healthy. The only positive state is
"present"; a non-expired `expiresAt` still reads "present, valid until …"
because validity is not proven.

**Home attention line.** Flag an account when `last_rejected_at` is set and
(`last_accepted_at` is null or `last_rejected_at > last_accepted_at`). Compute it
in the account read model, not in the dashboard, so the dashboard keeps talking
only to the API. `apps/dashboard/src/overview.ts` `attention()` already takes
`overview.accounts.by_provider` (`overview.ts:132`), so the flag is an added input
there.

## 5. Spec-update plan

1. `account-usage.spec.md` §3.5 read model: add `last_accepted_at` (derived as in
   §1) and `last_rejected_at` (derived from `account.auth_rejected`). State that
   neither is a column and neither is ever shown as healthy.
2. `account-usage.spec.md` §3.3: state that no probe reads an auth state (unchanged).
3. `claude-accounts.spec.md` §3: add the Claude rejection signal
   (`assistant.error === "authentication_failed"`), the pinned version (2.1.296),
   and that live emission is unverified.
4. `codex-accounts.spec.md` "Structured auth-expiry signal": add that Codex
   rejections also write `account.auth_rejected`, in addition to exhaustion.
5. `account-selection.spec.md` §3.6 (channel): add the Claude `auth_expired` branch
   next to the existing `rate_limit` one.
6. Migration: only if credential expiry is wanted on read. It would be the next
   free number after the highest in `db/migrations/`. Not decided here.

## 6. Verified, left open

**Verified (by reading or running):**
- `last_accepted_at` derivable from `account_usage` (schema, index, measurement rules).
- `last_rejected_at` derivable from `events` (`account.exhausted` with `reason_code`).
- Codex `auth_expired` path, with 14 passing tests.
- Claude's `assistant.error` enum in the pinned 2.1.296 binary, and the
  `rate_limit` precedent in the NanoClaw patch.
- Local CLI version is 2.1.296, matching the pin.

**Open:**
- Live emission of `authentication_failed` for an expired or revoked login in `-p`
  stream mode. Needs a forced failure on a disposable credential (a credentialed
  run, not done).
- Whether `events` is retained indefinitely. No pruning was found in the code;
  not checked against a real database.
- Whether `assistant.error` is a documented SDK contract. It is absent from the
  shipped typings.
- The NanoClaw runner and channel source are not in this repo. The patch anchors
  (`patch-claude-rate-limit.py`) and the `argus-usage-relay.ts` behaviour were read
  here but not run against the upstream runner.
- Credential-expiry storage (§4): the migration decision is open.
- The events-based `last_rejected_at` query has not been benchmarked. The JSON
  filter scans one account's events.
