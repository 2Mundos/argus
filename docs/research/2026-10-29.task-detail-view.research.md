## Missing connections

### 1. Quiet / stall context drops at the task panel

**Verdict:** Inbox and the workers rail show stall semantics; the task detail payload and UI do not.

- DB columns `quiet_at`, `activity_at`, `observation`, `observation_at` (migrations cited in
  [stall-visibility](../specs/stall-visibility.spec.md)); inbox quiet rows
  (`inbox.py:103-108`, enrichment `:206-227`).
- `InboxItem` carries `last_signal_at`, `last_signal_source`, `stall_cause` (`inbox.py:58-62`);
  quiet card copy (`Inbox.tsx:262-312`, `STALL_CAUSE_COPY` `:263-268`).
- Core `Task` / `TaskSummary` expose progress and `output_at` but **no** `quiet_at` or
  `stall_cause` (`tasks.py:463-522`, `views.py:39-65`). `stall_cause()` is derived in
  `service.py:2178-2203` for inbox only.
- Workers rail: `quiet_since` on agents (`agents.py:64-65`, `WorkersSidebar.tsx:33-36`).
- Task panel: only `Activity` + `NoSignal` (10 min), not the 20 min `quiet_at` flag
  (`QUIET_CLAIM_S = 1200` in `service.py:2172`) or host observation.

**Operator cost:** Opening a quiet task from Tasks loses stall cause and last-signal lines that
Inbox already showed.

### 2. `block_reason` not rendered in task detail

**Verdict:** The field is on the task model and returned by `GET /api/tasks/{id}`; the detail UI
ignores it.

- Card: `Tasks.tsx:147-149`; Inbox blocked card with `BLOCK_COPY` (`Inbox.tsx:218-250`).
- `TaskDetail.tsx`: Unblock when `state === "blocked"` (`:264-268`) but no `block_reason` (grep:
  no matches in file). Field defined on `Task` (`tasks.py:487`).

**Operator cost:** Unblock is offered with no explanation of why the task blocked.

### 3. No shared attempt navigation

**Verdict:** Detail is pinned to `task.attempt`; history API exists but is unused.

- `TaskChanges` alone can select up to three attempts (`TaskChanges.tsx:93-105`).
- `TaskLog` title shows current attempt only (`TaskLog.tsx:163`); no selector.
- `task_attempts` holds `claimed_at`, `agent_id`, `definition`, `outcome` (`task_edit.py:92-101`);
  endpoint `routes.py:549-555`; dashboard never calls it.

**Operator cost:** Cannot see when attempts ran, who held them, or how they ended from the task
panel.

### 4. Task cost (spec-only)

**Verdict:** [task-cost](../specs/task-cost.spec.md) describes `GET .../cost`, `task.cost`, and
dashboard tiles; **none** implemented — no `/cost` route under `tasks/`, no `budget_usd` in
shipped migrations through `0053_attempt_usage.sql`, Cost tab is account/project only
(`task-cost.spec.md` 3.2). Usage rows already carry `task_id` and `attempt` (spec 3.1).

**Operator cost:** Spend and budget invisible while investigating a task (out of scope for a
detail-view patch until the cost spec ships).

### 5. Artifacts, models, history not tied to selected attempt

**Verdict:** All attempts mixed in one view.

- Artifacts: flat list, label only (`TaskDetail.tsx:341-361`).
- Models: grouped by attempt number but no “current” marker (`:108-164`).
- History: newest 50 events for the task, no attempt column (`TaskDetail.tsx:42-47`, `:363-364`).

**Operator cost:** Long tasks make it unclear which attempt produced an artifact or event.

### 6. History truncates silently

**Verdict:** Fixed `limit: 50` with no footer; unlike Tasks list copy (`Tasks.tsx:79-82`).

- `EventList` renders the array as-is; REST list does not attach a total count in this call
  (`eventlog/routes.py:47-69`).

**Operator cost:** Early events of a busy task vanish with no indication.

### 7. Steering only from Live (and Inbox quiet card)

**Verdict:** Spec ties Steer to the live-log term bar; inbox duplicates it for quiet rows.

- Steer button in `TaskLog` term bar (`TaskLog.tsx:186-195`); `TaskSteers` loads assignee
  features (`TaskSteers.tsx:33-56`).
- Inbox quiet card (`Inbox.tsx:316-333`).
- No steer when `attempt === 0` (no `TaskLog`, `TaskDetail.tsx:321`) or when the operator
  never scrolls to Live.

**Operator cost:** Steering requires finding the terminal panel, not the task header/actions.

## Task update filtering

**One global stream.** `GET /api/events/stream` accepts only `Last-Event-ID`
(`eventlog/routes.py:214-238`). Managers receive all events; the dashboard fans out in memory
(`live.tsx:51-57`). Per-task filtering is client-side (`TaskLog.tsx:94-96`, `taskChanges.ts:12-18`).

**Transient replay.** `task.log`, `task.changes`, (spec) `task.cost` use `id: 0`; SSE omits
`id:` (`events.py:114-126`), so they never advance `Last-Event-ID`. Correct recovery: REST
backfill after reconnect or `seq` gap (`TaskLog.tsx:59-92`, `:136-141`; `TaskChanges.tsx:68`).

**`seq`.** Per task across attempts, never reused ([task-live-log](../specs/task-live-log.spec.md)
3.3; `GET .../log` `routes.py:420-434`); gap detection spans attempt boundaries
(`TaskLog.tsx:101-105`).

**Volume (spec bounds).** At most one log batch per second per source per task, up to 200 lines
([task-live-log](../specs/task-live-log.spec.md) 3.1); changes PUT rate-limited to one per 5 s
([task-changes](../specs/task-changes.spec.md) 3.3). With *N* dashboards, each subscriber still
receives every task's events today.

**Server-side filter.** Filtering in `event_stream`'s loop (`eventlog/routes.py:301-316`) would
drop non-matching events after the bus fan-out — mainly a bandwidth win, not less publish work.
Reconnect headers carry only integer `Last-Event-ID`, not `subject_id`; transient events still
need REST catch-up regardless.

**Bounded recommendation:** Keep **one unfiltered stream**; per-task panels already reconnect-safe
via `connection` + REST. A second `GET /api/tasks/{id}/stream` would duplicate replay,
keepalive, and overflow handling (`eventlog/routes.py:242-316`) and add a connection per open
panel — defer unless measured pain justifies it.

## Mobile width and stream traffic

**Layout.** Shell goes single-column at `max-width: 1100px` (`styles.css:1859-1883`). Panel
bodies stack; `.table-wrap` scrolls horizontally (`:1855-1857`).

**Terminal panels.** `.term-body` `max-height: 60vh` (`:2292-2298`); `.task-log` caps log at
`18rem` (`:2775-2777`). Worker panel overrides exist; task panel does not.

**Facts grid.** `.facts` is two-column with no narrow rule (`:1222-1233`); only
`.worker-panel-meta .facts` adjusts at 900px (`:768-772`).

**Term bar.** Single flex row, no wrap (`:2143-2152`): title, filter, pulse, Pause, Steer — first
likely overflow at ~390px width (inference from fixed controls; not browser-tested here).

**Stream traffic.** Spec-limited write rates bound per-task event volume; unfiltered fan-out
scales with open dashboards × fleet activity, unchanged by detail-view layout work.
