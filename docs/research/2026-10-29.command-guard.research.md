## 2. Q1: where Claude Code registration lives

- **Nothing in this repo writes a Claude Code `settings.json`.** Grep for
  `settings.json`, `managed-settings`, `.claude`, `PreToolUse` across `integrations/`,
  `deploy/`, `scripts/`, `apps/`, `packages/` finds only: a credentials path read by
  `engines/argus-delegate.mjs:140`, the login sandbox dirs and `CLAUDE_CONFIG_DIR` in
  `apps/api/src/argus_api/accounts/claude_login.py:286,342`, and NanoClaw skill dirs in
  `install-engines.sh:14`. The Claude "account settings" in `engines/account-settings.mjs:1`
  are lease settings for custom accounts (`base_url`, `model`), not Claude Code config.
- **Claude Code is not installed by Argus.** `install-engines.sh:41-47` says
  "claude-code stays as the checkout pins it" (NanoClaw's `container/cli-tools.json`).
  Argus pins only `@openai/codex` and `opencode-ai`.
- **Consequence:** there is no existing account/user settings writer to extend. Options are
  (a) a file baked into the image, (b) a new writer. The repo's only image-level
  extension points are the Dockerfile patcher `engines/patch-engines-dockerfile.py` and
  `install-engines.sh`, which copy files into `container/` (`install-engines.sh:67-69`).
- **Precedence (external, not verified in repo):** Claude Code documents managed settings
  (Linux: `/etc/claude-code/managed-settings.json`) as the highest-precedence scope, not
  overridable by user or project `.claude/settings*.json`. Hooks from all scopes merge,
  and a managed setting can restrict hook sources. A project's own `.claude` therefore
  cannot remove a managed hook. Settle with: install a probe hook in managed settings in a
  disposable image and run `claude` with a project `.claude/settings.json` that disables hooks.
- **Fit:** managed settings in the image matches the draft's intent. Per-project opt-out
  (section 7) must then be an env/flag the hook reads, not a settings-file edit.

## 4. Q3: does a block count toward a failure class?

- **Recommendation: informational only.** `failure-classes.spec.md:35-49` maps *failure
  reasons* to classes; a failed or blocked attempt gets one. A blocked command is not an
  attempt outcome: the draft says the task continues (`draft:35-36`). Mapping it would
  spend attempts (`failure-classes.spec.md:53-59`) for no failure.
- **An informational event type exists:** `task.quiet` (`stall-visibility.spec.md:63`;
  emitted at `apps/api/src/argus_api/tasks/service.py:2377`) and `task.progress`
  (`live-work.spec.md:20`). Neither changes class or attempts. The reason string is not in
  `FAILURE_CLASS`, and an unknown reason defaults to `task` (`failure-classes.spec.md:48`),
  so a block must never be sent as a fail reason.
- **If wanted later:** repeated blocks could feed the existing stall/quiet signals; do not
  add a class for them now.

## 5. Q4: fail open vs missing guard blocks startup

Existing patterns support the draft's split:
- **Missing prerequisite blocks, fail-closed:** an unrealizable sandbox profile is refused and
  nothing is created (`codex-sandbox-profile.spec.md:93-96,126-131`); the adoption gate
  stops the claim loop until adoption succeeds (`failure-classes.spec.md:144-152`); a probe
  that cannot run is an `environment` block, not a pass (`failure-classes.spec.md:233-234`);
  the repo preflight fails closed without `probeRepository` (`:180-181`). The patcher
  asserts "upstream shape changed" rather than patch blindly
  (`patch-codex-sandbox.py:29`).
- **Runtime fault stays soft:** "best-effort" probes and relays never change the exit code
  (`engines.spec.md:127-131`; `failure-classes.spec.md:233`).
- **Mapping:** missing guard binary or unregistered hook at session start is an
  `env_*` block reason (new, e.g. `env_guard_missing`, a `failure-classes` 3.3 row), not a
  silent unguarded run. A parse/runtime error inside the guard allows the command and is
  logged. Caveat: a block at start needs the opt-out check first, so a project with the
  guard off is never blocked for a missing guard.

## 6. Q5: `task.command_blocked` event

- **Naming:** dotted `task.<snake_case>` kinds (`task.quiet`, `task.progress`, `task.log`,
  `task.changes`); `task.command_blocked` fits.
- **No central kind registry found:** `grep` for `EVENT_KINDS`/kind enums in
  `apps/` and `packages/` finds none. Kinds are strings emitted at call sites
  (`tasks/service.py:2377`); the inbox uses a literal tuple (`eventlog/routes.py:158`,
  `_INBOX_KINDS`), which a block must **not** join. The dashboard formats kinds in
  `apps/dashboard/src/eventLine.ts`, so a line formatter is a likely (small) change;
  unknown-kind fallback behavior is unverified.
- **Worker path is missing.** The event log has only GET routes
  (`eventlog/routes.py:40,87,214`). Workers reach task state through `POST .../progress`
  (`tasks/routes.py:315`) and the log batch route. A new worker-authenticated route (or
  reuse of progress) is required, and it must be a worker-scope route limited to leased tasks.
- **Redaction/truncation:** reuse the live-log rules: `argus_core.redact.redact` runs before
  storage (`task-live-log.spec.md:57-60`); lines are cut at 2000 characters after redaction
  with `…` (`:40`); cleaning removes escapes and control characters first (`:46-55`).
  Event data proposal: `{task_id, attempt, rule, command}` with the command redacted,
  cleaned, cut to a smaller bound (spec decision), and the `rule` a closed token.
- **Persistent vs transient:** `task.log` is transient (`:91-98`); the draft wants Fleet
  counts, so `task.command_blocked` must be persistent (written via `Database.write()`, time
  from `tx.now`; `AGENTS.md` rules). Rate-limit it, since a looping agent could flood events.

## 7. Q6: per-project opt-out

- **Mechanism:** registry key per `settings.spec.md:35-39`; adding a key is "a code change
  and a spec change" (`:40`). Project overrides resolve project, global, default (`:46`).
- **Shape fit:** existing keys are objects (`review.independent` is
  `{"mode": ..., "max_rounds": ...}`, `:93-99`); `routines.enabled` is named as a boolean-style
  key (`:144`). A default-on boolean (`command_guard.enabled`, scopes `global` and `project`,
  default `true`) fits both. An object (`{"enabled": true}`) leaves room for rule opt-outs
  but is not needed now (negentropy).
- **Delivery gap:** "new attempts" read the effective value at claim time, as the model
  policy does (`settings.spec.md:82-85`). The hook runs in the container, so the channel
  must pass it as env/mount at session start; this is the same seam as the
  `ARGUS_CODEX_SANDBOX_PROFILE` pool env (`codex-sandbox-profile.spec.md:66-74`), which is
  host-wide, not per project. A running session cannot change its value.

## 8. Q7: shared single-source rule set

- **Where:** one dependency-free ES module in `integrations/nanoclaw/engines/`, next to the
  other files copied into the image (`install-engines.sh:67`; e.g. `livelog.mjs`,
  `milestones.mjs`), for example `command-guard-rules.mjs`. Both the hook entry and its
  test import it; the test file follows the `*.test.mjs` pattern already there
  (`argus-delegate.test.mjs`, `livelog.test.mjs`). The Python suite (`apps/api`) should
  not duplicate the patterns; if it needs them, read a JSON export of the table.
- **Packaging:** the file must be in the `COPY` list that `patch-engines-dockerfile.py`
  writes, and in the staged tools-layer context, or the hook cannot import it
  (`engines.spec.md:215-218`).
- **Test shape per rule:** a table `{id, reason, block: [..], allow: [..]}`; the test asserts
  each `block` entry returns that id and each `allow` entry returns null. Examples: block
  `rm -rf ~`, `rm -rf "$HOME"`, `rm -rf /home/*`, `rm -rf --no-preserve-root /`; allow
  `rm -rf ./build`, `rm -rf /tmp/x`. Include shell forms (`sudo`, `bash -c '…'`, chained `;`/`&&`).
  Plus one test that every rule has at least one of each, so a new rule cannot ship without both.

## 9. Q8: Cursor limitation (stated)

**Cursor (the `agent` executor, delegated through `argus-delegate`) runs no native hooks,
so the guard cannot cover it.** `engines.spec.md:15,72-73` makes Cursor an executor only,
run by `argus-delegate` as a child process (`engines.spec.md:120-131`); the guard would
register on Claude Code and Codex only. The same holds for `opencode` and the `local`
executor. Claude Code and Codex invoked *as executors* by `argus-delegate` are covered only
if they pick up the managed settings and Codex hook config in the delegate's environment
(unverified). The spec must say this plainly and not imply coverage.

## 10. Q9: draft rule list

- **Confirmed (generic):** recursive delete of `/`, `~`, `$HOME`, `/home/*`, `/root`;
  `--no-preserve-root`; `mkfs`/`mke2fs`; `dd of=/dev/<disk>` and block-device redirects;
  fork bombs. None of these is present in the repo today; there is no command-level rule set.
- **`gh repo delete`:** `gh` is not an Argus tool (`AGENTS.md`, `gitea-helper.spec.md`).
  It may exist in the image and holds no token, but OneCLI injects credentials for HTTPS
  clients (onecli-gateway skill), so the rule stays valid as defence in depth.
- **`argus-gitea-api` repo deletion: refuted as a rule.** The helper has no repo-delete
  command: its help states "no merge, approve, admin, user, token, secret or
  repository-delete command" (`gitea-api.mjs:1897`), and a test asserts `repo-delete`,
  `merge`, `approve`, `request` are not commands (`gitea-api.test.mjs:1209`). The only
  delete it has is `comment-delete` (`gitea-api.mjs:1667`).
- **`argus-github-api`: refuted likewise.** It has the same CLI and command matrix as the
  Gitea helper (`github-repositories.spec.md:12,71-73`); `github-api.mjs` has no repo-delete
  (grep for `repo-delete` / `deleteRepo` finds none). Both helpers exist in the repo
  (`gitea-api.mjs`, `github-api.mjs`; installed by `install-gitea-api.sh`; probed in
  `.github/workflows/quality.yaml:235`).
- **Recommendation:** drop the two helper rules; replace with a regression test that neither
  helper exposes a repo-delete command (already covered by `gitea-api.test.mjs:1209`; add the
  github-api equivalent if missing). Keep `gh repo delete` and raw `curl -X DELETE` on
  `/repos/` as a possible rule only with a test showing a real risk (the draft's own bar).
- **Argus-specific:** deleting the task workspace root is the draft's example. Workspace paths
  are defined in `task-workspace.spec.md`; I did not verify a rule shape for them.

## 11. Recommendation

Proceed to a spec, scoped small:
1. One managed-settings hook for Claude Code (image-baked), one Codex hook once hook support in
   the pinned 0.162.1 is confirmed by a probe. If Codex 0.162.1 lacks it, either bump the pin
   (`install-engines.sh:19`, `smoke.sh:31`) or ship Claude-only and say so.
2. Shared rules module with paired block/allow tests; drop the helper-deletion rules.
3. Informational, persistent `task.command_blocked`; no failure class; not in the inbox.
4. `command_guard.enabled` setting, default on, passed to the hook as env at claim.
5. Fail open inside the guard; missing guard when enabled is an `env_*` block.
6. State the Cursor/opencode/local limit in the spec.
