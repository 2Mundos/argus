**Consequences if sessions have no quota (the likely case):**

| Item | Effect |
| --- | --- |
| 2. CPU shim | Values must come from the session quota, not the host. No-op without one. |
| 1. OOM priority | Still useful, but victim choice is host-global without a container memory limit. |
| 3. Classification | `OOMKilled` / `memory.events` report only container-cgroup OOMs. Host-wide kills cannot be classified `env_oom`. |

Recommendation: add a session quota first (plumb pool cpus/memory into the
NanoClaw session spec via a patch to `composeSessionSpec`/`container-runner`, or a
documented env), then build items 1-3 on it.

## 3. Q2: `oom_score_adj`, CPU shim placement, override rule

### 3.1 `oom_score_adj` under the cap/AppArmor profile

- Worker state: uid 1000, `CapEff=0000000000000000`, `CapBnd=0`, `NoNewPrivs=1`,
  AppArmor `docker-default (enforce)`. VERIFIED
- `/proc/self/oom_score_adj` 0 -> 500 succeeded. A process at 500 then wrote 0 and
  400: both succeeded (no floor was set). Writing 1001 was rejected (I/O error).
  VERIFIED
- Kernel rule (proc(5), `fs/proc/base.c` `oom_score_adj_write`): unprivileged
  processes may raise their own value; going below the `oom_score_adj_min` floor,
  or negative, needs `CAP_SYS_RESOURCE`, which also sets the floor. UNVERIFIED;
  the floor logic was not checked against the running kernel source.
- AppArmor candidate `integrations/nanoclaw/security/argus-codex-worker.apparmor`
  is not loaded here (`:1`). It has no `oom` or `sys_resource` rule. It denies
  writes only to non-pid `/proc/*` files and `/proc/sys` except `kernel/shm*`
  (`:49-53`); `capability,` is allowed (`:35`). So `/proc/<pid>/oom_score_adj`
  is not denied by the profile text. SOURCE; runtime effect UNVERIFIED.
- Codex path drops all caps (`argus-codex-sandbox.ts:214`) and refuses any cap-add
  (`:315`). SOURCE

**Design rule:** shims only raise `oom_score_adj` (to 500), never lower it. Raising
needs no capability. Answer to the draft's question: no, `CAP_SYS_RESOURCE` is not
needed to raise the score.

### 3.2 CPU-count shim

Nothing in the repo sets `BASH_ENV`, `CLAUDE_ENV_FILE`, `OMP_NUM_THREADS`,
`PYTHON_CPU_COUNT`, `NODE_OPTIONS` or a `sitecustomize` (repo-wide grep: only the
draft mentions them). The shim is entirely new. SOURCE

| Runtime | Observation |
| --- | --- |
| coreutils `nproc` | `OMP_NUM_THREADS=2` -> 2; `OMP_THREAD_LIMIT=3` -> 3. VERIFIED |
| Node 22 | `NODE_OPTIONS` does not change `os.cpus().length` (stays 24); a preload module that patches `os.cpus` is required. VERIFIED |
| Python 3.11.2 | `PYTHON_CPU_COUNT=2` leaves `os.cpu_count()` at 24; `python3 -S` also 24. VERIFIED |
| Python 3.13+ | `PYTHON_CPU_COUNT` is honoured. UNVERIFIED (no 3.13 interpreter here) |
| `sitecustomize` | Loads only if `site` is imported and the dir is on `sys.path`; `-S`, `-I`, `PYTHONNOUSERSITE`-style launches skip it (known gap). UNVERIFIED for the `-I` variants, VERIFIED for `-S` effect on the env var only |

Delivery of the env:

- `BASH_ENV` is read only by non-interactive bash; a missing file is ignored
  silently (`BASH_ENV=/nonexistent bash -c 'echo ok'` prints `ok`). VERIFIED
- Whether Claude Code sources `CLAUDE_ENV_FILE`, and how Codex starts its command
  shells, was not observed (no Claude or Codex run). UNVERIFIED

**Placement:** helpers in the agent image tools layer, as the draft says
(`2026-10-29.agent-resource-hygiene.draft.md:40`), values from the session quota.

**Project-override-wins rule:** the shim sets a variable only when unset or empty
(`: "${OMP_NUM_THREADS:=N}"` semantics). Caveat: a project that sets
`NODE_OPTIONS` **replaces** the value rather than merging, so a Node preload
delivered only through `NODE_OPTIONS` is silently lost. The shim must append on
load and log when it finds `NODE_OPTIONS` already set without the preload. Python
`sitecustomize` skipped by `-S`/`-I` is a documented gap.

## 4. Q3: reliable OOM-kill detection and `env_oom`

Detection:

- Docker `.State.OOMKilled`. UNVERIFIED (no docker CLI). Expected caveat: it
  reflects the container-cgroup OOM event and is most reliable when PID 1 dies; a
  non-init process killed while the container keeps running may not set it. Test
  in a disposable container with `--memory 512m`.
- In-container cgroup v2 `/sys/fs/cgroup/memory.events` exists and is readable
  (fields `low high max oom oom_kill oom_group_kill`, all 0). VERIFIED. Counter
  increment on a real kill: UNVERIFIED (needs a limited cgroup).

Recommended design:

1. The runner reads `memory.events` `oom_kill` before a command and after it exits;
   a delta > 0 marks that command OOM-killed.
2. Container exit code 137 plus `OOMKilled=true` marks the session.
3. Only container-cgroup kills count, so no memory limit means no `env_oom`
   signal (see section 2).

Classification:

- `env_oom` is not a pre-attempt block reason. `failure-classes.spec.md` 3.2 says
  `environment` blocks with no attempt spent; an OOM happens after the attempt
  started. SOURCE (`docs/specs/failure-classes.spec.md:35-51`)
- `env_oom` is in no reason set today: not in `ENV_BLOCK_REASONS`
  (`packages/core/src/argus_core/tasks.py:250-269`); only the draft and
  `docs/README.md:173` use the name. SOURCE
- A reason absent from `FAILURE_CLASS` (`tasks.py:273-285`) is `task`
  (`tasks.py:288-289`; spec table note `failure-classes.spec.md:48`), so a bare
  `env_oom` would retry as `task`. Fleet's `classify_failure` maps unknown system
  reasons to `other` (`apps/api/src/argus_api/fleet_health.py:280-281`). SOURCE
- **Recommendation (open choice for the orchestrator):** record an `oom_kill` fact
  on the failure row and classify the attempt as `session`. Promote to a blocking
  `env_oom` (class `environment`, added to `ENV_BLOCK_REASONS`) only after 2
  consecutive OOM-killed sessions on the same pool.
