Read-only investigation of [the quota-resume draft](../drafts/2026-10-29.quota-resume.draft.md).
No code was run and no live container, OneCLI vault or provider account was touched.
Findings are from reading this repository at `origin/main`. The NanoClaw agent runner
and the Claude Code / Codex CLIs are not in this checkout, so every claim about them is
marked as open.

## Q1. Credential swap: in place or container recreate

What the code does today:

- **Rotation is a recreate, by design.** `argus.ts` `recycleRuntime` (line 3613) calls
  `stopGroupSessions` (3625), which kills every running session container of the group and
  waits for exit (`stopSessions`, 3635, rejects after `RECYCLE_TIMEOUT_MS` = 30 s). The
  comment at 2216-2218 says the old container "holds the previous account's stubs: it must
  be gone before the new account is written". Rotation paths call it at 2218, 2386, 2927-2935,
  3030-3037 and 3863 (image change).
- **The stubs are spawn-time inputs.** `account-selection.spec.md` 112-128 describes the
  Claude gateway stub (`/home/node/.config/argus/claude-gateway.json`, read-only, written by
  the host). `codex-accounts.spec.md` 85-95 says the next container "is built with the stubs
  (credential, workspace id) of the account now held". `argus-codex-stub.ts` 1-10 explains the
  Codex stub's `chatgpt_account_id` must match the real workspace, and `withMirroredCodexAccount`
  (56) rewrites it. So a credential-identity change must be made through the stub, and the
  running container never re-reads it.
- **The OneCLI secret itself can change in place.** `applyLeasesDetailed`
  (`argus-accounts.ts` 677-707) writes the agent's secrets through the OneCLI API. Whether
  the proxy picks up a changed secret for a running container without restart is **not
  verified**: the repo has no test or log for it, and the repo's own rotation never relies on it.
- **Session files survive a recreate.** `stopSessions` only kills containers
  (`killContainer`). It does not change the DB session row. The row is closed only by
  `closeSessionFromEnv` (4001-4014: `status: "closed"`), which runs in `closeAttemptSession`
  (2066-2080) after every attempt (`finally`, 3063). The session folder is host state, so a
  new container for the same session id mounts the same files. That mount behaviour is
  NanoClaw's and not read here.

Conclusion for Q1: a mid-session swap is **not** done in place today. The designed behaviour is
"stop the container, apply the new account, resend the task". For a resumed native
conversation this means the session files must survive the stop and the runner must start the
new container on the same native session id. Both are plausible but unverified (the runner
source is outside this repo).

Note on the draft: it describes Cloudroom as "restarts only the harness" and the proposal says
"touches only sessions stopped by quota". This repo already stops all group containers on any
rotation, including within one provider. The draft's "in place" framing does not match what
Argus does now.

## Q2. Session validity after a pause

- **Context.** Transcripts show 33 compactions over the work so far
  (`2026-10-24.worker-efficiency.draft.md` 96). A resumed session is therefore bounded by the
  provider's compaction, not by a hard limit. Compaction can drop detail the resumed model
  would need, so a resume is a "continue", not a guaranteed restore.
- **Retention.** Nothing in this repo states how long Claude Code or Codex keep a session
  transcript or thread on the local disk or server side. Left open. Vendor docs or a
  disposable test would settle it.
- **No cutoff exists today.** `patch-no-session-ceiling.py` removes NanoClaw's age ceiling
  for running sessions ("a long-lived or idle session is valid and is never killed for its
  age alone"). Only stale message claims are reclaimed.
- **Recommendation (proposal).** Resume only when the pause is short and the native session
  is intact. Start fresh (with the checkpoint, as today) when any of these hold: the paused
  session is older than a fixed cutoff (a starting value of 24 h is a guess to be tuned), the
  transcript cannot be read, or the session id is absent. The cutoff value is a decision for the
  spec, not something this report can prove.

## Q3. Codex: resume a thread under a different ChatGPT account

- The Codex stub rewrites `chatgpt_account_id` to the workspace of the account held
  (`argus-codex-stub.ts` 1-10, 56-66). Codex checks that id against the workspaces listed for
  the real token. A thread created under one workspace and resumed under another is not
  covered by any test or spec in this repo.
- Codex keeps thread state under `CODEX_HOME` (`codex-accounts.spec.md` 53, a private home per
  login). Whether the thread store is tied to the account that created it is **not verified**.
- **Open.** Answering needs a spike: create a thread under account A, rotate the stub to
  account B, resume the thread id, and record the result. Only a real ChatGPT workspace pair
  settles it. Until then the Codex case must fall back to a fresh thread with the checkpoint.

## Narrow slice vs worker-efficiency P4

P4 (`2026-10-24.worker-efficiency.draft.md` 191-206) is "interruptions keep the work". It is
still a draft, with no `worker-efficiency.spec.md` in `docs/specs/`. The draft's own status
says P4 is "partial" and "session-transcript resume ... unproven".

Quota-only slice (belongs in this work):

- Record the native session id, node and engine with a quota-paused attempt.
- On re-claim on the same node and engine, resume that session under the new account and send
  one framed operator message (the framing of `task-steering.spec.md`).
- Fallback to today's fresh session plus checkpoint when the session is missing, unreadable, or
  past the cutoff. Never report a resume that did not happen.
- Keep attempt counting and failure classes unchanged (`quota_exhausted` rotates, no attempt
  spent).

Stays in P4:

- Resume across nodes or engines.
- Resume after `session_lost`, crash or stall.
- Mid-task account switch as a general mechanism (P4 bullet 4).
- Transcript storage, retention and cleanup policy.

## Spec-update plan (fold into P4)

Specs that currently say the opposite must be amended before any code:

1. `docs/specs/task-checkpoint.spec.md` 28-31: "No resume of the engine's session transcript".
   Scope the sentence to non-quota exits and point to P4.
2. `docs/specs/account-selection.spec.md` 55-62 and 220-225: state that a quota rotation keeps the
   native session id and does not close the attempt session, and that stopping the container
   (the rotation's recreate) is the documented swap.
3. `docs/specs/worker-lifecycle.spec.md` (one session per attempt, `closeAttemptSession`): add the
   exception for a quota pause, with the cutoff.
4. `docs/drafts/2026-10-24.worker-efficiency.draft.md` P4: add this slice as a sub-section, with
   the Q1-Q3 answers and the "fresh session on any doubt" rule.
5. Then the quota-resume draft is superseded by the P4 sub-section and marked so in
   `docs/README.md`.

Order: P4 spec first (no spec for P4 exists), then the amendments above, then the spike, then code.

## What was verified

- Rotation stops session containers before the new account is applied (code path above).
- The DB session row is closed only at attempt end (`closeAttemptSession`), not on rotation.
- The Codex stub carries the workspace id and is rebuilt per container.
- No age ceiling on running sessions in NanoClaw (patch header).

## What is not verified

Everything under "Open questions". In particular, no test in this repo exercises a resume, a
mid-session credential change, or a Codex thread under a second account.
