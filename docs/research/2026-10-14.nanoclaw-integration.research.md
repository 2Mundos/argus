# NanoClaw integration spike — Research

Read-only review of `qwibitai/nanoclaw` at commit `8fbacc9` (2026-10-14), against
the open questions in [worker lifecycle 4.1](../specs/worker-lifecycle.spec.md).
Nothing was executed. Complete for the three questions; the prototypes it
recommends are not done.

## Q1. Can a module inject inbound messages without a chat platform? — Yes

- Channel adapters self-register (`registerChannelAdapter`, `src/channels/channel-registry.ts`)
  and push messages with `setup.onInbound(platformId, threadId, message)`
  (`src/channels/adapter.ts`). Replies come back through the adapter's `deliver()`.
- The built-in `cli` channel (`src/channels/cli.ts`) is exactly this pattern: zero
  credentials, no platform, routed like any chat. An `argus` channel can copy it:
  `onInbound` per claimed task, `deliver()` mapped to progress/complete.
- Agent groups, messaging groups, and wirings are created with internal DB helpers
  (`createAgentGroup`, `createMessagingGroup`, `createMessagingGroupAgent`), as
  `scripts/init-cli-agent.ts` does; an Argus module can do the same at `onHostStart`
  (`src/host-lifecycle.ts`).
- **Install model is source-level**: skills copy files into `src/` and append an
  import to a barrel (`src/channels/index.ts`, `src/modules/index.ts`). There is no
  runtime plugin loader, so Argus ships an image built `FROM` NanoClaw with its
  channel file added and one import appended (or an `/add-argus` skill).

## Q2. Can the credential be switched per session? — Per agent group, fragile

- Credentials are a gateway seam (`docs/gateway-seam.md`): `sessions.ensure(input)`
  returns a typed contribution (env, mounts, containers, labels, network intent).
  Credentials never go into the agent container.
- OneCLI (`/add-onecli`) keys identity on the **agent group** (`ensureAgent({identifier:
  agentGroupId})`) and grants secrets with `onecli agents set-secrets`. Since one
  Argus agent = one agent group, switching an account = reassigning that group's
  secret. The skill pins OneCLI **1.42.0**: 1.43+ removed the assignment API.
- **Verified live (2026-10-14, OneCLI gateway 1.42.0, CLI 2.2.5)**: reassigning a
  secret takes effect on the next request of an already-running process, with no
  restart. See [Credential switch test](#credential-switch-test).
- Iron Proxy uses principals/grants but needs PostgreSQL + a Rails console.
- Option to evaluate: an Argus gateway provider (credential-injecting proxy fed by
  Argus leases). Most control, most work.

## Q3. Does a host run on Kubernetes with DinD? — Not as shipped

How the Docker driver works (`src/drivers/docker-driver.ts`, `cli.ts`):

- It shells out to the **`docker` CLI** (`execFileSync`/`spawn` through one `Cli`
  seam; the binary name is configurable). It issues `network create --internal`,
  `create`, `start --attach`, and so on. The host image therefore needs the Docker
  CLI and a daemon to talk to.
- Mounts are `-v <hostPath>:<containerPath>[:ro]` with each `hostPath` checked by
  `fs.existsSync` **in the NanoClaw host process's own filesystem**. The same
  string is then resolved by the Docker daemon on *its* filesystem. So the two
  must agree: a NanoClaw host running in a container that drives the node's
  Docker (socket mount) needs its `data/`, `groups/`, and `store/` directories
  bind-mounted at the **identical absolute path** inside and outside; with
  Docker-in-Docker the daemon is the sidecar's, so the path must be shared
  between the host container and the sidecar (a shared volume mounted at the same
  path in both).
- Kubernetes has no driver. The driver seam is designed for more
  (`docs/gateway-seam.md`, `src/drivers/installed.ts`: out-of-tree drivers
  self-register by an appended import), but a Pod-per-session driver would have to
  be written; per-session internal networks and the gateway "network intent" have
  no direct equivalent.

Consequences for Argus:

- **Docker target** (the one that exists): run the NanoClaw host as an Argus
  instance with the node's Docker socket and its data dir mounted at an identical
  path, or use a remote/dedicated Docker host. The socket mount is
  root-equivalent on that Docker host.
- **Kubernetes target**: a NanoClaw host Pod needs DinD with a shared volume at
  matching paths (privileged), which is poor isolation. Prefer treating each
  NanoClaw agent as its own Pod through a NanoClaw Kubernetes driver (upstream
  work), or skip the NanoClaw runtime on Kubernetes and use the `plain` runtime.
- Because `grep` reports "binary file matches" on `docker-driver.ts` (it contains a
  non-text byte), searches of that file need `grep -a`.

## Recommendation

1. Build the `argus` channel (Q1) and a `nanoclaw` runtime for the **Docker
   target only**, with the identical-path mount requirement documented.
2. For credentials (Q2), start with OneCLI 1.42.0: on each lease, set the agent
   group's secret assignment; verify live whether a running session picks up a
   change. If not, apply changes at session spawn and treat a switch as a restart.
3. Defer Kubernetes + NanoClaw until a NanoClaw Kubernetes driver exists.

### Gateway install gotcha: port 5432

`--step gateway` (OneCLI 1.42.0) failed with `ports are not available: exposing
port TCP 127.0.0.1:5432`: its Postgres container publishes host port 5432, which a
native PostgreSQL service already held. Fix without touching the existing service:
set `POSTGRES_PORT=55432` in `~/.onecli/.env` (the compose file reads it), then
re-run the step. The installer's own hint ("a failed database migration is the
most common cause") is misleading here; the compose output above it names the
port. Read the full stderr, not the summary line.

## Credential switch test

Question: does `onecli agents set-secrets` reach a session that is already running?

Setup (dummy values, public echo host): one throwaway agent, two `generic` secrets
`spike-A`/`spike-B` for host `httpbin.org` injecting header `x-argus-test`
(`onecli secrets create --type generic --host-pattern … --header-name …`), A
assigned. A long-lived process under `onecli run --agent …` requested
`https://httpbin.org/headers` every 3 s; the secret assignment was switched to B
mid-run.

| Request | Time | Header received |
| --- | --- | --- |
| 1–2 | 16:28:44, 16:28:48 | `VALUE-A` |
| (switch) | 16:28:51 | `set-secrets` → B |
| 3–8 | 16:28:52 onwards | `VALUE-B` |

Result: **the switch applies to the next request, immediately, from the same
process.** The injection happens in the gateway, so nothing in the running agent
needs to change. Consequences for Argus:

- A lease change maps to one `set-secrets` call on the agent group's OneCLI
  agent; no session restart is needed.
- Quota fallback can therefore be transparent to a running NanoClaw agent: Argus
  swaps the account and the agent's next call uses the new one.
- Caveat: each request in the test opened a fresh connection; a long-lived
  keep-alive connection was not tested.
- `set-secrets` replaces the whole assignment list, so Argus must read, merge,
  and write (and serialize per agent group).

## Runtime built (2026-10-14)

Pool `runtime: nanoclaw` runs a host image against a bind-mounted checkout. Checked
live: Argus started the host container; it registered; a task made it spawn an
agent container from the host container through the identical-path mounts; the
agent reached the gateway and failed only for lack of a credential; terminating
the instance removed host and agent. Findings on the way: the host roots
everything at `cwd` (so per-instance working directories with shared symlinks),
needs `package.json` there, the upgrade tripwire needs a marker, the agent image
name derives from a hash of the working directory (so `CONTAINER_IMAGE` must be
set), socket paths must be short, and agent containers needed a descendant
selector to avoid leaking.

### First real run

With a credential registered (`--step gateway-auth`; every OneCLI agent is in
secret mode `all`, so no per-agent grant was needed) a task completed end to end,
and an `ASK:` round trip worked with a live model; see the integration README.
Found and fixed along the way: a drained NanoClaw host never exited, because the
channel did not leave when drained and idle, so the instance could not end.
