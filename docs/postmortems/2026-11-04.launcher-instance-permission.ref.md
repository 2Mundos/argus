# Postmortem: Worker instance directory permission denial under launcher

Date: 2026-11-04
Incident / PR: #194

## Summary

The launcher runs the Argus API container as `nobody` on a local Docker socket.
When starting a NanoClaw worker, the API attempted host-side `mkdir` and `chown`
for the instance directory. Because the directory lived under the operator's
filesystem, the host-side call failed with `PermissionError`. Because target error
handling only caught `DockerException`, the exception bypassed error recording:
the worker remained indefinitely in `reserved` state and the dashboard displayed
"starting…" with no explanation. The fix falls back to the helper container on
`PermissionError` and captures `OSError` as `TargetError`.

## Impact

Every worker launch on fresh launcher-managed installations (`argus up`) failed
to start. Workers remained stuck in `reserved` status and gave operators no
actionable error indication.

## Mechanism

1. `DockerTarget._prepare_dir` inspected `self._local_unix_daemon()`, which
   evaluated to `True` because the API container communicates via the local
   UNIX socket (`/var/run/docker.sock`).
2. When `_local_unix_daemon()` is true, `_prepare_dir` called
   `_prepare_dir_on_host(mount)`, attempting `os.makedirs` and `os.chown`
   directly from the API process. Since the API container runs as unprivileged
   `nobody`, this raised `PermissionError`.
3. In `DockerTarget._call`, only `(DockerException, asyncio.TimeoutError)` were
   caught and wrapped into `TargetError`. The uncaught `PermissionError` (an
   `OSError`) escaped into the reconciler unhandled, preventing `last_error` from
   being recorded on the worker instance.

## Why it escaped

- Local development servers run directly as the host user who owns the workspace
  and instance directories, so host-side `mkdir`/`chown` always succeeded in
  development.
- Unit tests for directory preparation only covered the remote daemon path
  (`tcp://...`) or assumed host permissions were available on local sockets.
- Error handling in `DockerTarget` assumed that all container setup and startup
  failures would manifest as `DockerException`, overlooking standard library OS
  errors raised during socket or filesystem operations.

## Guardrails added

Links to the tests, `AGENTS.md` rules, spec changes, or checks that now fail on this class of bug:

- Tests:
  - `test_prepare_dir_falls_back_to_a_helper_when_the_host_side_is_denied`
    in [`apps/api/tests/test_nanoclaw_hardening.py`](../../apps/api/tests/test_nanoclaw_hardening.py)
    verifies that an unprivileged process unable to write to the host directory
    falls back to the helper container.
  - `test_an_os_error_in_a_start_is_a_target_error`
    in [`apps/api/tests/test_nanoclaw_hardening.py`](../../apps/api/tests/test_nanoclaw_hardening.py)
    verifies that `OSError` raised during container startup is caught and
    converted to `TargetError`.
- Specs:
  - [`docs/specs/worker-launch.spec.md`](../specs/worker-launch.spec.md)
    reflects directory preparation fallback under unprivileged daemons.

## Lessons

1. Access to a local Docker socket does not imply write access to the host
   filesystem.
2. System calls made alongside driver operations must have their `OSError`
   exceptions mapped to target errors.
3. Hardening a service to run as an unprivileged user (`nobody`) requires tests
   verifying operations that previously relied on host permissions.
