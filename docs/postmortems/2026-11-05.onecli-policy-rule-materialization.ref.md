# Postmortem: Repository preflight blamed credentials when OneCLI published no policy rule

Date: 2026-11-05
Incident / PR: tasks `4a87a3ee`, `dadba422`, `26f34a88`

## Summary

Repository preflight blocked tasks with `policy_denied repository_write_access`
and told the operator the forge credential lacked push access, although the
OneCLI admin read showed both repository secrets assigned to the agent with a
matching scope. OneCLI publishes the policy rules its gateway injects by in a
`rematerialize` transaction; under concurrent secret and assignment writes that
transaction exceeded Prisma's fixed 5 s limit and failed with `P2028`, so the new
repository secret had no rule. The gateway forwarded the probe without a
credential, the public repository answered 200 without a permissions object, and
the preflight reported the resulting `unknown` outcome with the credential hint.
It escaped because the assignment check stops at admin-visible state and the
probe never retried after the proxy proved it had attached nothing.

## Impact

Tasks whose repository secret or assignment commit collided with another OneCLI
write could fail their first attempt with a misleading error and an `unknown`
outcome. It was seen in three incidents between 2026-11-01 and 2026-11-04; in
each, a later attempt that committed the same assignment after the contention
passed. No data was lost: the repository lease was released and the task could
be retried.

## Mechanism

1. The channel applies the repository lease with `PUT /agents/{id}/secrets` and
   `PATCH /agents/{id}/secret-mode`. Each write commits the assignment, then
   calls `td`, which calls the policy-coherence bridge's `rematerialize` inside
   a Prisma interactive transaction.
2. `rematerialize` reads every published and draft rule for the project and
   rewrites the materialized rows. With concurrent writes it runs past the
   hardcoded 5000 ms and throws `P2028 Transaction already closed`.
3. The catch in `td` logs the warning and the assignment write succeeds, so
   `GET /agents/{id}/secrets` confirms the secret while no `policy_rules_v2`
   row exists for it. The gateway injects only through those rules.
4. The preflight session's request reaches the forge without a credential and
   is logged with `injections_applied=0`. For a public repository the answer is
   200 with no permissions object, so the helper reports `policy_denied` and
   the host classifies it as `unknown`, not as a missing injection.
5. The `repository_write_access` hint assumes a credential was attached, so the
   task error says the credential lacks push access and suggests fixing the
   assignment, which is already correct.

## Why it escaped

- The preflight tests fake the probe at the host boundary and the assignment
  check at the OneCLI admin boundary. No test modelled "the admin read is
  correct and the gateway still injects nothing", so a real proxy that did not
  publish its rule looked like a credential or scope problem.
- The evidence contract re-read the forge answer but had no retry and no signal
  that the lease had been re-applied, so a transient publication failure and a
  wrong credential produced the same event.
- `request_logs` keeps only injected requests. The failed probe is absent from
  it, which makes the incident look like the probe never ran.
- The pinned OneCLI version is required for its secret-assignment API, so the
  upstream transaction failure could not be fixed by upgrading.

## Guardrails added

- Tests: `integrations/nanoclaw/argus-repo-preflight.test.ts` now proves that a
  200 with no permissions object re-applies the lease once and probes again,
  that only one retry happens, that a proven credential or a 4xx answer is not
  retried, and that a failed re-arm keeps the original failure.
- Rules / checks: the evidence event records `rearmed`, so the task log shows
  when the fix was exercised; the preflight still fails closed on the second
  answer.
- Specs: [failure classes](../specs/failure-classes.spec.md) 3.3.1 defines the
  one re-arm and the event field; [project code availability](../specs/project-code-availability.spec.md)
  records it in the configured-repository flow.

## Lessons

1. An admin read confirms the desired assignment, not the proxy's effective
   injection rules; verify with the same path the worker uses.
2. A public 200 without a permissions object proves no credential was attached,
   not that the credential lacks access.
3. When the proxy demonstrably attached nothing, re-apply the authoritative
   assignment and retry once before reporting a permission error.
4. Logging only successful injections hides the failures that matter most:
   absence of a request is not absence of a probe.
