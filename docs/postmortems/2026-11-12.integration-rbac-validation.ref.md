# Postmortem: Integration validation and credential changes failed open

Date: 2026-11-12
Incident / PR: Unfinished integration implementation, found during independent local review

## Summary

Integration validation treated incomplete evidence as success: sampled Kubernetes
permissions were described as namespace confinement, malformed negative reviews
counted as denials, and any MCP HTTP success counted as token acceptance. Credential
updates also assumed an exception meant SQLite had not committed. Tests exercised
mock HTTP responses and ordinary failures, missing the real HTTP core logging path
and cancellation around COMMIT. The corrections require explicit protocol and
store evidence, isolate credentialed HTTP logging, and finalize persistence before
propagating request cancellation.

## Impact

The unfinished implementation could mark invalid or indeterminate upstream replies
as valid, expose a bearer echoed into debug response headers, report a missing
credential as successfully revoked, or compensate a committed credential change.
This review established local defects, not production exposure. Worker credential
delivery remains absent. No real MCP server, cluster or credential was used.

## Mechanism

- The original negative Kubernetes probes missed cluster-wide pod listing. Even
  with the broader probe matrix, an absent boolean authorization decision or an
  `evaluationError` was interpreted as a denial. Neither establishes confinement.
- MCP validation ignored the JSON-RPC envelope and result. A public server can
  answer without accepting Authorization, and HTTP 200 can carry an RPC error.
- A regex using `$` accepted a terminal LF in a token. Sanitizing response details
  did not protect HTTP core DEBUG tracing, which formats raw response headers;
  an upstream could echo the bearer there or in a reason phrase.
- A store with no loaded referenced value could silently no-op deletion or lack
  the rollback value for rotation. Store readiness was not enforced by these routes.
- A cancelled COMMIT can finish in aiosqlite's worker thread. Outer exception
  compensation could then delete a committed create's secret, replace a committed
  rotation's token, or restore a committed revocation's secret. Filesystem work
  started by SOPS edits also must finish before any compensation is applied.

## Why it escaped

The permission matrix originally lacked a namespace pod reader with an additional
cluster-wide grant, then continued to model every authorization answer as a valid
boolean. MCP fixtures returned HTTP success without a valid protocol response.
MockTransport bypassed HTTP core's decoder and trace logger. Store tests covered
thrown write errors but not unloaded/missing references or silent deletion. No
service test cancelled immediately before and after a real COMMIT, so exception
handling was mistaken for proof of rollback.

## Guardrails added

- [Backend regression cases](../../apps/api/tests/test_integrations.py) exercise
  explicit namespace and broad grants, malformed and indeterminate negative
  reviews, modern MCP JSON/SSE and legacy fallback, matching IDs and result
  contracts, authentication failures and modern errors, and newline rejection.
- The same suite runs HTTP core over an in-memory network backend with hostile
  dummy credential echoes in response headers and the reason phrase. Assertions
  never print credential contents. Logging remains available outside the check.
- Store readiness, missing references, unreadable values and unconfirmed deletion
  have regression coverage. Cancellation tests await explicit milestones at
  COMMIT and fake SOPS edits; they verify row, secret, durable audit and normal
  post-commit event publication. Commit-interruption cases check serialized
  readback before compensation.
- [The living contract](../specs/integrations.spec.md#35-validation) states what
  protocol success proves and which replies fail closed. Its persistence section
  defines cancellation finalization and compensation boundaries; worker delivery
  remains an open item for every engine.
- [Dashboard fixtures](../../apps/dashboard/src/views/Integrations.test.tsx) use
  the accurate MCP success detail instead of claiming token acceptance.

## Lessons

1. Require explicit evidence before turning an unknown into success or denial.
2. Exercise the decoder and logging layer that can expose an untrusted response.
3. An exception during a commit does not prove rollback; finalize or read back.
4. A validation message must describe only the checks actually performed.
