## 2. Resolved questions

### 2a. Who runs the loop

Evidence:

- The API process hosts the background loops as asyncio tasks
  (`single-node.spec.md:27-32`). `main.py:153-154` registers `LoopStats` for
  `reaper` and `reconciler`; `main.py:168-195` starts the reaper, quota, runtime,
  reconciler and (when enabled) the workspace-cleanup loop as tasks.
  `ops.py:32` defines `LoopStats`; `ops.py:91` is `readiness`, which turns a
  stale loop into a failing check (`ops.py:117`, "no pass within").
- `DockerTarget` (`targets.py:176`) talks to the engine via `DOCKER_HOST` or the
  unix socket (`targets.py:238`). The `Target` protocol has `start`, `stop`,
  `list`, `list_by_label`, `logs` (`targets.py:166-173`) and no pause or unpause.
- `targets.py:103-107` maps Docker `paused` to `running`. A docker-paused
  container looks alive to Argus today, so nothing in the reconciler reacts to a
  pause.
- `targets.py:447-454` (`_list_by_label`) already lists containers by label
  including `paused`; `_mount_sources` (`targets.py:456`) maps containers to
  bind-mount sources. Both are usable to find the right containers and their
  instance directories.
- `runtimes.py:111` mounts the instance directory `rw` into the NanoClaw host
  container; `runtimes.py:125-126` mounts the Docker socket `rw` when the pool is
  not sandboxed. `runtimes.py:32-35` and `:42` (`descendant_label`,
  `descendant_owner`) recognise NanoClaw's agent containers, which Argus did not
  start; `worker-lifecycle.spec.md:412` says they are stopped with their instance.

Important detail the draft misses: the lease heartbeat comes from the NanoClaw
host container (the Argus-started one). Pausing that container would stop
heartbeats and let the lease expire. The guard must pause only the descendants
(agent containers found by `descendant_label`), never the host container.

Recommendation: the API process owns the guard loop (one more asyncio task, a
`LoopStats` entry, `main.py` next to the cleanup loop). NanoClaw host needs no
loop. Add `pause(ref)` and `unpause(ref)` to `DockerTarget` (and the `Target`
protocol; Kubernetes raises "unsupported"). Pause only on a target whose probe
reports `shares_filesystem` (the rule from `workspace-cleanup.spec.md:25` and
`:79`), that is, a local unix-socket daemon. Remote daemons and Kubernetes get
the warn and refuse bands only, as the API cannot measure their disks.

Gaps this leaves:

- A new `paused` status is needed in the Docker status mapping, or the guard
  keeps its own set. Otherwise a paused container is indistinguishable from a
  running one (`targets.py:103-107`).
- If the API restarts while containers are paused, the in-memory state is lost.
  On start the guard must list paused descendants and resume them when space is
  fine. Needs the status above.
- Whether agent containers actually write under the instance directory is
  unverified (NanoClaw owns their mounts, not Argus).

### 2b. "Wrote most" per container

- Session (descendant) writes: the instance directory is bind-mounted `rw`
  (`runtimes.py:111`) into the host container, and the heavy writes (workspaces,
  caches, checkpoints) land in bind mounts, not in a container writable layer.
- `docker ps --size` reports the writable layer (`SizeRw`) and walks it, which is
  slow. It cannot see bind-mount writes. Not good enough; reject.
- cgroup v2 `io.stat` `wbytes` is a cheap file read per container, cumulative.
  It measures write volume, not space held: overwrites and deleted files count.
  It is a good ranking signal for "wrote most while paused" (read once at pause,
  once at shed time, compare deltas). It does not say who occupies the space.
- For the shed decision, add one bounded directory-size sample per candidate
  instance, taken only at pause time (not per poll), using the existing bounded
  walker from workspace cleanup (`workspace-cleanup.spec.md` 3.3, 3.6).
  Rank by write delta; use directory size as tie-break and as the number shown
  in the event.
- Sandbox fact: `/sys/fs/cgroup/cgroup.controllers` lists `io`, but
  `cgroup.subtree_control` is empty here. Per-container `io.stat` needs `io`
  enabled for the Docker slice. Not verified on a Docker host. If `io.stat` is
  unreadable, fall back to the directory-size sample alone (state "ranked by
  size" in the event).

Recommendation: `io.stat` write delta for ranking, directory size at pause time
as the fallback and the displayed number; no `docker ps --size`.

### 2c. Warning band and a workspace-cleanup dry run

- A dry run writes only audit rows and the run row (`workspace-cleanup.spec.md:89`)
  and is open to managers even while cleanup is disabled (`:375`). It is safe to
  start automatically.
- Threshold conflict: `workspace_cleanup_low_disk_bytes` defaults to 10 GiB
  (`config.py:110`; spec table 3.1, `ARGUS_WORKSPACE_CLEANUP_LOW_DISK_BYTES`
  `10737418240`). Low-disk mode (3.7) therefore starts at 10 GiB, above the
  draft's 5 GiB warn band. It also measures the archive root and the instances
  roots only, not the data directory or Docker's data root.
- The conflict is one of ordering, not contradiction: cleanup's low-disk mode
  is the earliest, cheapest, already-specified reclaim; the guard bands are
  later. They must be written down together or an operator will read 10 GiB and
  5 GiB as two different "low disk" meanings.

Recommendation: the start of a warn episode triggers at most one dry run per
episode (never a real run), and the event carries the run id and the reclaimable
byte count. Keep the 10 GiB cleanup default; say in `workspace-cleanup.spec.md`
3.7 that low-disk mode is the first stage and the guard's bands follow it.
Draft numbers unchanged.

### 2d. Docker pause, leases and stall detection

Evidence:

- Heartbeats renew the lease. Observation never renews, expires or clears
  anything (`tasks/service.py:718-720`).
- Quiet is signal-based: after `ARGUS_QUIET_CLAIM_S` (default 1200,
  `config.py:96`, `:245`) with no `activity_at`, progress or live-log signal
  (`stall-visibility.spec.md:51-67`). `expire_stalled` fails a quiet claim after
  `ARGUS_STALL_FAIL_S` (default 3600, `config.py:99`, `:246`; `service.py:2140-2157`;
  `stall-visibility.spec.md:103-121`) and counts as a failure.
- The claim's wall-clock deadline (`timeout_s`, claim docstring,
  `service.py:293`) keeps running during a pause. Not checked beyond the docstring.

So the draft's "the lease is renewed with an explicit `paused_disk` heartbeat
reason, so stall detection does not count a paused attempt as quiet" does not
hold as written:

- Any heartbeat already renews the lease. A heartbeat does not stop quiet or
  stalled; those read `activity_at`, progress and live-log signals only.
- A paused container stops writing the session heartbeat file, so `activity_at`
  stops advancing. A pause longer than the remaining quiet window flags the
  claim quiet; one longer than 3600 s after that fails it as `stalled`.
- There is no heartbeat "reason" field today. The only structured channel is
  `LeaseObservation` (`argus_core/tasks.py:297-303`), a closed enum per part:
  `session` is `running|gone|unknown`, and the server answers `422` for other
  values (`stall-visibility.spec.md:3.7`).
- `stall_cause` (`service.py:2178-2203`) is "descriptive only: no decision reads
  it", and `quiet_facts_from_row` only evaluates it when `quiet_at` is set
  (`service.py:2247-2251`). A `paused_disk` cause alone would exempt nothing.

Who knows about the pause: the API itself (it issued `docker pause`). Options:

1. Reaper exemption (decision input). The guard exposes the set of paused task
   ids; `reaper.run` receives it like `quiet_claim_s` (`main.py:168-173`); the
   quiet stage and `expire_stalled` skip those tasks. Heartbeat observation adds
   nothing the API does not already know.
2. Heartbeat observation only (visibility). A new `session` value (for example
   `paused`) plus a `paused_disk` rule in `stall_cause`. Shows the cause in the
   inbox, exempts nothing.

Recommendation: do 1 for behaviour, and add 2 for visibility so the inbox says
why. Do not make the worker report the pause as authority.

Other points:

- Precedent for no attempt consumed: `env_workspace_missing`
  (`stall-visibility.spec.md` 3.7; `argus_core/tasks.py:267`, `:276`;
  `retry_class` is `ENVIRONMENT`, `test_stall_causes.py:260-285`). `env_disk_full`
  does not exist in code; it needs an entry in `ENV_BLOCK_REASONS`
  (`tasks.py:250`) so it maps to `RetryClass.ENVIRONMENT`.
- Wording conflict: the draft says "fail its attempt as `env_disk_full` (no
  attempt consumed)". In the class table (`failure-classes.spec.md:51-60`)
  `environment` means `blocked` with the `env_*` reason, an inbox row, and a
  manager unblock, not a requeue. Decide: block (existing rule, a person
  unblocks after freeing space) or requeue without spending an attempt (like
  `admission`; new rule). Recommendation: requeue without spending an attempt,
  held until the guard is out of the refuse band, because a person unblocking
  does not scale for a fleet-wide disk event. State this as a new rule in
  `failure-classes`, since it differs from the `environment` row.
- Shed is initiated by the API, not sent by the worker. The `env_*` reasons in
  `ENV_BLOCK_REASONS` are documented as reasons "a worker may send" (`tasks.py:248`).
  The server-side shed needs its own path into `block`
  (`service.py:1040`) or a requeue; not designed here.
- Pause churn: "resume the rest" in the shed row resumes sessions while space is
  still below 2 GiB, which pauses them again on the next poll. Recommendation:
  keep resume gated on the 2.5 GiB hysteresis only; while still paused, shed one
  writer per 30 s. Draft rule changed here, flagged.
- Measurement failure: `disk_free` returns 0 on `OSError` (`ops.py:152-156`),
  which would read as "below everything". The draft's "a failed measurement
  counts as below 2 GiB" would pause every running session on one transient
  `statvfs` error. Recommendation: a failed measurement refuses new claims
  (fail closed for new work) but pauses running sessions only after two
  consecutive failures. The guard must not reuse `disk_free` as is; it needs a
  variant that distinguishes "failed" from "0 free". Draft rule changed here,
  flagged.

## 3. Per-filesystem judgement (worst one decides)

Filesystems:

1. Argus data directory (SQLite, secrets, backups). Today's readiness measures it
   (`ops.py:119-122`; `MIN_FREE_BYTES = 64 MiB`, `ops.py:25`).
2. Task workspaces and checkpoints: `instances_root` (`config.py:46`) and the
   cleanup archive root (`config.py:103`).
3. Docker data root (`DockerRootDir`, `/var/lib/docker` by default), from the
   daemon's info call. Only local unix-socket daemons share a filesystem with the
   API (`targets.py:243`, `shares_filesystem`); remote daemons are reported
   `not applicable`, not `failed`.

Dedupe by `os.stat(path).st_dev`: one disk often holds several of these, and one
fact should produce one episode, not three. A deduped group takes the strictest
members' roles (a group containing the data dir counts as the data dir for the
64 MiB row).

Also check, unverified: if the API runs in a container, `DockerRootDir` is a
host path it cannot stat. Then the filesystem is `not applicable` unless the
operator mounts it read-only. That is an operator choice, not a default.

The 64 MiB readiness check stays data-dir-only and unchanged (operations 5 also
keeps `/readyz` free of filesystem walks and at one probe per 2 s). Guard bands
use all three, but the guard is a separate loop with its own cached reading.
`/readyz` does not read it, apart from the optional loop-staleness check.

| Band | Data dir | Workspaces / checkpoints | Docker data root |
| --- | --- | --- | --- |
| Warn (below 5 GiB, clear above 6 GiB) | one event per episode; Home banner; one cleanup dry run | same | same |
| Refuse (below 2 GiB) | claims refused; sessions paused; SQLite still writes | claims refused; sessions paused | claims refused; sessions paused |
| Resume (above 2.5 GiB on all) | resume; admit | resume; admit | resume; admit |
| Shed (still paused after 30 s) | heaviest writer shed; reclaim cannot help here (cleanup does not touch the data dir) | heaviest writer shed | heaviest writer shed |
| Below 64 MiB | `/readyz` disk check fails (unchanged) | no readiness effect | no readiness effect |

Notes on the table:

- Pausing helps least for the data directory: the writers that fill it may not be
  sessions (event log, backups, Litestream). Shedding a session may not free
  anything. Recommendation: for the data dir the guard still refuses claims and
  pauses (stops new load), but sheds only if the bytes written under the
  candidate's instance directory sit on that device. Flag for the owner.
- The 5/6/2/2.5 GiB numbers are absolute and were not changed. On small data
  disks they are large relative to the disk, so the warning could be permanent;
  a percentage floor is an owner decision (open question, section 5).

## 4. Spec-update plan

All settings are environment variables read by `Settings.from_env`
(`config.py`), like the cleanup settings. Proposed:

| Variable | Default | Meaning |
| --- | --- | --- |
| `ARGUS_DISK_GUARD_ENABLED` | `true` | Runs the loop (warn and refuse bands) |
| `ARGUS_DISK_GUARD_PAUSE` | `false` | Allows `docker pause` and shed (off until verified on a Docker host) |
| `ARGUS_DISK_GUARD_INTERVAL_S` | `5` | Poll interval ("every few seconds") |
| `ARGUS_DISK_GUARD_WARN_BYTES` | `5368709120` (5 GiB) | Warn below this |
| `ARGUS_DISK_GUARD_WARN_CLEAR_BYTES` | `6442450944` (6 GiB) | Clear the warn episode above this |
| `ARGUS_DISK_GUARD_REFUSE_BYTES` | `2147483648` (2 GiB) | Refuse claims and pause below this |
| `ARGUS_DISK_GUARD_RESUME_BYTES` | `2684354560` (2.5 GiB) | Resume and admit above this |
| `ARGUS_DISK_GUARD_SHED_AFTER_S` | `30` | Pause age before shedding one writer, repeated per period |
| `ARGUS_DISK_GUARD_FAIL_PAUSE_COUNT` | `2` | Consecutive failed measurements before pausing running sessions |

Startup validation: `clear > warn > resume > refuse`, else refuse to start (a
bad ordering would flap). `ENABLED=true` and `PAUSE=false` as defaults are
owner decisions: `single-node.spec.md` 3.5 says optional means off by default,
but the guard needs no external service. Recommendation above.

## 5. Open questions and blockers

Could not be verified here:

- Any real `docker pause`/`unpause` behaviour, the new paused-status mapping, and
  tmpfs-based tests: no Docker daemon or CLI in this sandbox.
- Per-container `io.stat`: `cgroup.subtree_control` is empty here, so the `io`
  controller is not enabled for children. A Docker host with cgroup v2 and the
  systemd driver is needed to check the path and that `wbytes` is readable.
- Where NanoClaw agent containers write (instance directory or their own
  mounts), and whether pausing them leaves the host container's heartbeat and
  claim path intact. Settled by a run on a Docker host with one real claim.
- Whether the API can see `DockerRootDir` when it runs in a container.

Decisions for the owner:

1. Shed outcome: `blocked` (existing `environment` row) or requeue without an
   attempt (recommended; new rule).
2. Defaults: `ARGUS_DISK_GUARD_ENABLED=true`, `ARGUS_DISK_GUARD_PAUSE=false`
   (recommended).
3. Absolute byte thresholds vs a percentage floor on small disks.
4. Whether the wall-clock `timeout_s` is exempt while paused.
5. Whether the guard's staleness fails `/readyz`.
6. Data-dir band: pause and shed when the data dir is the full disk, given that
   sessions may not be the writers.
7. Accept two changes to the draft: resume gated on 2.5 GiB only, and two
   consecutive failed measurements before pausing running sessions.
