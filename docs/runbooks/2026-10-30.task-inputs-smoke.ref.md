# Task inputs: Docker session smoke

The one check of [task inputs](../specs/task-inputs.spec.md) that the repository
tests do not run: a real NanoClaw **session container**, as its non-root user,
reading an input the channel materialized in the mounted group dir. Run it on a
Docker host with a disposable Argus database and a disposable task. Record the
result (date, host, NanoClaw commit, Argus version, output) in a report; this
runbook does not claim it.

## Before you start

- A NanoClaw checkout with the current channel installed and built
  (`integrations/nanoclaw/install.sh <checkout>`, then `pnpm run build`) and the
  worker instance recreated, so `GET /api/agents` shows `task-inputs` in
  `runtime.features` (spec 3.8).
- A pool whose capabilities include `task-inputs`.
- An orchestrator or admin token in `ARGUS_TOKEN`, the API at `$ARGUS`.
- A fixture with multi-byte UTF-8 of at least 62,300 bytes, for example a patch
  that applies to a throwaway repository.

## 1. Provision the task and the input

```bash
TASK=$(curl -s -X POST -H "Authorization: Bearer $ARGUS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"project":"global","title":"task-inputs smoke","required_capabilities":["task-inputs"]}' \
  "$ARGUS/api/tasks" | jq -r .id)
python3 scripts/attach_artifact.py --url "$ARGUS" --task "$TASK" \
  --file fix.patch --share-with-workers | tee attach.json
```

Then set `attachment:<id>:<sha256>` (the printed `ref`) as the continuation WIP
reference with `PATCH /api/tasks/$TASK/continuation`, and give the task an
objective that tells the model to run the verifier and `cat` the size with
`wc -c`, without applying anything.

## 2. Run

Let a `task-inputs` worker claim the task. Do not run a model by hand; the
channel materializes before the session starts.

## 3. Expected output

- On the host: `<group dir>/task-inputs/$TASK/` is mode `0700`, `fix.patch` is
  `0400`, both owned by the channel user, and `manifest.json` lists the id, size
  and SHA-256 of `attach.json`.
- `GET /api/tasks/$TASK/inputs` shows `materialized` and `verified` receipts for
  the attempt, then `consumed` once the attempt ends.
- In the session transcript: `node verify-inputs.mjs` prints
  `fix.patch <size> <sha256> ok` and exits 0; `wc -c` prints the same size; the
  container user is not root.
- No content, URL or token appears in the task events, the block error text or
  the channel log.

Negative check: on a second task, attach the same file without
`--share-with-workers` and set its `ref` as the WIP reference; the PATCH is
refused with `422 input_not_shared`.

## What the repository tests do not prove

- API tests cover upload integrity, the inputs view, receipts, isolation and the
  reference checks. Channel tests and `scripts/task-input-e2e.sh` run the real
  channel against a real API, but on the host, without a session container.
- Only this run shows that the Docker mount, its ownership and the container's
  non-root user can read the files, that the image's Node runs the verifier, and
  that a recreated instance advertises the feature.
