# Project agent images

A worker can only prove its own work if the image carries the project's runtime
and system libraries. One image for every project cannot: Radar needs Python
>= 3.12, the base has 3.11. So the image is built in three layers.

| Layer | Source | Carries |
| --- | --- | --- |
| Base | built by NanoClaw | node 22, chromium, git |
| Tools | `engines/Dockerfile.tools-layer` (`apply-tools-layer.sh`) | ssh, rsync, python3, uv, make, `argus-delegate`, model policy |
| Project | `engines/projects/<project>.Dockerfile` | the project's system libraries and interpreter (Radar also pins `graft`, refreshes `argus-gitea-api`, and sets `ARGUS_CODEX_TURN_TIMEOUT_MS=7200000` for long delivery turns) |

The project layer is additive: it starts `FROM` an image that already has the
tools layer and never changes it.

## Build

After changing the Codex turn overlay or `install.sh` patches, re-apply the
channel on the NanoClaw checkout and rebuild the **base** agent image (the
overlay lives in `container/agent-runner`, not only the project layer):

```bash
integrations/nanoclaw/install.sh /path/to/nanoclaw
# rebuild argus-nanoclaw-agent:<base-suffix> per provision.sh, then:
integrations/nanoclaw/engines/build-project-image.sh radar argus-nanoclaw-agent:<base-suffix>
```

For Radar, the build stages a prebuilt `@nanonets/graft@0.21.1` tree from
`$GRAFT_COPY_FROM` (default `~/.hermes/node/lib/node_modules/@nanonets/graft`)
because the slim agent image has no C++ toolchain for `npm install -g graft`.

The script builds `projects/radar.Dockerfile` on that base, tags the result
`argus-nanoclaw-agent:radar-<base-suffix>` and prints the tag as its last line.
It fails if `projects/<project>.Dockerfile` does not exist. It only builds: it
does not touch provisioning or `.env`.

Check the result (offline; fails if `uv`, `python3`, the project interpreter,
`git`, `ssh` or `make` is missing):

```bash
integrations/nanoclaw/engines/projects/smoke.sh argus-nanoclaw-agent:radar-<base-suffix>
```

Rebuild the project layer whenever the base or tools layer changes: its tag
carries the base suffix, so the old one stays valid for the old base.

## Point a pool at it

The image is chosen **per pool** through the existing `nanoclaw.agent_image`
field; there is no project field. A pool per project is what isolates projects:
give the Radar pool the Radar tag and leave other pools on their own image.
Set it in the pool editor (or pool upsert API), then start new instances through
the normal fleet lifecycle; running instances keep the image they started with.
Make sure the image is loaded on the node (`agent_image_archive` as usual).

## Optional disposable PostgreSQL for Radar pytest (worker runtime)

Radar integration tests that use the repo root `conftest.py` fixtures (`db_engine`,
`db_session`) need a reachable PostgreSQL instance. This is **operator-side QA
infrastructure** for workers on the Radar project image. Argus does not provision,
require, or manage Postgres; no fleet field or API change is involved.

### What to run

| Item | Choice |
| --- | --- |
| Image | `postgres:16-alpine` (same major as Radar CI) |
| Network | User-defined Docker network, preferably `--internal` (no host route) |
| Published ports | **None** — `HostConfig.PortBindings` and `NetworkSettings.Ports` must stay empty |
| Postgres container | Dedicated test fixture only; never Stage/Prod, never OneCLI's Postgres |
| Agent child | Existing session container keeps its original networks; **add** the test network with `docker network connect` (do not replace its default attachment) |

The agent child's default `localhost:5432` from the Radar `conftest.py` fallback does
not work inside an isolated bridge network. Point URLs at the Postgres container
**name** on the shared test network (DNS on that network).

### Environment variables (exact names)

Set these **inside the agent child** (or in the shell that runs `pytest` there):

- `RADAR_TEST_DATABASE_URL` — `postgresql+asyncpg://…` for pytest / `db_engine`
- `RADAR_DATABASE_URL` — same shape when running `make db-migrate` or tests that import `api.database`
- `DATABASE_URL` — optional legacy fallback for migrate paths that still read it

Use placeholder hosts in documentation and tickets, for example:

```text
postgresql+asyncpg://radar_user:<test-only-password>@<pg-container-name>:5432/<database-name>
```

Do not record real passwords, Stage/Prod hosts, or OneCLI DSNs in Argus or runbooks.

### One logical database per active task checkout

Root `conftest.py` runs `DROP SCHEMA public CASCADE` on session setup for the
pytest master worker. **Do not share one database across parallel task checkouts.**
Provision a separate database name per task workspace (for example
`radar_task_<id>_test` on the same disposable Postgres container) and set
`RADAR_TEST_DATABASE_URL` / `RADAR_DATABASE_URL` to that database before
`pytest` for that checkout.

When migrations are part of the gate, run `make db-migrate` with `RADAR_DATABASE_URL`
(and `DATABASE_URL` if the Makefile path requires it) aimed at the same database.

Run pytest **per task** with `-n0` during this QA unless you intentionally mirror
CI xdist grouping; ad-hoc parallel runs against one database will race the schema reset.

### Preconditions before resuming work or answering an Argus decision

Do **not** infer success from TCP alone or from a green port check on the host.

1. Postgres health: `pg_isready -U radar_user -d <database-name>` on the fixture container.
2. No published ports: inspect the fixture container and confirm `PortBindings` is
   null/empty and published port maps are unset.
3. Connectivity **from the authorized agent child**: open TCP (or run a minimal client)
   to `<pg-container-name>:5432` **inside** that child — the same network namespace
   the worker uses for `pytest`.
4. Confirm the child is the one whose mount contains **`/workspace/agent`** for the
   instance you intend to unblock (not a stale or unrelated `ncl-…` container).

Only after the above, **resume the same Argus task**; do not open a new batch of
tasks just because Postgres was missing.

### Child recreation and temporary watchers

NanoClaw may recreate an idle agent child. A disposable Postgres fixture survives on
the Docker host, but the **new** child must be attached to the test network again
and must receive the same env URLs. For temporary QA, an operator may run a short-
lived watcher that reconnects only children belonging to the authorized instance;
the watcher must have a deadline and stop on teardown. This is **not** automatic
product lifecycle or a shipped Argus feature.

### Provision / teardown pattern (operator tooling)

Operator-maintained scripts (for example scratch helpers alongside
`argus-pg-runtime-recipe.md`) typically:

- Label fixture resources (`argus.fixture.project=radar`, `argus.fixture.purpose=disposable-tests`).
- Create the internal network and Postgres container with test-only credentials.
- Create per-task databases on that instance.
- Connect the manifest child, verify in-child TCP, and write a small JSON manifest
  (network name, container name, database map, `published_ports: false`).

**Teardown:** remove only the labeled fixture container and test network created for
QA; disconnect the child from that network; keep the NanoClaw child and host
processes unless fleet policy says otherwise. Preserve manifest/label metadata until
cleanup so nothing else on the host is deleted by mistake.

A successful in-child TCP probe means the path is reachable, **not** that pytest
passed. Report test results only from actual `pytest` / `make` exit status.

## Adding a project

Copy `projects/radar.Dockerfile`, keep `ARG BASE` / `FROM ${BASE}`, install only
runtime libraries the lockfile's wheels need (justify any `-dev` in a comment),
install the interpreter with `uv python install <minor>` as user `node`, and
verify it with `uv python find <minor>`. Adjust the interpreter check in
`projects/smoke.sh` if the minor differs.

## Not covered

- Pre-warming the project's dependencies (`uv sync`): it needs the project's
  lockfile at build time, and the lock changes faster than the image. A worker
  syncs on first run, which needs network.
- `ffmpeg` for Radar's asset-pipeline tests: not installed; add it to the layer
  if those tests must run in the worker.

## `argus-gitea-api` commands

`get`, `issue-get`, `list-prs`, `status` (reads) and `create`, `update` (pull
requests; `create` is idempotent per head/base). Both writers take `--body-file PATH`
(regular file, at most 256 KiB) as well as `--body TEXT`, so long PR bodies need no
shell quoting. Workers are told this in the task prompt (`renderTask`); see
[worker lifecycle](../specs/worker-lifecycle.spec.md) 3.8.
