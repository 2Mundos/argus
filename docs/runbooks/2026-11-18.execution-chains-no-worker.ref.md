# Execution chains never admit work after Setup saves chains

This runbook documents an operational incident: after the operator saved execution
chains in Setup, new tasks of the configured difficulties stayed `ready` forever
and `POST /api/tasks/claim` kept returning `204` — no diagnostic explains it.
The root cause is a capability declaration mismatch; the fix is to declare the
route's adapter capability IDs on the pool, not to retry recycling blindly.

## Symptom

- New tasks whose difficulty has a saved execution chain stay `ready` and are
  never executed.
- `POST /api/tasks/claim` returns `204` for them (a worker claims, then the
  chain route is rejected), with no error surfaced in the task view.
- No obvious task-level or settings-level explanation points at the cause.

## Cause

Once any difficulty has a saved chain, a worker is admitted for that route only
if its pool `capabilities` — rendered into each instance's `ARGUS_CAPABILITIES`
— contain `execution-chains-v1` plus the `nanoclaw:harness:<adapter>:<provider>`
and `nanoclaw:executor:<adapter>:<provider>` capability IDs of the route. A
worker that declares none keeps legacy routing and cannot claim chain-routed
tasks (see the [Execution-chain capability declaration](../../integrations/nanoclaw/README.md)
and [`execution-chains`](../specs/execution-chains.spec.md)). The declaration is
evidence of which adapters the instance's image really contains, not a claim
about a live provider.

## Diagnosis (read-only)

```bash
# API: settings shows execution.chains with a non-default source
curl -s http://127.0.0.1:8000/api/settings | jq '.settings.execution.chains'
# API: task route shows execution.skips and the last selection
curl -s http://127.0.0.1:8000/api/tasks/<id>/route
# API: engines lists execution_capabilities; agents/Workers tab lists their registered
# capabilities. A worker that declares none is the suspect.
curl -s http://127.0.0.1:8000/api/engines | jq '.engines'
# Look for a task whose route.execution.skips contains engine_account_unavailable
# or a block reason of awaiting_execution_route: that is a provider-side lease
# symptom, not the capability cause — see the second symptom section below.

## Fix

1. Probe the agent image's CLIs first and use only the adapter IDs the image
   actually contains (from `GET /api/engines` `execution_capabilities`).
2. PATCH the pool `capabilities` to add `execution-chains-v1` and the exact
   adapter capability IDs for the adapters the image contains.
3. Recycle idle instances one at a time, not in bulk: a worker picks the
   declaration up at start, and never recycle an instance that holds a claimed
   task. New instances (recycled from the pool) inherit the corrected
   declaration.

## Second symptom (separate, report rather than auto-fix)
`skips: engine_account_unavailable` / block reason `awaiting_execution_route`
means the provider's account has no free lease slot (`max_leases` vs
`active_leases`). For a shared `local` account this can be the internal
orchestrator holding the lease. Report it to the account owner rather than
raising leases blindly.

## Last line
After a host restart a task attempt's lease expires and the task is requeued;
steers sent to the dead attempt are lost. Re-run the claim path on the
requeued task after fixing the capability declaration above.

## Prevention notes (suggestions, not done)
- Probe the image CLIs and record the adapter capability IDs once, rather than
  discovering them at runtime, so the declaration is accurate from the start.
- Make a claim that returns `204` for a chain route surface a capability
  mismatch instead of a generic 204, so the task view explains the stall.
