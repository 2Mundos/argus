# Model policy operation

## Changing models

Any one of these (they share the same service code and validation):

- **Dashboard:** Engines tab, "Model preferences". Edit, reorder (first is the default,
  the rest are fallbacks), add the Cursor executor (`agent`) if wanted, Save. "Restore
  defaults" removes the saved file.
- **REST:** `GET /api/models` (any token); `PUT /api/models` with both `harness` and
  `implementation` maps (admin); `DELETE /api/models` (admin). 422 names a bad chain.
- **MCP:** `get_model_policy` (any token), `set_model_policy(harness, implementation)`
  and `reset_model_policy` (admin).

Defaults: harness codex `gpt-6-luna`; implementation codex `gpt-6.1-sol` (placeholder
ID, replace it with the real CLI ID); claude harness and implementation
`claude-sonnet-5-5` then `claude-opus-5-5`. Revision, requested/configured model,
`resolved_model: null` and fallback reason are recorded per attempt.

## How it reaches NanoClaw

- **New instances:** the manager hands the effective policy (`ARGUS_MODEL_POLICY`, from
  the file or defaults) to instances it creates, so changes apply from the next start.
- **Existing instances** keep their startup policy and shared defaults file. To update
  them, reinstall the integration by hand with `integrations/nanoclaw/install.sh` and
  restart the instance. This is a manual step, never run automatically, and nothing is
  deployed by changing the policy.

## Details

Preferred way: edit the chains in the dashboard's Engines view (`PUT /api/models`,
written to `data/model-policy.json`). Point the NanoClaw host's
`ARGUS_MODEL_POLICY_PATH` at that file for it to take effect. If `ARGUS_MODEL_POLICY` is
set it wins over the file and the view says so.

Or set `ARGUS_MODEL_POLICY` in the pool's existing `env` editor (or pool upsert API).
It is a complete JSON replacement; omitted engines retain native defaults.
For example:

```json
{
  "harness": {"codex": ["gpt-6-luna"], "claude": ["claude-sonnet-5-5", "claude-opus-5-5"]},
  "implementation": {"codex": ["gpt-6.1-sol"], "claude": ["claude-sonnet-5-5", "claude-opus-5-5"]}
}
```

These are requested model IDs, not a declaration of provider availability.
Change them to the exact IDs accepted by your installed CLI/provider. No
credential changes are needed. Policy rejects unknown engines, empty/duplicate
chains, malformed IDs, and chains longer than ten models. Reorder a chain to
change its default; remove entries to disable escalation. Start new instances
through the normal fleet lifecycle to apply pool env updates; existing instances
keep their startup policy. No active instance is restarted automatically.

Provisioning must rebuild both the NanoClaw host integration and agent image.
`install.sh` places JS policy assets in host src/dist; a build that deletes dist
must rerun install.sh afterwards (provision.sh already does this). `install-engines.sh` copies image assets.
The thin engines2 Dockerfile also copies these assets. No changes to Stage/Prod
are part of this feature delivery.

Before every task the channel applies the harness model and writes the complete
snapshot to `groups/<folder>/argus-model-policy.json`, mounted as
`/workspace/agent/argus-model-policy.json` in the worker. It uploads
`model-policy-attempt-N.json` to the task's existing artifact list. A missing
snapshot is valid for standalone delegation (environment or shipped defaults);
a corrupt snapshot fails closed. Standalone callers can specify an explicit
snapshot path with `ARGUS_MODEL_POLICY_FILE`.

Use `argus-delegate claude --cwd /workspace/agent/argus-work` for the policy
default. On executor failure it tries the next configured model, recording both
runs; auth/quota/timeout/signal/installation failures are not escalated. No CLI
success is treated as evidence that your verification gates passed. After a
failed gate or context limit, request the next model explicitly:

```sh
argus-delegate claude --model-attempt 2 --fallback-reason verification_failed \
  --cwd /workspace/agent/argus-work < prompt.txt
```

`--model MODEL` pins that invocation and disables automatic fallback. The final
JSON contains all model attempts; each also has its own `.json`, `.out`, `.err`
and (where supported) last-message file. Attach the JSON reports to the task
using the normal file attachment flow. Reports contain task identity when a
snapshot exists, requested/configured models, policy hash and fallback reason.
`resolved_model` stays null: the channel/CLI argv proves a requested model, not
what the provider actually served. No paid calls are made by unit tests.
