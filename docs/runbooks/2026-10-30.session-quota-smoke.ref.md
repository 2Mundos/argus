# NanoClaw session quota: Docker smoke

The checks in [worker launch](../specs/worker-launch.spec.md) prove Argus
composes `CONTAINER_CPU_LIMIT` / `CONTAINER_MEMORY_LIMIT` onto a NanoClaw host.
They do **not** prove a spawned agent session carries `--cpus` / `--memory` on a
real Docker daemon, or that an OOM kill sets `OOMKilled` / increments
`memory.events`. Run this on a Docker host with a disposable NanoClaw worker;
record the result in a report. This runbook does not claim it.

## Before you start

- A NanoClaw checkout at the pin in `integrations/nanoclaw/provision.sh`, with
  the current Argus channel installed (`integrations/nanoclaw/install.sh`) and
  built.
- A NanoClaw pool with `cpus` and `memory_mb` set (for example `2` and `512`).
- `GET /api/fleet/capabilities` shows `session_quota` `ok: true` for that pool.
- A Docker CLI on the same daemon the pool uses (`docker` binary required).

## 1. Confirm host env

On the running NanoClaw host container:

```bash
docker exec "$HOST" printenv CONTAINER_CPU_LIMIT CONTAINER_MEMORY_LIMIT
```

Expect the pool values (`2` and `512m` in the example). Missing values mean the
instance was started before the propagation change; recreate the instance.

## 2. Spawn a session and inspect

Trigger any short task that starts an agent session. Then:

```bash
SESSION=$(docker ps --filter label=nanoclaw-role=agent -q | head -1)
docker inspect -f '{{.HostConfig.NanoCpus}} {{.HostConfig.Memory}}' "$SESSION"
```

Expect NanoCpus ≈ `cpus * 1e9` (or the driver equivalent for `--cpus`) and
Memory ≈ `memory_mb * 1024 * 1024`. Exact label filters may differ by NanoClaw
version; fall back to `docker ps` and match the session name from the host log.

## 3. Optional OOM signal (assistance)

Only when an operator needs Docker-side OOM evidence for
[agent resource hygiene](../drafts/2026-10-29.agent-resource-hygiene.draft.md):

```bash
# Disposable probe — do not run against a production session.
docker run --rm --memory 64m --cpus 1 alpine \
  sh -c 'cat /sys/fs/cgroup/memory.events; head -c 200m /dev/zero | tail'
docker inspect -f '{{.State.OOMKilled}} {{.State.ExitCode}}' "$PROBE"  # if kept
```

Workers without a Docker CLI should request help with:

```text
ASSIST: docker: need a disposable daemon to confirm session --cpus/--memory and OOMKilled / memory.events
```

That is technical assistance (`category: assistance`, resource `docker`), not a
scope decision.

## What the repository tests do not prove

- API tests cover `session_quota_env`, the readiness check, and host env on
  `container_spec`.
- They do not run `docker run` or inspect a live session container.
- Claude Code / Codex `BASH_ENV` handling and AppArmor `oom_score_adj` writes
  remain unverified here (see the hygiene research).
