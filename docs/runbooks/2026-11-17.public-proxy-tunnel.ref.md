# Public proxy tunnel going stale after a host restart

This runbook documents an operational incident: after the desktop host restarted,
the public dashboard URL stopped answering (TLS connected, then the request hung
until the client timeout) while `http://127.0.0.1:8000/healthz` stayed healthy.
The cause is stale `sshd-session` listeners on the VPS, and the fix is to stop
only those listeners and let the tunnel units reconnect.

## Topology

The preview API listens on the desktop only at `127.0.0.1:8000`. The public
URL is reached only through systemd tunnel units:

- `ssh-desktop-tunnel` opens a reverse forward from the VPS `127.0.0.1:18000`
  to the desktop's `localhost:8000`, plus an SSH forward on `8022`.
- `ssh-tinyproxy-tunnel` forwards `8889`.
- nginx on the VPS proxies the public hostname to `127.0.0.1:18000`.

A request through nginx goes through the tunnel to the preview API, so the public
URL is only usable while the tunnel is live and not merely while the preview
API is up.

## Symptom

- The public `/healthz` hangs until the client timeout (TLS connects, then the
  response header never completes).
- nginx on the VPS logs `recv() failed (104: Connection reset by peer) while
  reading response header from upstream`.
- On the desktop, the tunnel units sit in `activating (auto-restart)` and the
  journal says `remote port forwarding failed for listen port 8022` (or `8889`).

The local `http://127.0.0.1:8000/healthz` still answers, so this is not a
preview-API or nginx problem.
## Cause

After the desktop host restarted, `sshd-session` processes left behind from
before the restart still own the remote listening ports (8022 / 8889). New
tunnel sessions cannot bind those ports, so the forward fails and the units sit
in `activating (auto-restart)` instead of forwarding — the stale listeners
carry no traffic, which is why the local preview API is healthy while the
public URL is not.

## Diagnosis (read-only)

On the desktop:

```bash
systemctl --user status ssh-desktop-tunnel
journalctl --user -u ssh-desktop-tunnel -n 20
```

On the VPS:

```bash
ss -ltnp | grep -E ':(8022|8889|18000)\b'
ps -o pid,etimes,cmd -p <pid>   # age of any listener owning one of those ports
```

The VPS command shows which processes own each port and how long they have been
listening; the stale `sshd-session` processes are the ones to look for.

## Fix

1. Kill only the stale `sshd-session` pids that own one of those ports, as
   shown by the VPS command above. Do not kill the tunnel units or other
   sessions.
2. The units reconnect within about 10 seconds once those ports are freed.
3. Confirm, then check the public URL, not just the local one:

```bash
curl -sS -m 15 https://<public host>/healthz
```

A `200` means the tunnel, not only the preview API, is live.

## Prevention notes (suggestions, not done)

- Set `sshd` `ClientAliveInterval` / `ClientAliveCountMax` on the VPS so dead
  sessions release their listening ports automatically.
- The existing `ssh-tunnel-health-check` should check the public URL, not only
  the local tunnel process, so it notices this failure.
