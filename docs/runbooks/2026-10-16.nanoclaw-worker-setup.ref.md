# NanoClaw worker templates: setting up a node

How to make the two NanoClaw templates in the guided flow
([worker launch](../specs/worker-launch.spec.md)) **ready** on a Docker host:
`nanoclaw-sandbox` (sysbox, no socket) and `nanoclaw-socket` (host Docker socket,
**root-equivalent**). Each is "not ready" until its own prerequisites verify; the
step 1 artifacts are shared, step 2 is only for the sandbox template, and the
socket template needs the explicit opt-in in step 4. Nothing here makes Argus
claim readiness, and neither template ever falls back to the other.

## 1. User-owned artifacts (no root, no daemon changes)

```bash
integrations/nanoclaw/provision.sh          # state in ~/.local/share/argus-nanoclaw
integrations/nanoclaw/provision.sh env      # print the ARGUS_* lines for both templates
integrations/nanoclaw/provision.sh env-file # write them to ~/.config/argus/nanoclaw.env (0600)
integrations/nanoclaw/provision.sh check    # checkout, build and vitest only; no Docker (CI's nanoclaw-vitest)
```

It clones NanoClaw at the **pinned commit** in the script, installs the Argus
channel (`install.sh`), runs `pnpm install --frozen-lockfile`, rebuilds
`better-sqlite3`, builds, runs the channel tests, builds the agent image with
NanoClaw's own `container/build.sh`, tags it `argus-nanoclaw-agent:<commit>`,
saves it with `docker save` (the sandbox's private daemon starts empty), and
builds `argus-nanoclaw-host:dev` from `deploy/nanoclaw-host`. Override the state
directory with `ARGUS_NANOCLAW_STATE` (keep it short: the instances root is
limited to 56 characters).

`provision.sh check` runs only the suites named on the `pnpm exec vitest run` line in `provision.sh`; that includes the two preflight suites (`argus-repo-preflight.test.ts`, `argus-onecli-preflight-lease.test.ts`). `integrations/nanoclaw/tests/test_nanoclaw_vitest_list.py` (in `make test`) enforces: every `*.test.ts` that `install.sh` copies into `src/channels` or `src/gateway-providers` is on that line or in the test's `EXEMPT` dict (each with a reason: image-gated, e2e, or untriaged); stale exemptions fail too. Add new installed suites to the line, not to `EXEMPT`.

## 2. Isolation runtime for `nanoclaw-sandbox` (host level, needs root)

The sandbox template refuses to run without `ARGUS_NANOCLAW_DOCKER_RUNTIME` naming an
OCI runtime that the daemon actually offers; it never falls back to mounting
the Docker socket or to a privileged container.

Supported path: Sysbox CE from the upstream `.deb` (systemd required; `jq`
installed; the package registers `sysbox-runc` in `/etc/docker/daemon.json` and
signals Docker, and may restart it, which stops running containers).

**Compatibility to check first.** Sysbox's published matrix lists Ubuntu 22.04
and 24.04 (kernel 6.8+, fixed for containerd 2.x in v0.7.1). Ubuntu 25.10 and
kernel 6.17 are **not listed**: it may work, but it is outside what upstream
tests. Decide whether that is acceptable before installing, or use a supported
distro/VM as the Docker host (`ARGUS_FLEET_DOCKER_HOSTS`).

After installing, verify (read-only) that `docker info` lists `sysbox-runc`,
then prove the sandbox works before enabling the template:

```bash
docker run --rm --runtime=sysbox-runc argus-nanoclaw-host:dev docker --version
```

and start a host under it with the entrypoint's inner daemon (see the smoke
test in the integration README). Only then set the environment below.

## 3. Gateway: adapter (installed by `provision.sh`) vs service (operator's)

Two different things, measured separately:

- **Native adapter, needed for the host to boot.** NanoClaw exits at startup
  (`NANOCLAW_GATEWAY_PROVIDER='onecli' but no gateway provider is registered`)
  without a registered provider. `provision.sh` applies only the code part of
  upstream's `add-onecli` skill (copy the provider files, import it in
  `src/gateway-providers/installed.ts`, pin `@onecli-sh/sdk`, rebuild). It starts
  no service and handles no credential. Argus checks the built barrel
  `dist/gateway-providers/installed.js` actually imports the provider, not just that a
  file exists.
- **Gateway service, needed when an agent session starts.** The host boots,
  registers with Argus, heartbeats and claims tasks without it, but logs
  `Gateway approval subscription failed … fetch failed` (retrying with back-off)
  and cannot start the agent container: a claimed task stays claimed. The service
  is NanoClaw's upstream dependency (OneCLI's compose stack with Postgres, shell-rc
  edits), installed by NanoClaw's `--step gateway` and given the operator's model
  credential by `--step gateway-auth`. Argus does not install or require it, and
  the templates' *bootstrap* readiness does not depend on it.

### Running the gateway service on a single node (what was done on the first node)

Pinned to upstream's supported version (1.42.0, never newer: 1.43+ drops the
secret-assignment API the Argus channel uses) from upstream's own
`docker-compose.legacy.yml`, adapted in `~/.onecli/`: images by digest, **no published
Postgres port**, the gateway bound to loopback and the Docker bridge address only,
`restart: unless-stopped`, secrets in `~/.onecli/.env` (mode 600). Do not run the
upstream one-line installer or the skill's `setup.ts` unpinned: they track `latest`
and edit shell profiles. Account leasing is on whenever the pool has an OneCLI URL; Argus ranks every usable
account globally by priority ([global account selection](../specs/account-selection.spec.md)).
No provider list exists to set (the old `nanoclaw.account_providers` and
`ARGUS_ACCOUNT_PROVIDERS` are retired and ignored); the credential is leased from
Argus and written to the vault by the host, never put in an environment variable.

**Admin API isolation (upstream local mode has no login).** This image has two modes:
local (no login; the management API on 10254 is open) and OAuth (needs a Google OAuth
app). Because the API lists agents' proxy tokens and can change secrets and rules, it
must never be reachable from agent containers. So, on a single node:

- publish **10254 on `127.0.0.1` only**; Postgres has no published port;
- create a private network once (`docker network create onecli-control`), declare it
  `external` in the gateway's compose, and join only the gateway and the NanoClaw
  **host** containers: pool `docker.network = onecli-control`,
  `nanoclaw.onecli_url = http://onecli:10254`;
- keep the egress proxy **10255** on loopback and the Docker bridge address: agent
  containers (default bridge) reach it as `host.docker.internal:10255` and each request
  needs that agent's proxy token.

Result, verified from a real agent container: `onecli` does not resolve, the bridge
`:10254` is refused, the control-network address times out; the proxy and the LLM still
work. Limit that remains by design: a socket-enabled **host** is root-equivalent on this
Docker host and can reach everything, including this API; only the agent containers are
fenced off. Do not attach other containers to `onecli-control`.

## 4. Argus environment (no secrets)

`provision.sh env-file` writes the non-secret file (`EnvironmentFile=`-ready).
Shared: `ARGUS_NANOCLAW_INSTALL_DIR`, `ARGUS_NANOCLAW_INSTANCES_ROOT`,
`ARGUS_NANOCLAW_AGENT_IMAGE`, `ARGUS_NANOCLAW_HOST_IMAGE`.

- `nanoclaw-sandbox`: `ARGUS_NANOCLAW_DOCKER_RUNTIME=sysbox-runc`,
  `ARGUS_NANOCLAW_AGENT_IMAGE_ARCHIVE`.
- `nanoclaw-socket`: `ARGUS_NANOCLAW_ALLOW_DOCKER_SOCKET=true` (the opt-in; leave
  it out to keep the template unavailable **and** to refuse any raw
  `PUT`/`PATCH /api/pools/{name}` that would mount the socket),
  `ARGUS_NANOCLAW_USER=uid:gid` and `ARGUS_NANOCLAW_GROUP_ADD=<socket group id>`
  (derived by `provision.sh`; the host process runs unprivileged and reaches the
  socket through that group), optionally `ARGUS_NANOCLAW_DOCKER_SOCKET`. The agent
  image must be present on the node's daemon (step 1 builds it there). The Argus
  process itself must be able to reach the Docker daemon too, since it starts the
  host container. Do not set `nanoclaw.docker_socket` on a sandboxed pool
  (`docker.runtime`); that combination is rejected.

## 5. Kubernetes integrations (optional)

Tasks that select a Kubernetes integration reach the cluster through the channel's
own CONNECT broker, not the OneCLI gateway ([integrations](../specs/integrations.spec.md)
3.6 "Route"). It listens on one IPv4 address that sessions reach the host on, on a
free port, or on `ARGUS_INTEGRATION_ROUTE_PORT` in the host container's environment
when a firewall rule needs a fixed one. No `NO_PROXY` is set.

- `nanoclaw-sandbox`: the route listens on the Docker bridge address of the host's
  inner daemon, which runs the sessions. Nothing goes in pool env.
- `nanoclaw-socket`: sessions run on the outer daemon, where the host's `docker0`
  is not reachable. Without the setup below, Kubernetes tasks block as
  `env_integration_route_unavailable`.

### Socket mode: a dedicated network

1. Create a network only for this worker's host and its sessions, for example
   `docker network create argus-k8s-route`. Do not reuse `onecli-control` (sessions
   must never join it) or the default bridge.
2. Attach the host container to it, and make NanoClaw start its sessions on it.
   Argus cannot check where sessions run: confirm it with `docker inspect` on a
   running session container.
3. Set `ARGUS_NANOCLAW_INTEGRATION_ROUTE_BIND` in the Argus environment
   (`provision.sh env` prints it commented). Use the host's address on that network
   as an IPv4 literal, or `if:<interface>` for the host container's interface on it.
   With more than one replica, use `if:` so each host binds its own address. Argus
   refuses to start on a wildcard, loopback, link-local, multicast or reserved value.
   New `nanoclaw-socket` pools get it as `ARGUS_INTEGRATION_ROUTE_BIND`. At listen
   time the channel checks that it names exactly one IPv4 address the host holds.
   If it does not, Kubernetes tasks block with no listener and no `docker0`
   fallback. A request cannot set it, and a pool edit cannot change it.
4. Firewall: allow traffic from the network's subnet to the host's address on the
   route port only (set `ARGUS_INTEGRATION_ROUTE_PORT` to get a fixed port).

### Activate

1. `integrations/nanoclaw/install.sh <checkout>` and `pnpm run build` there;
   rebuild the tools layer (`provision.sh`, for `kubectl`).
2. If anything filters traffic from the sessions' network to the host container,
   allow it to the route port only.
3. Restart Argus if you changed its environment. Create or recreate the worker
   instances, then add `task-integrations` to the pool's capabilities.
4. Check: a task selecting a validated integration starts, and its first kubectl
   read succeeds. A block names its reason: `env_integration_route_unavailable`
   (no bridge, a bind address the host does not hold, bad port, cluster
   unreachable from the node) or `env_integration_gateway_intercepts` (the
   certificate does not verify against the integration's CA or name its host).

The socket-mode path is implemented and tested in source. No installed socket host
has run a sibling session against a fake API with a private CA, because there was
no container daemon to do it. Treat the first activation as that verification.

### Roll back

Remove `task-integrations` from the pool's capabilities, or clear the selection on
the tasks; running attempts lose their grants when they end. Deleting a task's
kubeconfig does not revoke its token: revoke it at the cluster as well.
Reinstalling the previous channel blocks every Kubernetes task as
`env_integration_gateway_intercepts`.

To undo the socket-mode route:

1. Remove the key from the pool:
   `PATCH /api/pools/{name}` with `{"env": {"ARGUS_INTEGRATION_ROUTE_BIND": null}}`.
2. Unset `ARGUS_NANOCLAW_INTEGRATION_ROUTE_BIND`.
3. Restart Argus and the host instances.

Kubernetes tasks on that worker then block as `env_integration_route_unavailable`.

## 6. MCP integrations (optional, `nanoclaw-sandbox` only)

Tasks that select an MCP integration reach its server through the channel's MCP
broker ([integrations](../specs/integrations.spec.md) 3.6 "MCP broker"), which holds
the token; the session's MCP config names a per-attempt grant URL on
`host.docker.internal`. The broker listens on the same Docker bridge address as the
Kubernetes route, on a free port, or `ARGUS_INTEGRATION_MCP_PORT` in the host
container's environment for a fixed one. Socket-mode workers block as
`env_integration_route_unavailable`. Section 5's bind address applies only to
the Kubernetes route, because the broker's grant URLs name `host.docker.internal`.

Activate:

1. Install and build the channel as in section 5 (no tools-layer change).
2. If anything filters traffic from the session bridge to the host container, allow
   it to the MCP port only.
3. Recreate the worker instances; `task-integrations` in the pool's capabilities
   covers both kinds.
4. In Setup → Integrations, give a `read_only` connection a tool allowlist (Edit,
   one name per line) and validate it. Select it on a task, then check: the task
   starts and a listed tool answers. A block names its reason:
   `env_integration_unavailable` (unvalidated, expired, no allowlist, the server
   refused the token or redirected), `env_integration_route_unavailable` (no bridge,
   bad port, server unresolvable, internal or unreachable) or `env_integration_gateway_intercepts`
   (its certificate does not verify against the public roots).

Correct a connection's URL, access or allowlist with Edit (`PATCH`), then Validate:
the edit resets validation, so tasks block until it passes again, and running
attempts lose their grant at the next heartbeat. Roll back: clear the selection on
the tasks, or Revoke the integration; running attempts lose access within one
heartbeat. Revoking in Argus does not revoke the token at the MCP server.

## Optional: engines overlay and gateway defaults

`ARGUS_NANOCLAW_ENGINES=1 integrations/nanoclaw/provision.sh` additionally installs
the native Codex provider, the pinned codex/opencode/Cursor CLIs, `argus-delegate`
and the Codex sentinel fix, and tags the agent image `…-engines`. `provision.sh env`
prints the matching `ARGUS_NANOCLAW_AGENT_IMAGE`. To make guided workers join your
gateway, set `ARGUS_NANOCLAW_ONECLI_URL` and
`ARGUS_NANOCLAW_NETWORK` (the Docker network that reaches the gateway). Unset, a
new pool keeps the plain defaults.
