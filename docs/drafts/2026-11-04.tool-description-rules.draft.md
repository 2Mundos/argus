# Tool description rules

## Context

[Model-facing evals](../specs/model-facing-evals.spec.md) check whether a
change to tool text makes the model behave better or worse. They don't say how
to write the text, or what it costs in context. Every MCP tool description and
schema is sent on every session's first turn, for every worker and the
orchestrator.

The DeepSeek harness keeps writing rules for model-facing text in an agent
skill (`.agents/skills/agent-experience`), and requires measuring first-turn
prompt tokens before and after a tool-definition change.

## Proposal

1. **Rules**, added to the evals spec under "Rules for agents":
   - Leave out constraints the model learns from the result (a missing task
     returns an error; a failed send was not delivered).
   - Describe what the tool does and returns, not how it is implemented.
   - Put a parameter's defaults, ranges and pairing rules on that parameter,
     not in the tool description. A description that varies with configuration
     means the varying part is a parameter.
   - Say each fact once: not in both the tool and the persona or
     `INSTRUCTIONS`, and not in two tools.
   - Put destructive effects and required checks before the action they guard.
   - Return bounded results with a reference for the rest. This one already
     holds: see `{text, bytes, truncated, ref}` in
     [MCP operations](../specs/mcp-operations.spec.md).
2. **A token budget check.** `make tool-tokens` uses `evals/source.py` (the same
   import path the evals use, no copy) to build the tool list and prompt for
   each role: orchestrator and worker. It prints each role's token count, plus
   a per-tool breakdown and the difference from `main`. Token counting uses a
   local tokenizer approximation, with no API call. `scripts/tool_tokens.py`
   builds the per-role totals and breakdown; run it with `make tool-tokens`. The
   difference from `main` is built: `make tool-tokens` prints it against `origin/main`.
3. **Agent rule.** A PR that changes tool descriptions, schemas or
   `INSTRUCTIONS` puts the `make tool-tokens` difference in its description. An
   increase needs a reason. No hard ceiling in the first version.

## Entry points

MCP is where the text lives. REST descriptions in the OpenAPI document are
read by people and the dashboard client, not models, so they are out of
scope.

## Success

The next tool-text change states its token difference, and the evals covering
it show no regression.

## Open questions

- Which tokenizer? A provider-exact count needs an API call. An approximation is
  enough for a difference.
- Should the first pass trim the existing tool text with these rules? Possibly,
  but only with the evals run before and after.
