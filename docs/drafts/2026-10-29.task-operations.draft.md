## Context

Argus remains one process, one SQLite database and local artifacts, with no new
required service. Existing worker access controls, redaction and prompt-data
isolation apply throughout. This draft builds on
[worker efficiency](2026-10-24.worker-efficiency.draft.md) (P4 checkpoint survival
and P5 stall visibility).

## 4. Make workspace ownership visible

Argus already defines a stable task workspace and node-local checkpoint
recovery. Make the current workspace owner and location understandable in the
task detail view, together with whether changes or a checkpoint are available,
unavailable or unknown. Avoid exposing host paths or credentials to unauthorized
users.

Read [task workspace](../specs/task-workspace.spec.md),
[checkpoint](../specs/task-checkpoint.spec.md) and
[worker read scope](../specs/worker-read-scope.spec.md) before designing this.
Clarify behavior after a worker disappears, when work sits on a remote worker
instance (still one Argus process), and when the reported owner is stale. The
dashboard continues to use the API, never a worker filesystem directly.

**Built:** the API slice. `GET /tasks/{id}` returns `workspace` (owner agent id and
checkpoint status), see [task workspace](../specs/task-workspace.spec.md) 3.5.

**Success:** an operator can identify where recoverable work lives and understand
why it cannot be inspected or restored when that information is unavailable.

## 5. Compare checkpoint representations

Hidden Git refs can capture workspace state without committing to the user's
branch. Compare that approach with Argus's existing hash-verified, node-local
[checkpoint](../specs/task-checkpoint.spec.md); do not replace the current format
until an experiment demonstrates a benefit and preserves its recovery guarantees.

Compare committed and uncommitted changes, untracked and ignored files, non-Git
state, secrets, binary files, disk limits, integrity verification, cleanup, and
restore after worker or node loss. Establish whether refs survive
[checkpoint restore](../specs/task-checkpoint.spec.md) into a later attempt and
whether they remain usable after
[workspace cleanup](../specs/workspace-cleanup.spec.md) archive and restore —
those are separate paths. A filesystem revert must not leave an agent conversation
claiming it has seen changes that were discarded; reject unsafe combinations.

**Success:** a small reproducible comparison identifies a concrete operational
benefit and all preservation limits, or records why the existing format is better.

## 6. Normalize engine events at the boundary

**Priority: only if an evidenced lifecycle or operator-signal inconsistency
blocks the shipped task view, commands or finalization (former §1–§3).** Provider adapters can present normalized commands and events to
orchestration. Audit Argus's
[engines](../specs/engines.spec.md), executor integration and
[model observability](../specs/model-observability.spec.md) for provider-specific
branches that produce inconsistent lifecycle or operator signals. Existing support
for multiple engines is not evidence that a new abstraction is needed.

If a concrete inconsistency emerges, define the smallest shared event vocabulary
that represents it, retain provider-specific detail as bounded evidence, and use
an explicit unknown state for unsupported signals. Preserve current account,
lease, authorization and failure-class behavior.

**Success:** the same meaningful lifecycle signal has the same interpretation
across the engines that can report it, while unsupported signals are not invented.

## Sequence and decisions

1. Include workspace ownership in the task detail view where the data exists (§4).
2. Run the checkpoint comparison (§5) and engine-event audit (§6) only against
   identified recovery or observability problems.
3. Update the relevant living specs before implementing any selected behavior.

Open questions: What workspace ownership data is authoritative on a remote worker
instance under one Argus process? Can any proposed checkpoint alternative
preserve all current recovery guarantees?

## Scope

No desktop shell, mandatory mobile app, new external service, or wholesale event
sourcing is proposed.
