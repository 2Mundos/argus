# Task operations and reliability

Status: draft · 2026-10-29

Progress: sections 1 and 2 are shipped (on main). Section 3 is shipped by
[task finalization](../specs/task-finalization.spec.md). Sections 4-6 remain draft.

## Context

Argus coordinates tasks and a fleet of workers. This draft proposes improvements
to task visibility, recovery and command reliability. These are candidates for
investigation, not descriptions of new current behavior. Any behavior change
needs a spec update before implementation.

Argus remains one process, one SQLite database and local artifacts, with no new
required service. Existing worker access controls, redaction and prompt-data
isolation apply throughout.

This draft builds on
[worker efficiency](2026-10-24.worker-efficiency.draft.md) (especially P4
checkpoint survival and P5 stall visibility). It does not reopen shipped
proposals there; it asks what operator surfaces and command guarantees are still
missing.

## 1. A focused task detail view

**Priority: first (parallel with §2).** An operator investigating a task should
be able to see its current attempt, state, live output, changes, progress, cost
and delivery together, and send steering from the same context. The view should
work on a narrow screen and show unavailable or stale information honestly.
Actions remain subject to their existing authorization and attempt boundaries.
This is an operator UI surface, not the on-disk
[task workspace](../specs/task-workspace.spec.md).

Argus already specifies [home](../specs/home.spec.md),
[live work](../specs/live-work.spec.md),
[stall visibility](../specs/stall-visibility.spec.md),
[logs](../specs/task-live-log.spec.md), [changes](../specs/task-changes.spec.md),
[milestones](../specs/progress-milestones.spec.md),
[cost](../specs/task-cost.spec.md), [steering](../specs/task-steering.spec.md)
and [delivery](../specs/task-delivery.spec.md). First map the existing task
journey and identify missing connections before designing another screen.
Investigate whether Argus can efficiently filter task updates while retaining
correct reconnect and history behavior.

**Success:** an operator can find a stalled task, inspect its latest attempt and
changes, and steer it without losing context; task switching and reconnect do not
mix attempts or silently omit updates. Check mobile usability and stream traffic
against the current view before selecting an implementation.

## 2. Durable, retry-safe commands

**Priority: first (parallel with §1), as an audit.** A client that times out
after issuing a command cannot necessarily tell whether it took effect.
Persisting command receipts and side-effect intent transactionally can make
retries clearer. Argus already requires writes through `Database.write()` and
forbids network calls in write transactions. Under
[worker launch](../specs/worker-launch.spec.md), pool create uses the pool name
as an idempotency key; `launch_worker` deduplicates via optional
`expected_desired_replicas` compare-and-set and can add another replica when that
field is omitted. Audit existing guarantees rather than assuming every command
needs an outbox.

For pool create, launch, steering and other commands with external effects,
document the retry key and scope, what an acknowledgment means, what survives a
restart, and how ambiguous or failed effects are surfaced. Where the audit finds
a concrete gap, consider a SQLite receipt or durable intent with bounded
retention and a reconciliation loop. A retry with the same key and different
input must be rejected; authorization must be checked on every request. Some
effects cannot safely be replayed, so recovery must reconcile or mark them
unknown rather than promise exactly-once execution.

**Success:** for each selected command, a lost response and an API restart have a
documented, observable outcome, and a retry cannot silently duplicate the action.
Scope the first change to an evidenced failure mode.

## 3. Separate execution from finalization

Investigate whether Argus can distinguish an agent's execution ending from checkpoint,
workspace and delivery follow-up, without implying that every task has all three.
Show the active step, failure or unknown state, and separate durations where the
underlying timestamps are reliable. Keep task success and retry rules explicit:
an agent exit alone must not imply successful preservation or delivery.

Start with [worker lifecycle](../specs/worker-lifecycle.spec.md),
[checkpoint](../specs/task-checkpoint.spec.md) and
[delivery](../specs/task-delivery.spec.md). Determine which steps are actually on
the critical path, what happens if the worker disappears, and how a later attempt
is fenced from stale finalization results.

**Success:** operators can tell whether the agent is running or follow-up work is
pending, and a failed or interrupted follow-up is visible without attributing its
duration to model execution.

## 4. Make workspace ownership visible

Argus already defines a stable task workspace and node-local checkpoint
recovery. Make the current workspace owner and location understandable in the
task detail view, together with whether changes or a checkpoint are available,
unavailable or unknown. Avoid exposing host paths or credentials to unauthorized
users.

Read [task workspace](../specs/task-workspace.spec.md),
[checkpoint](../specs/task-checkpoint.spec.md) and
[worker read scope](../specs/worker-read-scope.spec.md) before designing this.
Clarify behavior after a worker disappears, when work sits on a remote worker
instance (still one Argus process), and when the reported owner is stale. The
dashboard continues to use the API, never a worker filesystem directly.

**Success:** an operator can identify where recoverable work lives and understand
why it cannot be inspected or restored when that information is unavailable.

## 5. Compare checkpoint representations

Hidden Git refs can capture workspace state without committing to the user's
branch. Compare that approach with Argus's existing hash-verified, node-local
[checkpoint](../specs/task-checkpoint.spec.md); do not replace the current format
until an experiment demonstrates a benefit and preserves its recovery guarantees.

Compare committed and uncommitted changes, untracked and ignored files, non-Git
state, secrets, binary files, disk limits, integrity verification, cleanup, and
restore after worker or node loss. Establish whether refs survive
[checkpoint restore](../specs/task-checkpoint.spec.md) into a later attempt and
whether they remain usable after
[workspace cleanup](../specs/workspace-cleanup.spec.md) archive and restore —
those are separate paths. A filesystem revert must not leave an agent conversation
claiming it has seen changes that were discarded; reject unsafe combinations.

**Success:** a small reproducible comparison identifies a concrete operational
benefit and all preservation limits, or records why the existing format is better.

## 6. Normalize engine events at the boundary

**Priority: only if an evidenced lifecycle or operator-signal inconsistency
blocks §1–§3.** Provider adapters can present normalized commands and events to
orchestration. Audit Argus's
[engines](../specs/engines.spec.md), executor integration and
[model observability](../specs/model-observability.spec.md) for provider-specific
branches that produce inconsistent lifecycle or operator signals. Existing support
for multiple engines is not evidence that a new abstraction is needed.

If a concrete inconsistency emerges, define the smallest shared event vocabulary
that represents it, retain provider-specific detail as bounded evidence, and use
an explicit unknown state for unsupported signals. Preserve current account,
lease, authorization and failure-class behavior.

**Success:** the same meaningful lifecycle signal has the same interpretation
across the engines that can report it, while unsupported signals are not invented.

## Sequence and decisions

1. Map the existing task journey and audit command retries in parallel. Record
   concrete gaps and choose one small improvement in each area.
2. Trace execution and follow-up timestamps before proposing finalization states;
   include workspace ownership in the task detail view where the data exists.
3. Run the checkpoint comparison and engine-event audit only against identified
   recovery or observability problems.
4. Update the relevant living specs before implementing any selected behavior.

Open questions: Which operator journey currently takes the most steps? Which
commands have actually suffered ambiguous retries? Which finalization steps block
success today? What workspace ownership data is authoritative on a remote worker
instance under one Argus process? Can any proposed checkpoint alternative
preserve all current recovery guarantees?

## Scope

No desktop shell, mandatory mobile app, new external service, or wholesale event
sourcing is proposed.
