# Command guard for agent shells

Status: draft · 2026-10-29

## Context

Workers run Claude Code and Codex inside NanoClaw session containers without
approval prompts. The container, the AppArmor/seccomp
[Codex sandbox profile](../specs/codex-sandbox-profile.spec.md) and OneCLI
credential injection limit the damage a bad command can do to the host. Nothing
stops an agent from destroying what it can reach inside that boundary: the
mounted task workspace, its checkpoint, or a hosted repository it holds a token
for.

[Cloudroom](https://github.com/davidondrej/cloudroom) ships a small command
guard (`core/src/runtime/command-guard.mjs`, about 65 lines) as a native
`PreToolUse` hook for Codex and Claude Code. It rejects a short list of
catastrophic shell commands and returns a named reason to the agent. It is
explicitly accident prevention, not a sandbox.

## Proposal

Ship one guard script in the agent image and register it as a `PreToolUse` hook
on the shell tool of every harness that runs native hooks.

- **Rules.** Recursive deletion of `/`, `~`, `$HOME`, `/home/*` or `/root`;
  `--no-preserve-root`; `mkfs`/`mke2fs`; `dd of=/dev/<disk>` and redirects to a
  block device; `gh repo delete` and the equivalent `argus-gitea-api` /
  `argus-github-api` deletions, if they exist; fork bombs. Add Argus-specific
  rules only with a test case showing a real risk, for example deleting the task
  workspace root.
- **Fail open on guard errors.** A parse or runtime error in the guard allows the
  command. A missing guard binary blocks harness startup rather than silently
  running unguarded.
- **Block message.** `Blocked by Argus command guard: <reason>. Do not retry or
  work around this block.` The task continues; the agent decides what to do next.
- **Visibility.** Each block is a task event (`task.command_blocked` with the
  reason and a redacted, truncated command), so it shows in the live feed and
  can be counted on Fleet.
- **Opt-out.** A project setting (see [settings](../specs/settings.spec.md))
  disables the guard for that project's new attempts. On by default.

## What Argus has today

No command-level rule set. The Codex sandbox profile constrains syscalls and
file access for Codex's own Bubblewrap; it does not inspect commands. Cursor
(delegated through `argus-delegate`) runs no native hooks, so the guard cannot
cover it. Say so in the spec rather than implying coverage.

## Success

- Each rule has a positive and a negative test, shared between the hook and the
  Argus test suite (one source of truth for the patterns).
- A disposable worker shows a blocked `rm -rf ~` as a task event, and the agent
  keeps working.
- No measurable change in attempt duration.

## Open questions

- Where to register for Claude Code: managed settings in the image (for example
  `/etc/claude-code/managed-settings.json`) so a project's own `.claude`
  settings cannot remove it, or the account settings Argus already writes?
- Codex hook trust: Cloudroom pre-seeds a trusted hash in session flags. Which
  Codex version in the engines layer supports this, and does it survive
  `patch-codex-sandbox.py`?
- Should a block count toward any failure class, or remain purely informational?

## Out of scope

Allow-lists, LLM-based command review, network egress rules, and anything that
claims to contain a hostile agent.
