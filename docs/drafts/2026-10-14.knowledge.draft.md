# Knowledge — Draft

Status: draft; open questions answered 2026-10-14 (see §4). Builds after the
dashboard. Inspired by Radar's shared scenario knowledge
(`radar/docs/specs/shared-scenario-knowledge.spec.md`), reduced to fit
[lightweight single-node](../specs/single-node.spec.md).

# 1. Purpose and Scope

A shared, versioned wiki that agents and humans both read and improve, so the
fleet stops rediscovering the same facts: how a project builds and deploys,
conventions, decisions already made, pitfalls, who to ask. Knowledge is what
outlives a task; a task's spec and clarifications are what one task needs.

- **Humans** browse and edit pages in the dashboard.
- **Agents** search and read pages through the API/MCP while working, and
  propose additions or corrections when they learn something.
- **Orchestrators** curate: accept or reject proposals, attach pages to tasks.

# 2. Non-Goals

- Claim-level evidence and structural validation (Radar's `claims`). Pages are
  authored Markdown with page-level provenance.
- Elasticsearch, embeddings, or a vector store. Search is SQLite FTS5, which is
  built into SQLite. Semantic search may come later as an optional integration
  (single-node 3.5).
- A general-purpose wiki platform (permissions per page, attachments beyond
  artifacts, real-time co-editing).
- Changing agent instructions or permissions. Knowledge informs; it never
  grants.

# 3. Decisions Proposed

## 3.1 Scope: projects

Argus has no notion of a project yet, and knowledge is mostly per project.
Proposal: add **projects** (`slug`, `name`, `description`) as a lightweight
first-class scope.

- Tasks get an optional `project`; pools and kinds may later default one.
- Every page belongs to one project, or to the `global` space for fleet-wide
  knowledge (conventions, tooling, how Argus itself works).
- No per-project permissions in v1: any valid token reads every project.

## 3.2 Pages and revisions (from Radar 3.1–3.2)

- **`knowledge_pages`**: `id`, `project`, `slug` (unique per project), `title`,
  `tags`, `current_revision_id`, `state` (`active` | `archived`),
  `reviewed_at`, timestamps.
- **`knowledge_revisions`**: immutable; `number` (server-assigned, monotonic
  per page), `body` (Markdown), `summary` (one line, shown in search results),
  `author`, `reason`, `sources` (references to tasks, decisions, artifacts that
  justify the change), `created_at`.
- **Publishing is a compare-and-swap**: an edit names its `base_revision`;
  if the page moved meanwhile, it fails with `409 knowledge_conflict` instead
  of overwriting. Omitting the base on an existing page is refused. With one
  writer, the check is a simple compare inside the write transaction.
- **Restore** creates a new revision with the old body and a reason; history is
  never rewound.
- Archiving hides a page from search and agent reads; it stays readable in the
  dashboard.

## 3.3 Who writes

| Actor | Can |
| --- | --- |
| Admin (human) | Create, edit, restore, archive any page; accept/reject proposals. |
| Orchestrator | Same as admin, except archive (proposed: also allowed). |
| Worker | **Propose** only: a new page, or an edit against a base revision, with a reason and sources. |

A worker proposal opens a decision (3.10 of the worker lifecycle spec, new kind
`knowledge`, audience `any` by default). Accepting it publishes the revision
(still a compare-and-swap; a proposal whose base moved is returned as
conflicting rather than merged). Rejecting it records the reason. This reuses
the inbox instead of adding a second one.

Clarifications feed in naturally: when answering a worker's question, the
answerer can tick "save to knowledge", which turns the question and answer into
a proposal or an edit on a chosen page.

## 3.4 How agents use it

- **Search**: `GET /knowledge/search?q=&project=` over title, summary, body, and
  tags (FTS5, ranked by bm25), returning page id, title, summary, snippet, and
  freshness. Archived pages never appear.
- **Read**: `GET /knowledge/pages/{id}` (current or a pinned revision).
- **On claim**: the claimed task carries `knowledge`, a short list of page
  references: pages pinned to the task or its kind, then the top FTS matches for
  the task's title within its project. References only (id, title, summary), so
  the claim stays small and the agent decides what to read.
- **MCP tools**: `search_knowledge`, `get_knowledge_page`,
  `propose_knowledge_change`.

## 3.5 Freshness

`reviewed_at` is set when a human or orchestrator confirms a page is still
right (an edit counts). Pages not reviewed for `ARGUS_KNOWLEDGE_STALE_DAYS`
(default 30) are marked `stale` in search results and the dashboard, ranked
below fresh pages but never hidden: omission would read as "nothing is known".

# 4. Open Questions

Answered 2026-10-14:

1. **Projects**: yes, a first-class scope (3.1).
2. **Worker writes**: allowed, controlled by a setting
   (`ARGUS_KNOWLEDGE_WORKER_WRITES`: `propose` (default) or `publish`). With
   `publish`, worker edits publish directly and still record author, reason,
   and sources, so they can be reviewed and restored afterwards.
3. **Automatic context on claim**: yes (3.4).
4. **Structure**: plain Markdown for now; page types can come later.
5. **Build order**: right after the dashboard.

Still open: whether a task's project becomes required once projects exist.

# 5. Constraints

- Everything in [single-node](../specs/single-node.spec.md): SQLite (FTS5 for
  search), no extra services.
- Writes go through the single writer; FTS indexes are updated in the same
  transaction as the revision, so search never lags a committed page.
- Knowledge must never be the only place a task's requirements live: a task
  spec states what the task needs; knowledge is background.

# 6. Implementation Consequences

1. Projects (table, optional `project` on tasks).
2. Pages, revisions, CAS publish, restore, archive; FTS5 virtual table kept in
   sync on publish/archive.
3. Search and read endpoints; `knowledge` references on claim.
4. Proposals as `knowledge` decisions; "save to knowledge" on question answers.
5. Dashboard: browse, search, view history, edit with conflict handling,
   proposal review in the inbox.
6. MCP tools when the MCP endpoint lands.
