# Resume the same conversation after a quota pause

Status: superseded by [quota resume](../specs/quota-resume.spec.md) · 2026-10-29

## Context

[Account selection](../specs/account-selection.spec.md) already does most of
what [Cloudroom](https://github.com/davidondrej/cloudroom) calls "continue after
a usage limit". A quota notice marks the account exhausted, puts the task back to
`ready` on the same attempt without counting a failure, or parks it as
`awaiting_quota` until an account is usable again. A new or re-enabled account
and a secrets reload wake it.

What remains is the work context. The next claim starts a new agent session
([one task per session](2026-10-24.worker-efficiency.draft.md), P3). The
[task checkpoint](../specs/task-checkpoint.spec.md) restores files, but the model
starts over: it re-reads the repository and re-plans. Cloudroom instead restarts
only the harness with the new login and sends `keep working` into the same native
conversation. It touches only sessions stopped by quota, never ones the user
stopped manually or that are busy, and never sends anything twice.

This is a narrow slice of worker-efficiency P4 ("interruptions keep the work"),
whose session-transcript resume is still unproven. If P4 is specified first,
fold this into it.

## Proposal

For a quota pause only (not crashes or stalls):

- Record the native session identifier with the paused attempt: the Claude Code
  session id or Codex thread id, plus the node and engine.
- When the task is next claimed on the same node with the same engine, NanoClaw
  resumes that session with the new account's credentials and sends one framed
  operator message ("your previous account hit a usage limit; continue from where
  you stopped"). It uses the same framing as
  [task steering](../specs/task-steering.spec.md).
- If the native session is missing, from another engine, or unreadable, fall
  back to today's fresh session with the checkpoint restored. Never silently
  start a fresh conversation while reporting a resume.

## Success

On a disposable node with two accounts and a fake quota notice, the second claim
resumes the same Claude session (same session id, prior turns visible) under the
second account, and the attempt counter and failures match today's quota path.

## Open questions

- Does a mid-session credential swap work through OneCLI injection without a
  container restart, or must the container be recreated around the same session
  files?
- How long does a paused native session stay valid (context window, provider
  retention)? Should there be a cutoff after which a fresh session is better?
- Codex: is resuming a thread with a different ChatGPT account supported?

## Out of scope

Resuming across nodes or engines, and resuming after `session_lost`. Those
belong to P4.
