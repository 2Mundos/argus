# Agent container resource hygiene

Status: draft · 2026-10-29

## Context

Agent session containers are created by NanoClaw's `container-runner.ts`, which
Argus patches at install time (`integrations/nanoclaw/patch-*.py`). Inside a
container with a memory or CPU limit, two things go wrong:

- **The wrong process dies on OOM.** With no swap, the kernel kills the largest
  process, which is often the harness (Claude Code or Codex) rather than the
  runaway build it started. The attempt then looks like `session_lost`, not a
  tool failure.
- **Tools oversubscribe the CPU.** `nproc`, Node's `os.cpus()` and Python's
  `os.cpu_count()` report every host CPU, so test runners and bundlers start one
  worker per host core inside a quota of two.

[Cloudroom](https://github.com/davidondrej/cloudroom) handles both in
`core/src/runtime/linux.rs` (`agent_env`), documented in
`core/docs/harnesses.md`.

## Proposal

1. **OOM priority.** Every shell command the harness runs gets
   `oom_score_adj=500` through `BASH_ENV` (and `CLAUDE_ENV_FILE`, which Claude
   Code's command shells source). Its children inherit it. The harness and the
   NanoClaw agent runner keep 0, so a build dies before the agent does and the
   agent can report it. Raise-only: the shim sets 500 only when the current
   value is lower, never lowers it, and needs no capability to raise.
2. **CPU count matches the quota.** When the container has a CPU quota, set
   `OMP_NUM_THREADS` and `PYTHON_CPU_COUNT` to it, preload a small Node module
   that trims `os.cpus()`, and ship a `sitecustomize` for Python older than 3.13.
   The values come from the session quota, not the host. A variable is set only
   if unset, so a value the user or project sets wins. Caveats: a project that
   sets `NODE_OPTIONS` replaces it, so a preload delivered through it can be
   lost (append on load and log when it is missing). `PYTHON_CPU_COUNT` works
   only on Python 3.13+ (unverified, no 3.13 interpreter was available); older
   Python needs the `sitecustomize`, which `python -S` skips.
3. **Classify the result.** Detect an OOM kill per command from the cgroup
   `memory.events` `oom_kill` delta, read before and after each command, and per
   session from exit code 137 plus `OOMKilled=true`. Classify the attempt as
   `session` with an `oom_kill` fact first; promote to `env_oom` only after 2
   consecutive OOM-killed sessions on one pool, so
   [failure classes](../specs/failure-classes.spec.md) can tell an undersized
   pool from a crash. Unverified: Docker `OOMKilled` and the `memory.events`
   increment on a real kill (no Docker daemon was available).

The helpers live in the agent image (tools layer), not in the per-task mount.

## What Argus has today

No OOM adjustment, no CPU-count shims. Pools can request CPUs and memory, and
[worker launch](../specs/worker-launch.spec.md) checks the request against the
node. Runtime probes and the Codex enforcement probe pass `--memory`. Whether the
per-session agent containers NanoClaw creates carry a quota is not established.

## Success

- In a disposable container with `--memory 512m --cpus 2`, a command that
  allocates without bound is killed while the harness survives and reports it.
- `node -e 'console.log(os.cpus().length)'` and `python -c 'import os;
  print(os.cpu_count())'` print 2 in that container.
- An OOM-killed session is reported on Fleet as `session` with the `oom_kill`
  fact, and as `env_oom` after 2 consecutive ones on a pool.

## Open questions

- Do NanoClaw session containers inherit the pool's CPU/memory request? If not,
  should they get one first? Without a quota, item 2 does nothing and item 1 only
  matters when the host itself runs low. Answer (research): not in this repo, so
  quota first; the upstream NanoClaw source is needed to confirm.
- Does `oom_score_adj` need `CAP_SYS_RESOURCE` to raise the score? Answer
  (research): raising it needs no capability, lowering does. Unverified under the
  AppArmor profile (not loaded in the research environment). Also unverified:
  `BASH_ENV` and `CLAUDE_ENV_FILE` handling by Claude Code and Codex shells.

## Out of scope

Autoscaling pools by memory pressure, and per-task resource budgets.
