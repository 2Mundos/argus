## Problem

Over eight days of production use (2026-10-16 to 2026-10-24), Argus finished only
39% of tasks (101 of 257) and needed 2.3 attempts per task. A few tasks reached 64
and 65 attempts. Of 984 claims, 609 ended in `task.fail` and only 119 in
`task.complete`. A successful task took a median of 85 minutes from creation, and
the p90 was about 45 hours. Driving Claude Code directly is faster and cheaper. The
cause is the architecture around the model, not the model.

| Signal (events) | Count | Note |
| --- | --- | --- |
| `task.fail` reason `quota` | 332 | median 6 s after the claim; a claim → fail → claim loop |
| `task.fail` "The agent run failed. Check the logs…" | 102 | cause unknown to Argus |
| `task.fail` `provider_failure` / `worker_fail` | 53 / 51 | |
| `task.expire` (`lease_expired` 17, `timeout` 15, …) | 37 | median 120 min each, 112 h in total, against 23 h for every successful attempt combined |
| `task.block` `awaiting_quota` | 62 | |
| `task.released` (recycle, terminate, orchestrator) | 30 | live work dropped |
| `agent.lost` | 135 | |
| failures saying "no checkout in /workspace" | ~20 | retried, with the same result each time |

## Root causes

1. **Admission is predicted, not reserved.** `claim()` gates on a *model* of quota
   (`apps/api/src/argus_api/tasks/service.py:291`). The real account lease is taken
   later, on the worker (`integrations/nanoclaw/argus.ts:2122`). When the two
   disagree, the worker claims the task, fails it with `quota`, and claims again
   about every 6 s. One task logged more than 20 attempts in two minutes.
   The `quota` label is also wrong much of the time. `ensureAccount` returns false
   for *any* lease or apply error, including OneCLI or vault apply errors, network
   errors and repository reconcile errors (`argus.ts:2487-2507`). So many of the 332
   were never real provider limits.
2. **Nobody owns the workspace.** Nothing in Argus clones the task repository. The
   harness model picks its own directory under `/workspace/agent`, and the
   repository URL and credentials only exist when the task carries
   `repository:write` (`argus.ts:2158-2187`). The workspace lives on the instance,
   so a new instance starts empty. The only pre-model checks cover the image, the
   account, the model policy and the repository lease. `preflight`
   (`argus.ts:1758-1777`) only observes PR artifacts. A missing checkout is
   discovered by an LLM session, which reports the problem and fails. The task is
   then retried into the same empty workspace. A blanket `catch`
   (`argus.ts:2209-2216`) reports every error from that stage as "repository
   credential unavailable".
3. **Attempts are disposable.** Recycle, drain, lease expiry and `agent.lost` end the
   attempt. The next attempt may land on another instance with an empty workspace,
   so it rebuilds understanding from the spec and the continuation notes. Every
   interruption pays the whole warm-up again. On top of that, the worker interrupts
   itself:
   - It re-leases its account every 60 s (`REBALANCE_MS`, `argus.ts:107`).
   - Any account change, including a mid-run failover, kills the session containers
     (`recycleRuntime`, `argus.ts:3004`). So does a harness-model change
     (`argus.ts:3317-3321`) or a project-image change (`argus.ts:3237-3241`).
   - After such a kill, the full task text is re-sent with "continue this task"
     (`argus.ts:1929-1938`). After 3 re-sends the attempt fails.
   - An `agent.lost` without draining counts as a failure
     (`tasks/service.py:2018-2022`).
4. **Liveness means "heartbeating", not "progressing".** The lease (120 s) is
   renewed by a 30 s heartbeat whether or not the session is doing anything
   (`tasks/service.py:678-704`, `argus.ts:1549-1592`). A stuck session therefore
   holds its claim until the wall-clock `timeout_s`, which is often 7,200 s, and
   then fails as `timeout`. A dead attempt costs about two hours before it is
   retried.
5. **Two models per worker, glued by a shell call.**
   - The harness runs on Haiku in one session per instance. It delegates the coding
     to an executor (Opus, Sonnet, Codex or Cursor) by running `argus-delegate`
     through its Bash tool.
   - Every executor call is a fresh, memoryless session
     (`--no-session-persistence`, `codex exec --ephemeral`;
     `engines/argus-delegate.mjs:327-405`).
   - The executor gets only a prompt file that the harness writes. The harness gets
     back only the last 2,000 characters of output inside a report of 5 KB or more
     (`argus-delegate.mjs:42, 1006-1035`).
   - Context is paid twice and lost at the handoff.
   - The Bash tool caps foreground calls at 2 minutes while a delegate run takes up
     to 15 minutes. Session logs show 36 "Command timed out after 2m 0s" and 172
     calls pushed to the background, so the harness polls while burning tokens.
   - Haiku alone used about 100M cached input tokens over 148 runs.
6. **Sessions carry every task an instance has run.** The agent group uses
   `session_mode: "shared"` (`integrations/nanoclaw/init-argus-agent.ts:102`), and
   the harness resumes the same session for each new task. Context grows until it
   compacts; transcripts show 33 compactions. Late replies from earlier tasks land
   on the current one: releases cite "cross-task result contamination", and the
   reply fence (`argus.ts:587-600`, `replyScopeNotice`) is a workaround.
7. **Much of the prompt has nothing to do with the task.**
   - Each harness loads a 20 KB group `CLAUDE.md` (about 5k tokens). About 20 KB of
     that is generic NanoClaw material: agent creation, the `ncl` CLI, scheduling,
     cards, self-modification. Only about 350 bytes describe the Argus role.
   - Each task injection adds 9–11 KB of fixed process rules: repository, PR, CI,
     merge, phases, the delegate contract (`renderTask`, `argus.ts:877-976`).
   - Worst case per injection is about 60–80 KB, and the whole injection is re-sent
     on every account switch.
8. **Failures are not classified for retry.** Transient, quota, environment and task
   failures share one rule (`failures+1 < max_attempts`,
   `packages/core/src/argus_core/tasks.py`), so failures that will repeat
   identically are retried until the budget runs out.
   - "The agent run failed…" is the upstream NanoClaw runner's placeholder when the
     provider's message is dropped. Runner overlays add structure only for rate
     limits and Codex auth.
   - The log-tail fallback that could explain it (`cfg.agentLogTail`,
     `argus.ts:1859`) is never configured outside tests.
9. **We cannot see yield.** Only about 33 of 257 tasks have usage rows, so tokens
   per succeeded task cannot be computed today.

## Proposals (in order)

### P1 — Claim reserves the account (fixes 1)

`claim()` leases the engine account in the same `Database.write()` transaction. It
returns the task and the lease together, or nothing. The worker's
claim-then-fail-for-quota path (`argus.ts:2122-2145`) goes away, so an agent with no
lease never receives a task. Lease and apply errors get their own reason instead of
`quota`.

*Target:* zero `task.fail` with reason `quota`, and no attempt spent on admission.

*Status:* done. `claim()` takes the lease in its transaction; lease and apply errors
fail as `account_unavailable`, and both admission reasons spend no attempt.

### P2 — Argus owns the workspace and checks it in code (fixes 2)

- The host prepares the task workspace before the model starts: a git worktree of
  the project repository on a task branch, at a fixed path. It is keyed by task id
  and lives on the host's local disk, not in the instance directory.
- A deterministic preflight checks that the checkout is present with the expected
  remote and branch, that the repository lease is applied, that the executor
  credential works (the `argus-delegate` probe), and that the runtime is verified.
- On a preflight failure the task is blocked with a typed reason such as
  `env_checkout_missing`, `env_credential_missing`, `env_repo_not_allowlisted` or
  `env_executor_auth`. No attempt is spent and no LLM tokens are used.
- One inbox item covers the whole project or pool.
- The blanket `catch` is replaced with one reason per step.

*Target:* no LLM session ever starts without a checkout.

*Status:* done, except the executor probe. The repository preflight blocks with
`env_repository_*`. The channel then creates or validates the task workspace and
blocks with `env_workspace_*` ([task workspace](../specs/task-workspace.spec.md)).
It is a `git init` with the task branch and origin, not a worktree: the worker
fetches inside the container. It lives in the instance directory, not elsewhere
on the host. `env_executor_auth` stays reserved until a probe can run before the
session. P4 is untouched.

### P3 — One task per session (fixes 6, part of 7)

Every claim starts a new agent session: no `--resume` across tasks and no shared
session mode. That makes the reply fence and scope reminders unnecessary, and it
makes per-task usage attribution exact. The group `CLAUDE.md` is cut down to the
Argus role plus the tools a worker actually needs.

*Status:* done, as specified in [worker lifecycle](../specs/worker-lifecycle.spec.md): one
NanoClaw session per attempt (`per-thread` wiring, thread `argus:<task>:<attempt>`),
closed when the attempt ends, and `cli_scope: "disabled"` (about 7.7 KB less
`CLAUDE.md`). Still open: the `agents`, `interactive` and `self-mod` module
instructions (about 7.6 KB) are inlined by NanoClaw core for every group; dropping
them needs an upstream switch or the first overlay that patches core.

### P4 — Interruptions keep the work (fixes 3)

- A new attempt mounts the existing task workspace from P2 and resumes on the same
  branch.
- Where the engine supports it, the next attempt resumes the task's own session
  transcript. Otherwise it gets the last continuation plus `git log` and
  `git diff` of the task branch.
- Account rebalance, harness-model changes, image changes, recycle and drain take
  effect only between tasks. Mid-task, only two events may stop a session: a hard
  provider limit (checkpoint, then wait) and an explicit operator terminate.
- A mid-run account switch applies the new credential and resumes the session. It
  does not kill the containers and re-send the task.

*Targets:* zero `task.released` with reason `recycle`, and a retry reaches its first
commit sooner than the first attempt did.

### P5 — Liveness from progress (fixes 4)

The heartbeat renews the lease only while the session shows activity: SDK events,
tool calls, output, or a live delegate child. The container runtime (Docker state,
process exit) is a second source. A silent session with no live child for N minutes
fails as `session_lost`, which extends `stall-visibility.spec.md`. `timeout_s`
becomes a backstop, not the main detector.

*Target:* median time from a dead session to requeue under 5 minutes (today about
120 minutes).

*Status:* partial, by a different route. The lease still renews on any heartbeat.
Instead, a vanished session container fails within 90 s as `session_lost`; a claim
with no activity for 20 min is flagged quiet in the inbox; and a quiet claim with
no signal for 60 min expires as `stalled`. A container that is alive but silent
therefore still costs up to an hour, against the 5-minute target. Measure the new
dead-to-requeue median before tightening `ARGUS_STALL_FAIL_S`.

Stall causes (stall visibility 3.7) now tell the cases apart without changing
any threshold. Each heartbeat reports what the host sees (workspace, session,
delegate). Quiet, stalled and expired claims then carry a `stall_cause`:
`workspace_missing`, `session_gone`, `silent_delegate_active`, `no_progress`
or `unknown`. A workspace that stays missing for 90 s blocks the attempt as
`env_workspace_missing` and spends no attempt. Measured: the observation behind
each quiet or stalled claim, and how many attempts that cause blocks. Not
measured: the dead-to-requeue median, and whether a silent delegate is really
working. No time target is set here, and `ARGUS_STALL_FAIL_S` stays at 3600.

### P6 — The failure class drives the retry (fixes 8)

| Class | Examples | Action |
| --- | --- | --- |
| admission | no account | not a failure (P1) |
| environment | no checkout, credential, allowlist, runtime | block, no retry, inbox item |
| transient | provider 5xx, network, overloaded | retry with backoff, same workspace |
| session | lost, crashed, timeout | retry once and resume (P4) |
| task | model gave up, tests failing | send to review or a human after one attempt |

The host wires `agentLogTail` and extends the runner overlays beyond rate limits.
The generic "agent run failed" is then reported with its cause: exit code, the last
stderr lines and the provider error.

*Status:* done ([failure classes](../specs/failure-classes.spec.md)). Generic
failures carry the session log tail, and the class picks the retry. The preflight
half of P2 shipped with it, except the executor credential probe.

### P7 — Single-layer coding run (fixes 5, 7) — experiment first

For coding tasks, the coding model is the engine. Claude Code with Sonnet or Opus
does the work in the task workspace, with no Haiku wrapper and no `argus-delegate`
hop through a 2-minute Bash call. Delegation stays only for a task that needs a
different engine (Codex, Cursor), and then as a long-running supervised process,
not a Bash tool call.

Mechanical process work moves out of the prompt and into adapter code: push, open
the PR, wait for CI, report the result. The adapter already talks to the forge
(`task-delivery.spec.md`).

This changes `engines.spec.md`. Run an A/B on about 20 comparable tasks first and
decide on three measures: success rate, tokens per succeeded task, and wall time to
a merged PR.

### P8 — Measure yield (enables everything else)

Every attempt writes a usage row, either measured or `not_reported` with a reason.
A Fleet or Cost panel and an MCP read show:
- success per attempt
- tokens and cost per succeeded task
- wall time to success
- attempts lost, by failure class

The numbers in this draft are the baseline.

*Status:* partial. Usage rows carry `task_id`, `not_reported` rows exist, and Fleet
shows tokens by outcome with `usage_tasks` of `finished_tasks` as coverage. An
attempt that reports nothing still writes no row.

## Open questions

- Can every NanoClaw engine resume a per-task session, or only Claude Code?
- Where do task worktrees live (disk budget, cleanup on terminal state, archive)?
- Does the orchestrator LLM's polling and steering cost enough tokens to belong in
  scope? It is not measured today.
- Does the `claude` executor inherit the harness's `~/.claude` settings and hooks,
  given that the directory is mounted for the whole container?

## Appendix: baseline queries

Run read-only against a copy of `data/argus.db`.

```sql
-- outcomes and attempts
SELECT state, count(*) FROM tasks GROUP BY 1;
SELECT kind, count(*) FROM events GROUP BY 1 ORDER BY 2 DESC;
-- failure reasons
SELECT json_extract(data, '$.reason') AS reason, count(*)
FROM events WHERE kind = 'task.fail' GROUP BY 1 ORDER BY 2 DESC;
-- token use by layer
SELECT role, engine, model, count(*), sum(input_tokens),
       sum(cached_input_tokens), sum(output_tokens)
FROM account_usage GROUP BY 1, 2, 3 ORDER BY 4 DESC;
```

Claim-to-outcome durations pair each `task.claim` with the next `task.fail`,
`task.complete`, `task.expire` or `task.released` for the same task, in event id
order.
