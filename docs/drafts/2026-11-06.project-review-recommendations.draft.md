# Project review recommendations

## Context

A review of the project documentation and implementation found a sound
single-node architecture, clear contributor rules, generated API contracts, and
strong documentation governance. The most important gap is test health: a
Python import cycle makes affected task-service tests fail during collection.
Operational integration checks and dependency auditing are also manual-only,
and several documentation checks warn rather than require remediation.

This draft collects the work that would improve delivery confidence without
changing the product's single-node model.

## Proposal

1. **Break the Python service import cycle.** Move shared engine-selection
   contracts to a lower-level module so `tasks`, `orchestrator`, `fleet`, and
   `accounts` do not import one another cyclically. Add a focused collection or
   import test at the lowest layer that would fail if the cycle returns.
   _Status: done — EngineChoice/EngineAccount moved to `argus_api/engine_choice.py`; regression test `apps/api/tests/test_import_cycle.py`._
2. **Automate operational assurance.** Run Docker/Kubernetes integration tests
   and dependency auditing on a scheduled workflow, then decide which changed
   paths should require them before merge. Keep developer feedback fast by
   leaving the existing changed-only checks in place.
   _Status: scheduled half done (`.github/workflows/operational-assurance.yaml`, cron "17 6 * * 1"); merge-gate half still open._
3. **Prove the Codex sandbox at runtime.** Before relying on the default-on
   profile, record an end-to-end validation with the supported host, image,
   command set, expected restrictions, and failure behaviour. Link that
   evidence from the owning sandbox spec.
4. **Make documentation findings actionable.** Remove or create the advertised
   `docs/runbooks/` section. Require a verification boundary for edited active
   specs, or document and enforce explicit exceptions rather than leaving a
   warning backlog.
5. **Add documentation entry points.** Add a short reader-oriented guide to the
   documentation index for operators, contributors, and architecture/spec
   readers. Preserve the complete catalog as the reference index.
   Status: done for the entry-point guide (docs/README.md "Where to start"); the catalog is unchanged.

## Order and success

The import-cycle fix is first because a test suite that cannot collect is not a
reliable release signal. The operational, sandbox, and documentation work can
then proceed independently.

Success means the affected Python tests collect and run; scheduled operational
checks produce visible evidence; the Codex sandbox has a repeatable runtime
receipt; and the documentation index has no stale section or unexplained
verification-boundary warnings.

## Open questions

- Which integration checks have stable enough infrastructure and duration to
  become merge gates rather than scheduled checks?
- Does the service-cycle extraction belong in an existing architecture spec, or
  does it justify a focused test-architecture spec?
- Are verification-boundary exceptions limited to documentation-only specs, or
  should they be allowed for other categories?

## Out of scope

Changing the single-node deployment model, replacing the existing test
strategy, or redesigning the product's API and dashboard architecture.
