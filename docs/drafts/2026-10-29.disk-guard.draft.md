# Disk guard: warn, pause, then shed

Status: draft · 2026-10-29

## Context

Under [operations](../specs/operations.spec.md), Argus reports
`argus_disk_free_bytes` and turns readiness false when the data directory has
less than 64 MiB free, at which point SQLite can no longer write. By then running
attempts have usually already failed on a full disk, and the failures are
classified as whatever the harness happened to report. Agents fill disks
quickly: dependency caches, build outputs, test artifacts, and checkpoints.

[Cloudroom](https://github.com/davidondrej/cloudroom) (`core/docs/storage.md`)
measures real free space and acts in bands: it warns, stops admitting new work,
freezes running agents, and only then kills the heaviest writer. History can
always be saved because the last band is kept for it.

## Proposal

One disk-guard loop on the node, polling every few seconds, measuring the
filesystems that hold the Argus data directory, the task workspaces and
checkpoints, and Docker's data root. Each is judged separately; the worst one
decides.

| Band (defaults) | Effect |
| --- | --- |
| below 5 GiB, cleared above 6 GiB | one warning event per episode; Home shows it |
| below 2 GiB | claims refused with a typed admission reason; running session containers paused (`docker pause`) |
| above 2.5 GiB | paused containers resumed; claims admitted |
| still paused after 30 s | stop the paused session whose container wrote most, fail its attempt as `env_disk_full` (no attempt consumed), resume the rest |
| below 64 MiB | today's readiness failure, unchanged |

- The hysteresis bands stop warnings and pauses from flapping around a threshold.
- A pause never replays a prompt or extends a lease silently: the lease is
  renewed with an explicit `paused_disk` heartbeat reason, so stall detection
  ([stall visibility](../specs/stall-visibility.spec.md)) does not count a
  paused attempt as quiet.
- A failed measurement counts as below 2 GiB (fail closed for new work).
- Thresholds are settings, with these defaults.

## What Argus has today

The metric, the 64 MiB readiness check, the System widgets, and
[workspace cleanup](../specs/workspace-cleanup.spec.md) (opt-in, dry-run first).
No admission gate, no pause, no per-filesystem view.

## Success

A disposable test on a small tmpfs (Cloudroom uses 512 MiB with scaled
thresholds) shows: the warning fires once, claims are refused, a writing session
pauses and resumes without losing its turn, and the heaviest writer is stopped
when space does not come back. The test never fills the host disk.

## Open questions

Resolved in [operations](../specs/operations.spec.md) 3.5:

- The API process runs the loop; the NanoClaw host needs none.
- "Wrote most" is the cgroup `io.stat` `wbytes` delta, with directory size as
  tie-break and fallback.
- Still open: should the warning band trigger a workspace-cleanup dry run
  automatically? (Out of scope for the pause slice.)

## Out of scope

Disk quotas, per-task disk budgets, and automatic deletion of anything outside
cleanup's existing verified-archive path.
