# Evals for model-facing text

Status: draft · 2026-10-31

## Context

Much of Argus's behaviour is now text that a model reads: the MCP tool names,
descriptions and schemas in `apps/api/src/argus_api/mcp_server.py`, the
orchestrator persona in `skills/argus-orchestrator/SKILL.md`, the worker
instructions, and tool results such as error strings from `_describe()`. Unit
tests confirm that a tool returns the right payload. They cannot tell us whether
a model picks the right tool, passes the right arguments, or recovers after an
error. A small change to a description can change that, and today nothing would
notice.

## Proposal

Add a top-level `evals/` package that runs real models against the real text and
scores what they do.

- **Import, never copy.** An eval loads tool definitions, the persona and the
  worker prompt from the source modules, so it always tests the current text.
- **Cases are data.** Each case has an `id`, a source (the task, PR or incident
  it came from) and checks: expected tool calls, forbidden tool calls, required
  arguments, or a rubric for a grader.
- **Real cases only.** A case reproduces a real bad experience or guards a real
  good one. It is added before the fix and must fail on the old text.
- **Controls.** Some cases are ordinary work where the right action is the
  obvious one. They catch a fix that overcorrects.
- **Repeated samples.** Each case runs several times and fails when half or more
  of its samples fail. Runs are compared with a baseline run on the same model,
  not with an absolute score.
- **Fake world.** Tool calls hit a scripted stub that returns recorded API
  responses, so an eval never touches a live Argus or spends worker time.
- **Shape.** `evals/<name>/run.py`, `cases/`, `README.md` (what it measures, how
  to run, cost). Flags: `--out` (required, gitignored `runs/`), `--model`,
  `--baseline`, `--case`. A run writes result rows and a short summary with its
  cost.
- **CI.** Evals call paid models, so CI does not run them. CI runs the graders'
  unit tests and type checks the package.

First evals:

1. `orchestrator-tools`: given an inbox state, does the orchestrator choose the
   right read tools, avoid mutating tools it does not need, and stop when done?
2. `worker-protocol`: does a worker claim, heartbeat, report progress and
   finish in order, and react correctly to a steer or a cancelled claim?

## Rules for agents

- A change to tool descriptions, schemas, tool results, the persona or worker
  instructions runs the evals that cover that text.
- A fix for a model-behaviour bug adds a failing case first.
- No user data in cases or fixtures: use placeholder paths and repositories, and
  read every captured fixture before committing it.

## Success

A description change that makes the orchestrator call the wrong tool shows up as
a failing case before it merges, with the run's cost recorded.

## Open questions

- Which models form the baseline, and is the local model included?
- Run through each engine's real harness, or call the model API directly with
  the tool list? The API is cheaper and steadier; the harness is closer to
  production.
- Who grades free-form output: a rubric model, or a person with the new output
  hidden?

## Out of scope

Benchmarking engines against each other, and any eval that needs a live worker
node.
