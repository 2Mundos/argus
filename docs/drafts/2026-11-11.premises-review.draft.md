# Premises review: yield before features

## Context

A review on 2026-11-11 of the specs, the core code and a read-only copy of the
preview database (559 tasks, 2026-10-16 to 2026-11-11). The test suite was not
run. It asks whether the premises Argus is built on hold in its own data, and
complements [project review recommendations](2026-11-06.project-review-recommendations.draft.md),
which covers test and documentation health.

The control plane is sound. The worker path it controls is still the weak part,
and the experiment that would settle it
([single-layer experiment](../specs/single-layer-experiment.spec.md)) has not
been run.

## Findings

### Premises

| Premise | Evidence | Verdict |
| --- | --- | --- |
| One process, SQLite, no required services ([single-node](../specs/single-node.spec.md)) | 559 tasks and 31k events in a 61 MB database; one writer, `tx.now`, events published after commit | Holds |
| Leased queue with account failover ([account selection](../specs/account-selection.spec.md)) | The 332-failure `quota` claim loop of the first week is gone; task success rose from 61% to 80%; p90 time to done fell from about 64 h to under 4 h | Holds |
| A cheap harness model delegating to a coding executor ([engines](../specs/engines.spec.md)) | Among measured rows in the last week the harness used 306M tokens against 224M for the executor; first-try success is about 31% of tasks; median time to done is unchanged at about 95 minutes | Unproven |
| Argus shows what the work cost ([cost view](../specs/cost-view.spec.md)) | 59% of executor usage rows in the last week are `not_reported`; 44% of measured harness rows have no cost | Half true |
| A fleet across engines, hosts and Kubernetes | One operator, one Docker pool, no routines, 5 knowledge pages; 83% of tasks created by the admin, 61% of them on Argus itself | Built ahead of demand |

Success figures exclude the `global` project. The executor token count is
understated by its unmeasured rows, so the harness share is an upper bound.

### Implementation

Strong:

- The transition model, lease fencing and failure classes.
- Generated contracts, and specs enforced by CI.
- Real dogfooding: 260 Argus tasks succeeded through Argus.

Weak:

- **Size against age.** Four weeks produced 904 commits, 79 migrations, 84
  specs and about 230k words of docs. `tasks` has over 50 columns,
  `tasks/service.py` is 4,141 lines and `integrations/nanoclaw/argus.ts` is
  5,910. This contradicts the negentropy rule.
- **NanoClaw coupling.** About 37k lines of integration, and as many of tests,
  sit on a source-level install into a third-party project, pinned to an old
  OneCLI, with items blocked on upstream.
- **Environment blocks.** In the last week 167 of 307 claims ended in `block`
  against 111 in `complete`. About 74 were environment causes
  (`runtime_preparing` 25, `env_guard_missing` 24, repository setup 11, worker
  environment 14); most of the rest were questions to a human.
- **Human latency.** 566 decisions for 559 tasks; a question waits 4.1 hours
  on average and a review 1.5. This, not model speed, sets throughput.
- **Liveness noise.** 107 `agent.lost` events with `heartbeat timeout` in the
  last week suggest one-task agents do not deregister cleanly.

## Proposal

In order:

1. **Run the single-layer A/B.** It is instrumented and 20 tasks show a large
   effect. If it wins, remove the delegate hop in a spec PR to
   [engines](../specs/engines.spec.md).
2. **Freeze features for one cycle and set a yield target**, for example
   first-claim success above 60% and median time to a pull request under 45
   minutes, measured weekly with the baseline queries of
   [worker efficiency](2026-10-24.worker-efficiency.draft.md).
3. **Resolve the environment before the claim.** Runtime image, command guard
   and repository configuration are checked at task creation or pool start,
   not once per claim.
4. **Cut question round trips.** Batch questions per task, let the
   orchestrator answer more of them, and report decisions per succeeded task.
5. **Close the cost gap or label it.** Measure executor usage for every
   engine, or show coverage next to every total.
6. **Decide on NanoClaw.** If single-layer wins, compare the integration with
   a thin runner Argus owns: container, workspace, one coding session and a
   credential proxy.
7. **Prune by evidence.** Mark unused surfaces (the Kubernetes target,
   routines, Copilot, the Windows tray) `deferred`, and split `service.py` and
   `argus.ts` along spec boundaries.
8. **Validate on other repositories.** The only external project succeeds at
   61% against 77% for Argus itself.

## Open questions

- Which yield targets are realistic before the A/B result is known?
- Are the `heartbeat timeout` losses real, or a missing deregistration at the
  end of a one-task session?
- Which unused surfaces have a planned user, and so stay?

## Out of scope

Changing the single-node model, and any change to behaviour: each proposal
that is taken up starts as its own spec change.
