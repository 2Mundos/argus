# Repeat-call reminder

## Context

A worker that calls the same tool with the same arguments over and over burns
its lease and the account's quota without progress. Argus only sees this from
outside, later: [stall visibility](../specs/stall-visibility.spec.md) notices a
session that stopped reporting progress, but a looping session keeps calling
tools, so it looks busy. Nothing in the repository detects repeated identical
calls today.

The DeepSeek harness ships an advisory guard for this
(`packages/guard/repeat-tool-reminder`, on by default). It counts consecutive
identical calls (same tool, same arguments regardless of key order) per agent.
At 3, 5 and 8 repeats it adds a message after the call's result asking the model
to read the previous result and change approach or finish. It never blocks or
delays a call, and a new user message resets the count.

## Proposal

1. **A `PostToolUse` hook beside the command guard.**
   `integrations/nanoclaw/engines/repeat_guard.py`, registered in
   `engines/claude-managed-settings.json` next to `command_guard.py` (so a
   project's own `.claude` settings cannot remove it) and installed by
   `engines/Dockerfile.tools-layer`. Matcher: every tool.
2. **The count.** Key: `tool_name` plus the canonical JSON of `tool_input`
   (sorted keys). State: one small JSON file per `session_id` under a
   container-local directory (not the workspace, not the task's outputs). A
   different key resets the count to 1. A `UserPromptSubmit` hook (a steer, a
   continuation) clears it.
3. **The reminder.** At thresholds 3, 5 and 8 the hook returns
   `hookSpecificOutput.additionalContext`. At 3 it is one short line. At 5 and 8
   it names the tool and up to 500 characters of the arguments. The call itself
   is never denied.
4. **Excluded tools.** Calls where repetition is the point: Argus's own MCP
   `heartbeat` and `wait_for_events`, and `TodoWrite`. The list is a constant in
   the hook, tested.
5. **Visibility.** Each reminder appends one line to the hook's stderr, which
   the [harness stderr tail](../specs/worker-lifecycle.spec.md) keeps, so
   the attempt shows how often it looped. No new API field in the first version.

## Engines

- **Claude (harness and executor):** covered by the hook above, as the command
  guard is.
- **Codex:** not covered. Same open question as the command guard: hook support
  in the pinned version is unverified.
- **Cursor, Copilot, OpenCode, custom, local:** not covered. Custom and local run
  Claude Code as the harness, so their harness sessions are covered; their
  executors are not.

## Success

A worker that has run the same `Bash` command five times with identical output
receives the reminder. An eval case reproducing that loop
([model-facing evals](../specs/model-facing-evals.spec.md)) passes more often
with the reminder than without it, and the ordinary-work control case is
unchanged.

## Open questions

- **Thresholds.** dsh uses 3/5/8. Our long test commands are legitimately rerun
  after edits, but an edit in between already breaks the streak. Start with
  3/5/8 and read the stderr counts after a week.
- **Should 8 escalate?** For example, a progress milestone saying "looping on
  `<tool>`", visible in the task view. Not in the first version.
- **Near-identical calls** (same command, different `timeout`) are not caught.
  Accept that, as dsh does.

## Verification boundary

- Unit tests for the hook: key canonicalisation, reset on a different call,
  reset on prompt submit, thresholds, exclusions, a missing or corrupt state
  file.
- One disposable-worker run showing that Claude Code shows `additionalContext`
  to the model (the hook output format is the risk).
