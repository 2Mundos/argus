# Worktree dev isolation

Status: draft · 2026-10-31

## Context

Agents develop Argus in git worktrees, often several at once, on the same
machine as the preview install (`~/work/argus`, `data/argus.db`, the
`argus-preview` service on :8000). `make dev-api` uses a fixed port and
`ARGUS_DATA_DIR` from the environment, so two worktrees collide, and a
misconfigured shell can point a dev server at the preview database. An empty
database is also a poor test: most views and edge cases only appear with real
tasks, attempts and accounts.

## Proposal

1. **State per worktree.** In a worktree, `make dev-api` defaults
   `ARGUS_DATA_DIR` to the worktree's gitignored `.argus/`. This default wins
   over an inherited `ARGUS_DATA_DIR`; only an explicit `--data-dir` (or a
   `make` variable) overrides it. The API refuses to start when its data dir is
   the preview checkout's `data/` and the checkout is not `~/work/argus`.
2. **Stable ports per worktree.** The API and dashboard ports derive from a hash
   of the worktree path within a fixed range, shift when occupied, and are
   printed on one `dev:` line that agents read instead of guessing.
3. **Seed from real data, one way.** `make seed-dev` (and the first `dev-api` in
   a worktree with no database) takes a read-only SQLite backup of the preview
   database and prunes it:
   - keeps recent projects, tasks, attempts, logs and knowledge;
   - drops routines, open leases and claims, queued work, agent tokens, auth
     sessions and account credentials, and disables every pool;
   - so a dev server can never start real workers, spend account quota, or reach
     real nodes.
   Copy in, never link; data never flows back. `--no-seed` starts empty. Sources
   above a size limit warn and start empty.
4. **Credentials only on request.** Accounts and secrets are not copied unless
   the flow under test needs them (`make seed-dev ACCOUNTS=1`), and then into the
   worktree's `.argus/` only.

## Success

Two worktrees run `make dev-api` at once without clashing, each on realistic
data, and neither can start a worker or touch the preview database.

## Open questions

- Prune with SQL against the copy, or with a migration-aware Python step that
  stays correct as the schema grows?
- How many recent tasks to keep by default?
- Should artifacts be copied, or served read-only from the preview data dir?

## Out of scope

Sandboxing agents themselves; this is about the developer's dev servers.
