# Failure evidence audit

Status: implemented · 2026-11-04

## Context

The DeepSeek harness's postmortem 0004 is a classification bug of a kind Argus
can have. A sandbox launcher prints a harmless notice under the same prefix as
its fatal errors. The consumer treated "prefix present plus any non-zero exit"
as a sandbox failure, so ordinary child exits (ripgrep's exit 1 for no matches)
were reported as `SANDBOX_UNAVAILABLE`. A wrapper then replaced that structured
error with its own generic one. Their lessons:

- Attribution needs several independent pieces of evidence at once (exit code
  plus an exact fatal line), not a shared prefix.
- Informational lines are excluded exactly. Unknown fatal lines still fail
  closed.
- An adapter keeps the structured failure from the layer below; it never
  replaces it with its own nearest generic category.
- Platform-dependent behaviour needs a deterministic fake at the boundary plus
  one test of the assembled path.

Argus already follows these in most places:

- OOM trusts only the container runtime's exit state ([failure classes](../specs/failure-classes.spec.md) 3.2.1).
- Claude quota and auth come from SDK marks or one exact whole-line notice
  (`overlays/claude-rate-limit.ts`).
- Quota notices are anchored at the start, after the runner's prefix, with one
  fixture shared by Python and TypeScript (`argus_core/quota.py`).

A first pass found two places that don't follow them.

## Findings

1. **Network class matches anywhere in the error.** `failure_class()` in
   `packages/core/src/argus_core/quota.py` runs `NETWORK_NOTICES.search()` on the
   whole task error. That pattern includes `timed? ?out`, `connection refused`
   and `service unavailable`. A task whose own tests time out, or whose test
   database refuses connections, is shown as `network_unavailable` in
   REST/MCP/UI instead of `implementation`. This is the same mistake as
   postmortem 0004: words in the work's output read as infrastructure evidence.
2. **Codex quota text is unanchored in the channel.** `LIMIT_TEXT` in
   `integrations/nanoclaw/overlays/codex-usage-limit.ts` matches `\b…` anywhere
   in a failed turn's error, while its Python counterpart in `QUOTA_NOTICES`
   is anchored. The shared fixture (`quota-notices.json`) does not cover this
   overlay, so the two can drift.

## Proposal

1. **Audit every text classifier** that turns engine or process output into a
   failure class, provider failure or stall cause: `quota.py`,
   `argus-accounts.ts` (`classifyFailure`, log-tail scan), `overlays/*-limit.ts`,
   `argus-stderr-tail.ts`, the stall causes in `argus.ts` (tested by `argus-stall-causes.test.ts`),
   and `argus-oom`. For each one, record in the
   [failure classes](../specs/failure-classes.spec.md) spec what it accepts as
   evidence (source, anchoring, exit code), and whether text the model or the
   work can write could forge it.
2. **Fix finding 1.** Count network evidence only from the runner's own notice
   line or a structured error code (`ECONNRESET` on the engine's API call), not
   from anywhere in the error. Add failing rows first: a test-timeout error and
   a refused test database, both expected as `implementation`.
3. **Fix finding 2.** Anchor `LIMIT_TEXT` the way `quota.py` does, and add the
   overlay to the shared `quota-notices.json` test so the copies cannot drift.
4. **Rule for the spec.** "A failure class is attributed from evidence the work
   cannot write: a structured field, an exit status, or an anchored runner line.
   A wrapper keeps the class it receives."

## Success

Every classifier is listed in the spec with its evidence. The two findings have
failing tests that now pass. Nothing in the work's own output can be read as
quota, auth or network evidence.

## Open questions

- Is any decision driven by `network_unavailable` (retry, backoff), or is it
  display-only? If a retry depends on it, finding 1 causes wasted retries, not
  just a wrong label.
- Should the audit include the `oom_kill` path's fallbacks? It already rejects
  text; probably not needed.
