# Verification boundary in specs

Status: draft · 2026-10-29

## Context

Argus specs say what is decided and what the implementation must do. They do not
consistently say how far the behaviour has actually been verified. Did it run
against fixtures, a fake API, a disposable node, real inference, or production?
Against which harness versions? Reports in `docs/reports/` carry that evidence
for some features, and runbooks such as
[validating Claude and Codex as executors](../runbooks/2026-10-21.executor-layer-validation.ref.md)
note "procedure, not yet run". Elsewhere the reader has to guess.

[Cloudroom](https://github.com/davidondrej/cloudroom) ends most core docs with a
"Verify" list of exact commands and a "Verification boundary" paragraph, for
example: "Local probes against Claude Code 2.1.278 verified … These are not
real-inference evidence. Logged-in Linux/GUI acceptance … remain required before
claiming deployment readiness." The paragraph is short. It stops a fixture pass
from being read as production proof, and it pins the harness versions a change
was tested with.

## Proposal

Add a required subsection to the spec template, under
`# 6. Implementation Consequences`, so the six-section structure and
`scripts/validate_docs.py` are unchanged:

```markdown
## Verification boundary

- Commands: the exact commands that check this spec (make targets, test files).
- Verified: what those checks establish, at which level (unit, fixture, fake API,
  disposable node, real inference, production), with harness/CLI versions where
  behaviour depends on them.
- Not verified: what still needs evidence before the behaviour can be called
  shipped, with a link to the report or runbook that will hold it.
```

- New and edited specs fill it in. Existing specs gain it when next edited; no
  bulk rewrite.
- A spec that claims real-inference or production behaviour links the
  `docs/reports/` receipt that shows it.
- The validator could later warn, not fail, when the subsection is missing.

## Success

A reader can tell from any recently edited spec, without reading code, whether a
behaviour has been seen working with a real model and which CLI versions it
depends on.

## Open questions

- Required for every spec, or only for specs that touch harnesses, accounts and
  node operations, where versions and real inference matter?
- Should harness version pins live in one place (the engines layer) and be
  referenced from specs, rather than repeated?

## Out of scope

Changing the six-section template headings, or requiring reports for pure UI or
documentation specs.
