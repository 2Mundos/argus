# Engine transcript replay

## Context

The [replay engine](2026-10-31.replay-engine.draft.md) replays what a worker
sends to Argus, so the API and dashboard can be tested without a model. The
other side is untested the same way. The channel and its overlays parse what
each engine emits: Claude SDK messages, Codex app-server events, Copilot and
Cursor CLI output, usage records, stderr. They turn it into failure kinds,
provider failures, usage and stall causes. Today those parsers are tested with
hand-written strings and a few fixtures (`integrations/nanoclaw/fixtures/`:
`continuation/`, `copilot-cli/probe-*.json`). Hand-written strings show what we
think an engine emits, not what it does emit. An engine version bump can change
the format without any test failing.

The DeepSeek harness works this way: every model- or user-visible change comes
with a recorded session that CI replays without an API key. Recording needs a
key and happens locally; CI only replays (`DSH_SNAPSHOT=replay`), and every
re-recorded diff is reviewed.

## Proposal

1. **Recordings.** `integrations/nanoclaw/fixtures/transcripts/<engine>/<case>/`
   holds:
   - `events.jsonl`: the engine's raw output, one event or line per row;
   - `stderr.txt` when the case depends on it;
   - `expected.json`: what Argus must derive from it (failure kind,
     providerFailure, usage totals, stall cause, final output presence);
   - `source.md`: one line naming the task or incident and the engine version.
2. **Recorder.** `scripts/record_transcript.py` copies an attempt's raw engine
   output from a worker session's logs on a database or volume copy (never the
   live preview data). It redacts tokens, emails, absolute home paths and
   repository names, and writes a draft `expected.json` from what the current
   code derives. A person reviews the redaction and the expected values before
   committing.
3. **One table test.** `transcripts.test.ts` feeds each recording through the
   same functions the channel uses (`claudeRateLimitError`,
   `codexUsageLimitFailure`, `classifyFailure`, `recordHarnessLog`, the stderr-tail
   parser) and compares with `expected.json`. No Docker, no model, no network.
   `make check` runs it.
4. **First cases, one per real outcome:** Claude success, Claude session limit,
   Claude auth failed, Codex usage limit with structured `codexErrorInfo`, Codex
   success, Copilot success, Cursor success, a network drop mid-stream, an OOM
   kill.
5. **Rule.** An engine version bump re-records at least the success case and one
   failure case for that engine in the same PR. A parser bug fix adds the
   transcript that exposed it.

## Engines

Claude, Codex, Copilot and Cursor each get recordings. Custom and local run
Claude Code, so their recordings cover the bridge's translated errors (HTTP
402/429 from OpenRouter, Strata unavailable).

## Success

Bumping an engine whose output format changed fails a test before deploy. A bug
in quota or auth parsing can be reproduced from a committed file, without a
model.

## Open questions

- Where do raw engine events survive today? NanoClaw keeps `docker logs` stdout
  but drops container stderr ([harness stderr tail research](../research/2026-10-29.harness-stderr-tail.research.md)).
  The recorder may need that draft shipped first.
- ~~How big may a recording be?~~ Settled: 200 KB per case. `scripts/record_transcript.py`
  trims strings over 2000 characters (then 500, then 120 if still too large) and keeps
  the event structure. It copies the attempt's delegate log (`task_log`) only; redaction
  beyond the API's, `expected.json`, `source.md` and the table test are still to do.
- Should expected values be compared field by field, or the whole object?
  Field by field is easier to review.
