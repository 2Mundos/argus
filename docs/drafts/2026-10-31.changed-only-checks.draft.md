# Changed-only checks

Status: implemented · 2026-10-31

## Context

The pre-push hook runs `make check` and `make build` on the whole repository,
skipping only trees that passed before. A one-line docs or dashboard change
still runs the full Python suite, ty, tsc and the OpenAPI check. That is slow,
and long hooks have caused pushes to drop while the hook runs.

## Proposal

Add `make check-changed` (`scripts/check_changed.py`) and use it in the
pre-push hook. It compares the working tree with the merge base of
`origin/main` and runs only what the changed files can affect:

| Changed | Runs |
| --- | --- |
| any `*.py` | ruff check and format on changed files; ty on affected packages |
| `apps/api/**` or `packages/core/**` | pytest on tests beside the changed modules and tests that import them |
| API routes or models | OpenAPI check |
| `apps/dashboard/**`, `packages/api-client/**` | Biome on changed files, tsc, Vitest on related tests, build |
| `docs/**` | `validate_docs.py` |
| migrations | migration preflight and the full Python suite |
| lock files, `pyproject.toml`, `package.json` | the full `make check` |

- Steps run in parallel within a budget based on CPU count, each prints its
  output when done, and a step past its timeout is killed and reported.
- A rerun on exactly the files of the last passing run prints that summary and
  exits.
- The gitleaks scan still runs on every push.
- CI keeps running the full suite; `make check` stays available for a full local
  run.

## Success

A docs-only push finishes its hook in seconds, and a dashboard-only push never
runs pytest.

## Open questions

- How to find "tests that import the changed module": a static import graph, or
  the existing graft index?
- Should the hook fall back to `make check` when the merge base cannot be found
  (shallow clone, detached head)?

## Out of scope

Changing what CI runs.
