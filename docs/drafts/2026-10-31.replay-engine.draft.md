# Replay engine

Status: draft · 2026-10-31

## Context

Seeing a task move through Argus end to end (claim, live log, progress
milestones, changes, delivery) needs a real worker and a real model. That costs
money and minutes, so dashboard work on the task view, live log and Fleet tab is
often checked against an empty or hand-written database. The `scripts/*-e2e.sh`
runs avoid models but cover one protocol path each.

## Proposal

Add a dev-only **replay** worker: it claims a task and plays back a recorded
attempt through the real API, with no model.

- **Recording.** `scripts/record_attempt.py <task_id> <attempt>` reads an
  attempt's events, log lines, progress reports, model reports and final output
  from a database copy and writes a JSON fixture with relative timestamps.
  Secrets and absolute paths are redacted; the fixture is reviewed before it is
  committed under `apps/api/tests/fixtures/replay/`.
- **Playback.** `argus-replay --fixture <file> [--speed 4]` registers as an
  agent in a `replay` pool, claims the next task in that pool, and sends the
  recorded calls in order through the same MCP tools a worker uses
  (`claim_task`, `heartbeat`, `report_progress`, log append, finish). Steers and
  cancels arriving during playback are honoured, so those paths can be tested
  too.
- **Off by default.** The pool and the command exist only when
  `ARGUS_DEV_REPLAY=1`. Nothing registers it in production.

Uses:

- Develop the task detail, live log and Fleet views against realistic data.
- An integration test that replays a fixture at high speed and asserts the
  resulting task state, without Docker or a model.

## Rule for agents

Use the replay worker to watch a task flow through the system. Use a real engine
only when the change depends on that engine's behaviour, and then its cheapest
model.

## Success

A dashboard change to the live log can be checked against a realistic task in
under a minute, with no model spend.

## Open questions

- Replay through MCP (closest to a worker) or the REST routes (simpler)?
- Should fixtures include the workspace diff so task changes and delivery can be
  replayed, or only the event stream?

## Out of scope

Simulating engine-specific failures (quota, auth, OOM); those stay with the
failure-class tests.
