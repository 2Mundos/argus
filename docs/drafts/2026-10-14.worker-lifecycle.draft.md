# Worker Lifecycle and Task Coordination — Draft

Status: draft. When finalized this becomes `docs/specs/worker-lifecycle.spec.md`
and likely splits into `task-model.spec.md` and `fleet-provisioning.spec.md`.

# 1. Purpose and Scope

Define how Argus coordinates a fleet of agents:

- **Tasks**: what a unit of work is, its states, and how a worker claims, runs,
  and finishes one with only its current lease holder authorized to update it.
- **Agents**: how a worker or orchestrator registers, proves it is alive, and is
  declared lost.
- **Instances**: how Argus starts and stops the containers agents run in, at the
  request of the orchestrator or a human.

Actors:

| Actor | Does |
| --- | --- |
| Orchestrator agent | Breaks goals into tasks, sets fleet size, reviews results. |
| Worker agent | Claims tasks it can do, works on them, reports results. |
| Human (dashboard) | Watches everything; can create/cancel tasks, scale pools, kill instances. |
| Argus | Holds the state, enforces the rules below, runs the reconciler and reaper. |

# 2. Non-Goals

- Argus does not run agent logic, prompt models, or judge result quality. It
  stores state and enforces transitions; agents do the thinking.
- No general workflow engine (no loops, conditionals, timers in the task graph).
  Dependencies between tasks are the only control flow.
- No push-based dispatch. Workers pull; Argus never sends work into a container.
- No multi-tenancy in v1. One Argus deployment serves one fleet.
- No cross-host scheduling cleverness in v1 (bin-packing, affinity). One
  target per pool.
- No spend enforcement in v1. Usage is recorded (3.9), not capped.

# 3. Decisions Made

## 3.1 Data model

Postgres is the only store. Four tables, plus an append-only event log.

- **`pools`** — a named group of interchangeable workers: `name`, `image`,
  `capabilities[]`, `desired_replicas`, `max_replicas`, `provisioner`
  (`docker` | `nanoclaw`), `config` (jsonb: env, resources).
- **`instances`** — one container: `id`, `pool`, `provider_ref` (container id),
  `state`, `created_at`, `terminated_at`, `exit_reason`.
- **`agents`** — one registered agent identity: `id`, `role`
  (`orchestrator` | `worker`), `instance_id` (nullable: an orchestrator may run
  outside Argus), `capabilities[]`, `state`, `last_heartbeat_at`.
- **`tasks`** — `id`, `parent_id`, `title`, `spec` (text the agent reads),
  `input` (jsonb), `required_capabilities[]`, `priority`, `state`,
  `assignee_agent_id`, `lease_expires_at`, `attempt`, `max_attempts`,
  `result` (jsonb), `error`, `created_by`, timestamps.
- **`task_deps`** — `(task_id, depends_on_id)`.
- **`events`** — `id bigserial`, `at`, `actor`, `subject_type`, `subject_id`,
  `kind`, `data` (jsonb). Every state transition writes one row in the same
  transaction. The dashboard timeline and audit trail are this table.

Large outputs (files, logs) are not stored in `result`; `result` holds
references. Where those references point is Open Question 4.6.

## 3.2 Task state machine

```
            deps done              claim                 complete
 pending ─────────────▶ ready ─────────────▶ claimed ─────────────▶ succeeded
    │                     ▲                    │  │
    │                     │ lease expired,     │  │ fail (attempt < max)
    │                     │ attempt < max      │  └──────────────▶ ready
    │                     └────────────────────┤
    │                                          │ fail / expire (attempt = max)
    │                                          └──────────────▶ failed
    │                                          │ needs input
    │                                          └──────────────▶ blocked ──▶ ready
    └── cancel (any non-terminal state) ──▶ cancelled
```

- A task with no unfinished dependencies is created directly in `ready`.
- When a task `succeeded`, dependents whose dependencies are all done move to
  `ready` in the same transaction.
- If a dependency ends `failed` or `cancelled`, dependents stay `pending` and an
  event is raised for the orchestrator to decide (cancel, replace, or retry).
  Argus does not cascade cancellation on its own.
- `blocked` means the worker needs something it cannot get (human input,
  credentials). The lease is released; the task returns to `ready` when
  unblocked by the orchestrator or a human.
- Terminal states: `succeeded`, `failed`, `cancelled`.

## 3.3 Claiming: leases, not locks

- `POST /tasks/claim` with the worker's capabilities. Argus selects the highest
  priority, oldest `ready` task whose `required_capabilities ⊆ agent.capabilities`
  using `SELECT … FOR UPDATE SKIP LOCKED LIMIT 1`, sets `claimed`, the assignee,
  increments `attempt` (initially zero), and sets the lease deadline from the
  database clock plus `lease_ttl`, all in one transaction.
- Claim long-polls (up to 30 s) when nothing is ready, so idle workers do not
  hammer the API. Implemented with `LISTEN/NOTIFY` on task readiness.
- Every worker mutation of a claimed task, including completion, failure,
  blocking, subtask creation, and lease renewal, carries `(task_id, attempt)`.
  In the same transaction as the write, Argus checks that the authenticated
  agent is active (`busy` or `draining`), the task is `claimed`, its assignee
  matches that agent, its attempt matches, and `lease_expires_at` is strictly
  later than the database clock. A failed ownership check returns `409` without
  changing the task, even if the reaper has not processed expiry yet. Revoked
  credentials return `401`.
- Claims, worker writes, heartbeats, and reaping serialize through row locks:
  lock the agent first, then affected tasks in id order, and recheck their
  state. Read `clock_timestamp()` after acquiring the locks; transaction-start
  time or a worker's clock must not validate a lease that expired while waiting.
  Renewal sets the deadline to that fresh database time plus `lease_ttl` and
  cannot revive an expired lease. Leaving `claimed` clears the assignee and
  deadline in the same transaction as the transition and its event.
- These rules fence writes to Argus. Execution is at least once: an expired
  worker can continue external work while a retry runs. Workers must stop work
  when renewal is rejected or the last confirmed lease expires. External
  effects need destination-enforced idempotency using a stable operation key
  across attempts, or destination-enforced fencing; Argus cannot guarantee
  exactly-once effects in another system.
- Defaults: `lease_ttl = 120 s`, heartbeat every 30 s, `max_attempts = 3`.
  Per-task override allowed.

## 3.4 Agent liveness

- Agent states: `registering → idle ⇄ busy → draining → gone`, plus `lost`.
- An agent registers on boot with a one-time bootstrap token injected into its
  container, and receives a long-lived agent token (3.6).
- One heartbeat call (`POST /agents/{id}/heartbeat`) refreshes the agent and
  renews the submitted list of `(task_id, attempt)` pairs using 3.3. The response
  lists renewed leases with their deadlines and rejected pairs; a rejected pair
  does not renew that task or prevent other valid pairs from renewing. Agent
  liveness can refresh even when a task lease is rejected. Workers do not
  heartbeat per task.
- The **reaper** loop (every 10 s) independently expires task leases whose
  deadline has passed, including leases belonging to agents still sending
  heartbeats. It also marks agents with
  `last_heartbeat_at < now() - 3 × interval` as `lost`, expires their leases
  (tasks go back to `ready` or to `failed` per 3.2), revokes their agent and
  unused bootstrap tokens, and requests termination of their instances. Agent
  loss, credential revocation, task transitions, and events commit together
  under the locking rules in 3.3. Provider calls happen after commit.
- `lost` is irreversible for that identity. A late heartbeat cannot restore it,
  renew a lease, or authorize another claim; the old instance cannot register
  again. A replacement gets a new instance id and bootstrap token.
- `draining`: the agent finishes its current task, claims nothing new, then
  exits. Used for scale-down and for rolling a pool to a new image.

## 3.5 Provisioning: desired state + reconciler

Nobody "spawns a container" directly. The orchestrator or a human sets
`pools.desired_replicas`; a **reconciler** loop compares desired vs. live
instances and converges:

- Capacity counts every instance not confirmed terminated, including starting,
  draining, terminating, and unreachable instances. Reserve a slot in Postgres
  before each start; both `desired_replicas` and `max_replicas` constrain starts.
  An ambiguous start result retains its reservation and is resolved through
  provider lookup by the stable instance id before another start is attempted.
- Too few occupied slots → start instances through the pool's provisioner.
- Too many → mark the newest idle agents `draining`; never kill a busy agent
  for scale-down.
- Instance whose agent is `lost` → mark the instance `terminating` and request
  `stop` with a bounded grace period followed by forced termination. Agent loss
  alone never records a container exit or frees its capacity slot. Retrying
  `stop` for the same provider reference is safe, including after API restart.
- Set an instance's terminal state and `terminated_at` only after a successful,
  authoritative provider query confirms it stopped or no longer exists. A
  timeout, connection failure, or stop acknowledgement is not confirmation.
  Until confirmed, retain the slot, retry termination, and surface the unresolved
  instance to the operator. Replacement for that instance waits for confirmation
  and then starts only if occupied capacity is below desired and the cap.
- Container confirmed exited → revoke its agent and bootstrap tokens and expire
  any remaining leases in the same transaction as recording termination, then
  replace it if still below desired. An idle or draining instance follows the
  same confirmation rule before its slot is freed.
- `max_replicas` caps what an orchestrator can request. Raising the cap is a
  human-only action (guards against a runaway orchestrator scaling to the moon).

Reconciliation makes the system self-healing and makes "the orchestrator asked
twice" harmless. It runs inside the API process at first (single replica,
guarded by a Postgres advisory lock so a second replica would idle).

Provisioning has two independent axes, so N targets × M runtimes do not need
N×M implementations:

- **Target**: *where* a container runs. Two implementations cover the three
  required forms:
  - `docker`: the Docker Engine API. Local socket and remote host are the same
    code; only `DOCKER_HOST` differs (`unix://…`, `ssh://user@host`, or
    `tcp://…` with TLS).
  - `kubernetes`: one Pod per instance, created by Argus in a configured
    namespace (no CRD or operator in v1).
- **Runtime**: *what* runs in the container and how it is wired to Argus
  (image, env, mounts, how the agent learns its bootstrap token). v1 runtimes:
  `nanoclaw` (3.8) and `plain` (any image that speaks the Argus API itself;
  used for CI integration tests and custom workers).

```python
class Target(Protocol):
    async def start(self, spec: ContainerSpec) -> str: ...  # returns provider_ref
    async def stop(self, provider_ref: str, *, grace: timedelta) -> None: ...
    async def list(self, labels: Mapping[str, str]) -> list[ProviderInstance]: ...


class Runtime(Protocol):
    def container_spec(
        self, pool: Pool, instance: Instance, bootstrap: str
    ) -> ContainerSpec: ...
```

A pool names one target and one runtime. `list()` filters on Argus labels
(`argus.instance_id`, `argus.pool`) so the reconciler finds containers that
died silently, and orphans Argus did not start.

## 3.6 Auth and scopes

Bearer tokens, hashed in Postgres. Three scopes:

| Scope | Can |
| --- | --- |
| `worker` | Claim, heartbeat, update/complete/fail/block its own tasks, create subtasks under a task it holds. |
| `orchestrator` | Everything `worker` can, plus create/cancel any task, edit deps, set `desired_replicas` up to `max_replicas`, drain agents. |
| `admin` (human) | Everything, including pool definitions, `max_replicas`, killing instances, revoking tokens. |

Tokens are scoped to one agent and revoked when the agent becomes `lost` or its
instance terminates. Unused bootstrap tokens for that instance are also revoked;
revocation does not wait for an unreachable container to stop.

## 3.7 Interfaces

- **REST** (FastAPI) is the source of truth; its OpenAPI schema generates the
  dashboard client (`@argus/api-client`).
- **MCP server** for agents: thin tools mapped 1:1 onto REST calls
  (`claim_task`, `heartbeat`, `complete_task`, `fail_task`, `block_task`,
  `create_task`, `scale_pool`, …). LLM agents use tools far more reliably than
  hand-built HTTP calls. The MCP server holds no state or logic of its own.
- **SSE** stream (`GET /events/stream`) for the dashboard, fed by the `events`
  table through `LISTEN/NOTIFY`.
- Every mutating call accepts an `Idempotency-Key` header; agents retry often.

## 3.8 NanoClaw runtime

NanoClaw is a single Node.js **host** process that itself spawns one Docker
container per agent session, talking to it through per-session SQLite files
(`inbound.db` / `outbound.db`). It keeps credentials out of agent containers by
injecting them at the HTTPS layer (OneCLI Agent Vault or Iron Proxy), has a
pluggable provider interface (Claude Code by default), supports user-added MCP
servers, and is administered locally by the `ncl` CLI over a Unix socket (no
HTTP admin API). See https://docs.nanoclaw.dev/concepts/architecture.

Consequences for Argus:

- **The unit Argus provisions is a NanoClaw host, not an agent container.**
  One Argus instance = one NanoClaw host container (with access to a Docker
  daemon: the socket on a Docker target, a DinD sidecar on Kubernetes). Each
  NanoClaw agent group inside it registers with Argus as one agent, so one
  instance can carry several agents (`pools.agents_per_instance`).
- **Argus ships a NanoClaw module** (`integrations/nanoclaw`, TypeScript),
  baked into an image built `FROM` the NanoClaw base. It uses the module and
  channel extension points (`onHostStart`, channel registry):
  1. On host start, redeems the bootstrap token and registers its agent groups.
  2. Long-polls `POST /tasks/claim` per idle agent group, deterministically (in
     code, not an LLM loop that burns tokens polling).
  3. Writes the claimed task as an inbound message, which wakes the agent
     container.
  4. Heartbeats Argus while the session's `/workspace/.heartbeat` is fresh;
     maps NanoClaw's own stale-container kill to a task failure.
- **Agents talk back through the Argus MCP server** (3.7), added to each agent
  group as a user MCP server: `report_progress`, `complete_task`, `fail_task`,
  `ask` (3.10), `create_task`. The module scopes the agent's token to the task
  it holds.
- **Credentials stay in NanoClaw's gateway.** Argus decides *which* account a
  session uses (3.9) and the module points the session at it; raw secrets do
  not travel through Argus task payloads.

Unconfirmed and to verify against the NanoClaw source before implementation:
whether a module can create inbound messages without a chat platform behind
it, whether the gateway credential can be switched per session at spawn time,
and whether the host tolerates running under Kubernetes with DinD.

## 3.9 Account pool and fallback

Agents run on subscription or API accounts (Claude, Codex, Cursor, …) that hit
usage limits. Argus owns the **account registry and leasing**; providers'
credentials stay in a secret store.

- **`accounts`**: `id`, `provider` (`anthropic` | `openai` | `cursor` | …),
  `kind` (`api_key` | `subscription`), `secret_ref` (pointer into the gateway
  vault or a secret store, never the secret itself), `priority`, `state`
  (`available` | `exhausted` | `disabled`), `exhausted_until`, `labels`.
- **Leasing**: an agent session leases one account
  (`POST /accounts/lease {providers: [...]}`), choosing the highest-priority
  `available` account among the providers its runtime supports. Leases follow
  the agent's heartbeat like task leases do.
- **Fallback**: when a provider call fails with a quota or rate-limit error, the
  agent (or the NanoClaw module watching the session) calls
  `POST /accounts/{id}/exhausted {until}`. Argus marks it exhausted until the
  reported reset time (or a per-provider default), and the caller gets the next
  account. Fallback first prefers another account of the same provider, then
  another provider if the runtime supports it. An account returns to
  `available` automatically when `exhausted_until` passes.
- **No accounts left**: the agent's task goes `blocked` with reason
  `no_account`, and every waiting agent is visible on the dashboard with the
  earliest reset time.
- **Usage is recorded, not enforced** (decision): agents report
  tokens/cost per task and account; Argus aggregates per account, pool, and task.
  Budgets that block work are out of scope until wanted.

Check each provider's terms before pooling subscription accounts for
automated use; some consumer plans restrict it.

## 3.10 Decision requests (human in the loop) — proposed

One primitive covers every "someone must decide before this continues" case,
instead of a special state per case. A **decision request** has `subject`
(task, pool, agent), `question`, `options` (or free text), `requested_by`,
`audience` (`human` | `orchestrator` | `any`), `state`, `answer`, `decided_by`.

Uses:

- **Questions from a worker**: the `ask` MCP tool (NanoClaw's agents already
  have an `ask_user_question` pattern). The task goes `blocked` until answered;
  the answer is delivered back as a message to the agent.
- **Start gate**: a task created with `requires_approval` waits in
  `awaiting_approval` before `ready`.
- **Review gate**: a task created with `review: human | orchestrator` goes to
  `in_review` on completion instead of `succeeded`. Reject sends it back to
  `ready` with the reviewer's notes appended (attempt not counted as failure).
- **Policy gates**: scaling a pool above a threshold, or an orchestrator
  creating more than N tasks per hour, opens a decision request instead of
  failing outright.

The dashboard has an **inbox** of open requests. Notifications to a chat
platform come later, possibly through a NanoClaw channel.

## 3.11 Task kinds and result envelope — proposed

Hybrid of free text and typed contracts:

- Every task has `spec` (Markdown the agent reads) and `acceptance` (a list of
  checkable criteria, which makes review gates concrete).
- Every task has a `kind`. A **`task_kinds`** registry can attach a JSON Schema
  for `input` and for `result.data`, default `required_capabilities`, default
  lease, and default review policy. A kind without schemas is free-form, so
  ad-hoc work never waits on a schema being written.
- Every result uses one envelope, validated server-side:
  `{summary: str, data: object | null, artifacts: [ArtifactRef], usage: Usage}`.
  `data` is validated against the kind's schema when one exists; a failing
  result is rejected with the validation errors so the agent can retry.

## 3.12 Progress, logs, and artifacts — proposed

Three kinds of output with different access patterns, three homes:

| Output | Example | Home |
| --- | --- | --- |
| Progress notes | "tests written, fixing 2 failures" | Postgres `events` (`kind = progress`); shown on the dashboard live. A progress post also renews the lease. Rate-limited per task (e.g. one per 10 s). |
| Logs and transcripts | agent stdout, tool calls, provider requests | OpenTelemetry Collector → Elasticsearch/OpenSearch (Kibana for search). Every record carries `task_id`, `agent_id`, `attempt`, so the dashboard deep-links into Kibana. |
| Artifacts | files, diffs, reports, screenshots | S3-compatible object store, keyed `tasks/<task_id>/<attempt>/…`; `result.artifacts` holds the references. Argus issues presigned upload URLs so bytes never pass through the API. |

On Logstash: it is a pipeline, not a store, so the real choice is the backend
(Elasticsearch, which the team already runs for Radar, is a good one). For the
pipeline, the OpenTelemetry Collector (or Vector) is lighter than Logstash and
keeps us vendor-neutral, and OTel is what agent SDKs and NanoClaw-style tooling
already emit. Logstash would work if there is existing Logstash expertise or
pipelines to reuse.

# 4. Open Questions

1. **NanoClaw details** listed at the end of 3.8 (module-created inbound
   messages, per-session credential switching, Kubernetes + DinD).
2. **Account secret store**: reuse NanoClaw's OneCLI vault as the store for
   every runtime, or keep a separate store (SOPS, Vault, Kubernetes secrets)
   with the vault fed from it?
3. **Exhaustion signals per provider**: which errors and headers reliably mean
   "quota exhausted until T" for Claude subscriptions, Codex, and Cursor?
4. Accept the proposals in 3.10 (decision requests), 3.11 (task kinds), and
   3.12 (OTel + Elasticsearch + S3)?
5. Which S3-compatible store for self-hosted setups (Garage, SeaweedFS, or a
   cloud bucket)?

# 5. Constraints

- Postgres is the only stateful dependency. No Redis or message broker until a
  measured need appears; `SKIP LOCKED` and `LISTEN/NOTIFY` cover v1.
- Workers can crash, hang, or lose the network at any point. Every rule above
  must hold under those conditions; correctness comes from leases and fencing,
  never from trusting an agent to report its own death.
- Agents are LLMs: their calls may repeat, arrive out of order, or carry wrong
  ids. The API validates every transition server-side and returns clear,
  actionable errors.
- A runaway orchestrator must not be able to exhaust the host (`max_replicas`,
  human-only cap changes).

# 6. Implementation Consequences

Suggested build order, each step shippable and testable on its own:

1. **Schema + migrations.** Alembic in `apps/api`, tables from 3.1, Postgres in
   CI (service container in `quality.yaml`).
2. **Task API.** Create/list/get, the 3.2 state machine as one pure function
   with exhaustive tests, claim with `SKIP LOCKED`, atomic ownership and deadline
   checks from 3.3, events. Cover writes and renewal after expiry but before
   reaping, stale attempts after reassignment, and expiry while waiting on locks.
3. **Agents + reaper.** Register, batched heartbeat renewal, independent task
   lease expiry, irreversible `lost` handling and immediate token revocation.
4. **Auth scopes** (3.6).
5. **Dashboard v1.** Task board, agent list, event timeline over SSE.
6. **Pools + reconciler + `docker` provisioner**, with an integration test that
   scales a pool of a trivial worker image up and down. Cover agent loss while
   its container stays running, unreachable providers, and API restart during
   termination or an ambiguous start; unresolved instances retain capacity and
   replacements wait for confirmed termination.
7. **MCP server** (`apps/mcp`) over the REST client.
8. **`nanoclaw` provisioner**, after 4.1.

`argus_core` holds the state enums, transition table, and Pydantic models shared
by the API, the MCP server, and any Python worker SDK.
